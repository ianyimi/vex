## Deviations from spec

- **`collection` shape is `{ slug: TSlug }` object, not plain `TSlug` string.** The spec originally used a bare string. Kept as object to preserve room for future options (e.g. `label`, `filter`) without a breaking API change.
- **Validator always emits `v.array(v.id(...))`.** Spec branched on `hasMany`. Changed so the Convex schema is always an array — prevents a migration when toggling `hasMany` on an existing collection. `hasMany` is now UI-only.
- **`inputSchema` always uses `z.array(z.string()).default([])`.** Same rationale — form value is always `string[]`.
- **`constants.ts` `defaultValue` is `[] as string[]`**, not `undefined`. Matches the always-array storage decision.
- **`interfaceType` is static `"Id<CollectionSlug>[]"`**, not computed per-slug. Per-slug dynamic generation deferred.
- **File is `collections/validator.ts`**, not `collections/schemaGen.ts` as the spec named it. The file already existed under this name.
- **Explicit `field.index` suppresses auto `by_<fieldKey>` index** (`else if` in the index generation loop). Spec said both are always emitted. Changed so explicit takes precedence — avoids duplicate indexes on the same field.
- **Auto search index emitted once** regardless of how many collections point here. Deduplication also suppresses the auto index when a manually configured `searchIndex` has the same name (`search_${useAsTitle}`).

## Decisions made

- Always-array storage for relationship fields trades a small API surprise (`field[0]` for single values) for zero schema migrations when switching between single and multi-select. Considered the right trade-off given Convex's strict schema migration requirements.
- `collection: { slug }` object shape chosen over bare string to make the API extensible without a breaking change.
