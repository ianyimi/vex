## Verification method chosen

- Primary: browser at `http://localhost:3020` (apps/www) via built-in `browse` tool.
- Secondary: `pnpm --filter <pkg> typecheck` + `pnpm --filter <pkg> test` (Vitest).
- Tertiary: tmux pane 1 (`pnpm dev` output).

## Debug hierarchy chosen

UI-first order (browser console → tmux → git diff → ideaLog → tests → specs), because most vexcms bugs surface in the admin UI. No known fragile areas recorded yet — `/sync-spec` will populate that table over time.

## Commit conventions chosen

Conventional Commits with **required package-name scope** (`core`, `cli`, `next`, `react`, `www`, `repo`, etc.) plus a `Changeset:` line in the body whenever a published package's public surface changes. Created a bespoke `/changeset` prompt that reviews commits since the last `.changeset/*.md` and produces a copy-pasteable Changesets entry.

## Key decisions for agent reference

- Agent does NOT write code in `packages/*/src/**` unless explicitly asked — high-care tier.
- Always use `pnpm --filter <pkg>` for per-package tasks; avoid root `pnpm test` in a loop.
- The www app uses port **3020**, not the Next.js default 3000.
- Types colocated with implementation (`types.ts` next to `config.ts`) — never consolidate.
- Framework-adapter components use framework prefix (`NextAdminPage`), not `Vex`.
