# 2026-05-03 — Relationship Field End-to-End

## 2026-05-03 — Relationship field: core + react implementation

**Spec:** `.pi/agent-docs/specs/22-relationship-field.md`

The relationship field was the last major unimplemented field type blocking
a working admin UI. The decision was to wire it fully — core types through
Convex schema generation through React components — rather than stub it, so
that the generated schema is actually deployable once an app wires up a
relationship.

### Why validator.ts instead of schemaGen.ts

`schemaGen.ts` generated per-collection Convex `defineTable(...)` strings
but had no awareness of the rest of the config. Renaming to `validator.ts`
(matching the naming convention of all other field files) and threading the
full `VexConfig` through allowed two automated behaviours:

1. **Auto FK index**: any relationship field gets a `.index("by_<fieldKey>", ["<fieldKey>"])` unless the field already has an explicit `index` name.
2. **Auto search index**: when another collection has a relationship pointing *here*, the target collection's `useAsTitle` field gets a `.searchIndex("search_<useAsTitle>", ...)` automatically — which is exactly what the `search` Convex query needs.

This removes manual boilerplate from every app that defines relationships.

### Why storage is always `string[]` regardless of `hasMany`

Convex migrations are disruptive. Storing a single reference as `v.id(…)` and later toggling `hasMany: true` would require a schema migration to move to `v.array(v.id(…))`. By always using an array, `hasMany` becomes a UI-only constraint — the data shape never changes.

### sanitizeConfigForClient

Server-side `VexConfig` includes React component references (field input/cell components) that can't cross RSC serialization boundaries. `sanitizeConfigForClient` walks the tree recursively and replaces all functions, symbols, and class instances with `null`. It's intentionally exhaustive so that new non-serializable properties added anywhere in the config are stripped automatically.

### AdminTopNav breadcrumb

The header previously had only a sidebar toggle. Now it renders Home → Collection → Document breadcrumbs, resolving the active document title from Convex at runtime. The breadcrumb direction adapts to `config.admin.sidebar.side` (left sidebar = chevron-right dividers, right sidebar = chevron-left dividers, order reversed).

### Convex provider SSR fix

The `ConvexQueryClient` and `QueryClient` were being constructed at module scope in `convex.tsx`. This works in SPA mode but causes issues under Next.js SSR/HMR because the module-scope instances are shared across requests. Moving construction to `useState` (with initializer functions) ensures each React tree gets its own instances, and `useEffect` is used to call `connect()` client-side only.
