## Root Cause — Why errors appear in library source during `www` typecheck

When `www` runs `pnpm typecheck`, it compiles its own source AND all library
packages it depends on via their `"source"` export condition (resolved through
`customConditions: ["source"]` in `base.json`). This means `core`, `react`, and
`next` source files are included in the same TypeScript program as `www`'s code.

The www app includes `src/vex.types.ts`, which contains:
```ts
declare module "@vexcms/core" {
  interface GeneratedVexTypes {
    CollectionSlug: "pages" | "headers" | ... | "images"  // ← was string
    MediaCollectionSlug: "images"                          // ← was string
    StorageAdapterSlug: "convex"                           // ← was never
  }
}
```

This augmentation narrows three conditional types across `@vexcms/core` from
their pre-generation defaults (`string`, `string`, `never`) to specific literals.
Library code written to work with the wide `string` default now gets the narrow
generated literals, exposing three classes of type mismatch.

---

## The Three Patterns

### Pattern 1 — Runtime `string` passed to a generated-literal parameter

**Where:** `packages/next/src/NextAdminPage.tsx` lines 91 and 97

```ts
const [collectionSlug, documentId] = path; // string | undefined from URL params

await fetchQuery(vexConvexApi.find, {
  collection: collectionSlug,  // ❌ string, but vexConvexApi.find now expects CollectionSlug
});
```

After generation, `vexConvexApi.find`'s `collection` argument accepts `CollectionSlug`
(the specific literal union), not `string`. URL params are always `string` — they
need an assertion to cross this boundary.

**Fix:** Assert at the call site:
```ts
collection: collectionSlug as CollectionSlug
```
Both occurrences (lines 91 and 97).

**File:** `packages/next/src/NextAdminPage.tsx`

---

### Pattern 2 — `Set<GeneratedLiteral>.has(string)` — TypeScript 4.9+ strictness

**Where:** `packages/core/src/media/config.ts` line 107

```ts
const mediaSlugs = new Set(mediaCollections.map((c) => c.slug));
// mediaSlugs: Set<"images"> — because MediaCollectionSlug = "images"

if (!mediaSlugs.has(uploadField.to)) {  // ❌ uploadField.to is string
```

TypeScript 4.9+ made `Set.has()` strict — it only accepts `T` where the Set is
`Set<T>`. The set element type resolves to `"images"` (the generated literal) but
`uploadField.to` is typed as `MediaCollectionSlug` which in the context of this
internal validation code evaluates to `string` (the pre-generation default used
within core itself).

The validation code is internal infrastructure — it should use `string` throughout,
not rely on the generated narrow types.

**Fix:** Widen the Set to `Set<string>` at creation:
```ts
const mediaSlugs = new Set<string>(mediaCollections.map((c) => c.slug));
```

**File:** `packages/core/src/media/config.ts`

---

### Pattern 3 — `ClientUploadMap` key too narrow for a runtime registry

**Where:** Three react component files + the context default

`ClientUploadMap = Record<StorageAdapterSlug, fn>` where `StorageAdapterSlug = "convex"`.
After generation this becomes `Record<"convex", fn>` — a required object with a specific
key. This causes:

**a) Context default value fails (`StorageAdapterContext.tsx:12`)**
```ts
const StorageAdapterContext = createContext<StorageAdapterContextValue>({
  adapters: {},  // ❌ {} is missing required key "convex"
});
```

**b) `string` not assignable to `"convex"` (Input.tsx:68, MediaPicker.tsx:51, CreateMediaModal.tsx:53)**
```ts
const adapterName = config.mediaCollections.find(...)?.meta?.storageAdapter ?? "convex";
// adapterName: string

adapters[adapterName]  // ❌ string can't index Record<"convex", fn>
```

`ClientUploadMap` is a runtime function registry, not a compile-time adapter
inventory. It should accept any adapter name at runtime — `StorageAdapterSlug`
as the key type is too strict for this purpose.

**Fix:** Change `ClientUploadMap` in `packages/core/src/config/types.ts` to use `string`:
```ts
export type ClientUploadMap = Record<
  string,   // was StorageAdapterSlug
  (file: any, uploadUrl: string) => Promise<{ storageId: string; [key: string]: unknown }>
>;
```

The generated `StorageAdapterSlug` type still validates which adapters are
configured in the `vex.config.ts` storage setup — it just shouldn't constrain
the runtime upload function map.

**File:** `packages/core/src/config/types.ts`

## Remaining Build Blocker

### `sanitizeConfigForConvex` missing from `@vexcms/core`

`apps/www/src/vex.config.server.ts` imports `sanitizeConfigForConvex` from
`@vexcms/core` — this function was never implemented.

**Options:**

Option 1 — Implement it (if `vex.config.server.ts` is still needed):
```ts
// packages/core/src/config/sanitizeConfig.ts
export function sanitizeConfigForConvex(config: VexConfig): VexConfig {
  const { storage, ...rest } = config;
  return {
    ...rest,
    storage: storage ? { ...storage, adapters: [] } : undefined,
  } as VexConfig;
}
```
Export from `packages/core/src/config/index.ts`.

Option 2 — Delete `vex.config.server.ts` (if Convex files import `config` directly
from `~/vex.config` already, which they do in `convex/vex/media.ts`).
