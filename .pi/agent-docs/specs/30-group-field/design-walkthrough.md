# Spec 30 — Group Field — Design Walkthrough

---

## End-to-End Consumer Code

### 1. Define a collection with a group field

```ts
// apps/www/src/vexcms/collections/pages.ts
import { defineCollection, group, text, url, number } from "@vexcms/core"

export const pages = defineCollection({
  slug: "pages",
  admin: { useAsTitle: "title" },
  fields: {
    title: text({ required: true }),
    slug:  text({ required: true }),

    // SEO group — optional at the document level,
    // sub-fields respect their own required settings.
    // defaultOpen: false means the accordion starts collapsed.
    seo: group({
      label: "SEO",
      defaultOpen: false,
      fields: {
        metaTitle:       text({ label: "Meta Title" }),
        metaDescription: text({ label: "Meta Description" }),
        ogImage:         url({ label: "OG Image" }),
      },
    }),

    // Nested group — group within a group
    pricing: group({
      label: "Pricing",
      fields: {
        currency: text({ required: true, defaultValue: "USD" }),
        amount:   number({ required: true }),
        tier:     group({
          label: "Tier",
          fields: {
            name:  text({ required: true }),
            level: number(),
          },
        }),
      },
    }),
  },
})
```

### 2. Generated Convex schema

```ts
// convex/vex.schema.ts (auto-generated by vex dev)
export const pages = defineTable({
  title: v.string(),
  slug:  v.string(),

  // Optional group — outer v.optional(); inner sub-fields respect their own required
  seo: v.optional(v.object({
    metaTitle:       v.optional(v.string()),
    metaDescription: v.optional(v.string()),
    ogImage:         v.optional(v.string()),
  })),

  // Nested group — outer required determines outer wrapper; inner group is optional
  pricing: v.optional(v.object({
    currency: v.string(),              // required: true → no optional wrapper
    amount:   v.number(),              // required: true
    tier: v.optional(v.object({        // group default required: false
      name:  v.string(),               // required: true
      level: v.optional(v.number()),   // required: false
    })),
  })),
})
```

### 5. TanStack Form path resolution

`GroupFieldInput` registers the outer group field at `name="seo"`. Inside `FormGroup`, each sub-field is rendered with its full dot-notation path:

```
form.values.seo.metaTitle       ← "seo.metaTitle"
form.values.seo.metaDescription ← "seo.metaDescription"
form.values.seo.ogImage         ← "seo.ogImage"
```

TanStack Form v1 resolves these natively. No array mode, no custom form wiring — just standard `<form.Field name="seo.metaTitle">`.

For `pricing.tier.name` (3 levels deep):

```
form.values.pricing.tier.name ← "pricing.tier.name"
```

`FormGroup` recurses naturally: the `tier` sub-field is also a group, so `fieldToInputComponent("group")` returns `GroupFieldInput`, which renders another `FormGroup` with `name="pricing.tier"`.

## Type Narrowing Examples

### Correct — accessing typed sub-fields

```ts
import type { GroupField } from "@vexcms/core"
import { group, text } from "@vexcms/core"

const seoField = group({ fields: { title: text({ required: true }) } })
//    ^? GroupField<{}>

// ✅ Convex validator returns a string
import { groupFieldToValidator } from "@vexcms/core"
const validator = groupFieldToValidator({ field: seoField })
//    ^? string → "v.optional(v.object({ title: v.string() }))"
```

### Type error — missing required `fields` property

```ts
// ❌ TypeScript error: 'fields' is required in 'GroupFieldInput'

```

import { adminFieldToValidator } from "@vexcms/core"

// ❌ GroupField expected — adminFieldToValidator dispatches on field.type

## Decisions Reference

**D1 — Named `group` not `object`**

`object` clashes with the JavaScript `Object` global in certain import contexts (e.g., `import { object } from "@vexcms/core"` shadows the global in a module scope). Payload CMS uses `group` for exactly this field shape and the name carries the right semantic: a labelled grouping of fields within a form, not a raw data container. Convex stores it as `v.object({...})` regardless of the config function name.

**D2 — Sub-fields respect their own `required` individually**

Unlike `array()` where Convex forbids `v.optional()` inside `v.array()`, Convex's `v.object()` fully supports optional keys: `v.object({ a: v.string(), b: v.optional(v.string()) })` is valid. There is no need to force `required: true` on group sub-fields. Each sub-field generates its own validator via `adminFieldToValidator` as normal.

**D3 — `interfaceType` computed dynamically in `group()`**

The `ADMIN_FIELDS.group.interfaceType` constant is a placeholder `"object"`. At instantiation time, `group()` calls `buildInterfaceType(options.fields)` to compute a real TypeScript object-type string like `"{ title: string; description?: string }"`. This string is stored on `GroupField.interfaceType` and used directly by `collectionConfigToInterface` when generating `vex.types.ts`. Nested groups produce nested type strings, fully accurately reflecting the shape of the stored data.

**D4 — TanStack Form dot-notation paths, no special mode**

TanStack Form v1 resolves nested object paths via dot-notation natively (`"seo.title"` maps to `formValues.seo.title`). The `array` field required `mode="array"` to unlock `pushValue`/`removeValue` mutations. Group fields are static — the structure is fixed at config time, no dynamic add/remove is needed. Using dot-notation means `FormGroup` is straightforward: iterate `fieldDef.fields`, render each with `name="${groupName}.${fieldKey}"`, let TanStack Form handle the rest.

**D5 — `FormGroup` uses the existing `<Accordion>` component (Base UI)**

The `<Accordion>` primitive already exists in `packages/react/src/components/ui/accordion.tsx` (built on Base UI). Using it instead of a hand-rolled toggle gives consistent animation, keyboard navigation (Space/Enter to expand, arrow keys between items), and ARIA attributes (`aria-expanded`, `aria-controls`) for free. The `defaultValue` prop on `<Accordion>` controls which items start open, driven by `fieldDef.defaultOpen`. A single `<AccordionItem>` holds all sub-fields; the trigger displays the group label and a sub-field count badge.

**D6 — Column cell shows `{ N keys }`, not raw JSON**

The list-table cell for a group field shows `{ 3 keys }` (or `—` for null). Inline JSON dumps in a table cell are unreadable at column widths. If a consumer needs to display specific sub-fields in the list view, they can use the relationship pattern: register a custom `admin.components.cell` override. A compact badge is the sensible default for a type that can contain arbitrarily nested data.

**D7 — `defaultValue` is `{}`**

The group field's outer `defaultValue` is `{}`. Each sub-field's own Zod schema provides its own default via `applyBaseInputSchemaMeta`. When the form initialises, Zod's `.default({})` on the outer object means an undefined group value becomes `{}`, and then each sub-field's `.default()` fills in sub-field defaults. This mirrors how existing optional fields work and avoids any `undefined` deep-access error in TanStack Form's initialisation pass.

**D8 — No HKT binding; plain re-export from `@vexcms/react`**

`group()` has no user-supplied component slots (`admin.components.header` etc. are out of scope). There is nothing to bind to `ReactHKT`. It gets the same plain `export { group } from "@vexcms/core"` pass-through in `@vexcms/react/src/index.ts` as `text`, `number`, `checkbox`, etc. If a component slot is added in the future, the migration path is exactly the same as was done for `relationship()` (Spec 22 Decision 15).

**D9 — `group()` has no `min`/`max`**

Min/max item counts are an `array()` concept — they constrain the length of a list. A group has a fixed set of sub-fields defined at config time; there's no meaningful "minimum" or "maximum" for a static object shape. If field-level required/optional constraints are needed beyond the sub-field's own `required` flag, add them in a follow-up spec.

**D10 — Nested groups recurse via `fieldToInputComponent`; `index` disambiguates arrays**

**D11 — `defaultOpen` is a top-level field property, not in `admin`**

`defaultOpen` is specific to `group()` and has no meaning on any other field type. Adding it to the shared `FieldAdminConfig` would pollute the base admin config for every field. Keeping it at the top level of `GroupFieldInput` (alongside `fields`, `required`, `defaultValue`) follows the same pattern as `array()`'s `min`/`max` — field-specific options live at the top level, not buried in `admin`.

`FormGroup` renders each sub-field by looking up `fieldToInputComponent(subFieldDef.type)`. When a sub-field is itself a `group`, that lookup returns `GroupFieldInput`, which renders another `FormGroup` with a deeper `name` path (`"pricing.tier"`). No special handling for nested groups is needed — the registry lookup is the recursion mechanism.

When a group is rendered inside an `array()` (e.g. `array({ items: group({...}) })`), multiple `FormGroup` instances exist simultaneously — one per array item. Each needs its own accordion item value so they can be independently open/closed. The `index` prop appended to the item value (`"${name}-${index}"`) solves this without any global state or context.
