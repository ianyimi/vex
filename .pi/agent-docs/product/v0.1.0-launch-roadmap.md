# VexCMS — v0.1.0 Launch Roadmap

> **Context:** The `rebuild` branch is the target. It has a cleaner architecture than `master` (which was feature-complete) and is the version that ships. Everything below is "what remains to implement" before the rebuild becomes the product at v0.1.0.
>
> `master` is historical — it had all features but older patterns. Do NOT port it directly; re-implement against the rebuild's architecture (HKT adapters, framework-agnostic core, colocated types, etc.).

---

**Packages exist and build:**
- `@vexcms/core` — field system (text, number, checkbox, select, date, url, relationship), schema gen, type gen, defineCollection, defineConfig

## M1 — Field System Complete

> Goal: All field types that ship at v0.1.0 have core definitions + React admin components.

### Core field types to add (in `@vexcms/core` + `@vexcms/react`)

| Field | Priority | Notes |
|-------|----------|-------|
| `image` / `imageUrl` | Must | URL string field for image URLs — simpler than upload, needed before media |
| `upload` | Must | File reference field — stores storage ID, links to media collection |
| `json` | Must | Arbitrary JSON, `v.any()` in schema, textarea/code editor in admin |
| `ui` | Must | Non-persisted display/action field — renders arbitrary component, stores nothing |
| `array` | Must | Repeatable list of sub-fields — any field type as items |
| `object` / `group` | Must | Named sub-field group — flat object in schema, collapsible UI section |
| `blocks` | Must | Ordered array of typed block instances — discriminated union in schema |
| `richtext` | Must | Plate.js editor — JSON stored in Convex (`v.any()`), rich admin component |
| `color` | Should | String field (hex/CSS var) with popover color picker in admin |
| `tabs` | Should | UI-only grouping — organizes fields into tabs in admin, no schema impact |
| `textarea` | Should | Multi-line text — same schema as text, `rows` config option, different admin component |

### Follow-on: relationship field completion
The relationship field exists in core/react but may need picker UI (popover with search/select from existing documents).

**Deliverables:**
- Each field: `core/src/fields/<name>/config.ts`, `types.ts`, `validators/`, `inputSchemas/` following `adding-a-field-type.md` standard
- Each field: `react/src/components/fields/<name>/` with `InputComponent` and `CellComponent`
- All exported from package `index.ts` files
- Tests for each field's schema gen and Zod validation

## M2 — Authentication + Media

### Better Auth Package (`@vexcms/better-auth`)

The package is currently a stub. Needs:
- `vexBetterAuth(config)` — extracts user/session/account tables from Better Auth config and injects them into the Vex schema
- Schema extraction: generate Convex table definitions from Better Auth's table structure
- First-user auto-admin: atomic mutation that grants admin role to the first sign-up
- Admin panel auth integration: session reading, redirect-on-unauthenticated in NextAdminLayout
- Better Auth session in Convex query context (via `@convex-dev/better-auth` or custom Convex HTTP action)
- Export: `vexBetterAuth`, `useCurrentUser`, auth route helpers for Next.js

### Convex File Storage Adapter (`@vexcms/file-storage-convex`)

Needs the runtime wiring that the stub lacks:
- Convex HTTP actions for `generateUploadUrl`, `getUrl`, `deleteFile`
- Instructions/helpers for wiring these actions into user's Convex deployment
- The adapter interface in `@vexcms/core` (currently in `file-storage-convex` — may need moving)
- Integration with the `upload` field type and media collections

### Media Collections + Media Library UI

- `defineMediaCollection()` — auto-injects filename, mimeType, size, width, height, storageId fields
- Media library grid view in admin (list view variant for media)
- Upload dropzone in media library
- Media picker popover — opens from `upload` field components, allows selecting or uploading
- Per-field MIME type and size restrictions in upload field config
- Drag-and-drop upload support

**Deliverables:**
- `@vexcms/better-auth` fully implemented and documented
- `@vexcms/file-storage-convex` with runtime Convex actions (or instructions to generate them)
- `defineMediaCollection` in `@vexcms/core`
- Media library + picker in `@vexcms/react`

## M3 — Content Workflow (Drafts, Versioning, RBAC, Live Preview)

### Draft/Publish Workflow

- `_status` (draft/published), `_draftSnapshot`, `_version`, `_hasDraft`, `_publishedAt` fields on versioned collections
- `vex_versions` table (history per document)
- Generated mutations: `adminSaveDraft`, `adminPublish`, `adminUnpublish`, `adminRestoreVersion`
- Autosave with debounce + version coalescing (don't create a new version record on every keystroke)
- Version history panel in admin edit view — list of past versions, restore button
- Save Draft / Publish / Unpublish / Reset buttons in edit form toolbar
- `versions: { drafts: true, autosave: true }` config on defineCollection
- `_vexDrafts` arg support in generated queries (for live preview)

### RBAC / Access Permissions

- `defineAccess()` builder — type-safe permission matrix per role per collection
- Document-level permissions: create, read, update, delete per collection per role
- Field-level permissions: allowlist/denylist per action (read/update)
- `hasPermission()` runtime resolver
- Permission enforcement in all admin mutations and queries
- `defineAccess` config on `defineConfig`

### Live Preview

- `livePreview.url` config on defineCollection (function or string template)
- `LivePreviewPanel` component in `@vexcms/react` — side-by-side iframe
- postMessage protocol: init, refresh, ready
- `useVexPreview` hook in a separate or shared package (imported by user's frontend)
- Responsive breakpoint tabs in preview panel
- Open-in-new-tab button
- Draft snapshot sync: preview fetches draft content via `_vexDrafts: "snapshot"` arg

**Deliverables:**
- Versioned collections: full draft/publish lifecycle
- RBAC: defineAccess + enforcement in all admin routes
- Live preview: panel + postMessage protocol + useVexPreview hook

## M4 — Advanced Fields (Array, Object, Blocks, Richtext)

These are grouped separately because they are the most complex fields and depend on M1's base field infrastructure being solid.

### Array Field

- `array({ field })` — repeatable list of any field type (including object, select, text, etc.)
- Schema: `v.array(...)` of the item field's validator
- Admin UI: add/remove/reorder items (drag-and-drop), each item renders the sub-field component
- Works with all other field types as items (including object for array-of-objects)
- `minRows` / `maxRows` config

### Object / Group Field

- `object({ fields })` — named group of sub-fields stored as a flat object in Convex
- Schema: `v.object({ ... })` composed from sub-field validators
- Admin UI: collapsible section, renders each sub-field in a labeled grid
- Used as the item type inside `array()` for "array of objects" pattern

### Blocks Field

- `defineBlock({ slug, label, fields })` — defines a reusable block type (data-only, no React dep in core)
- `blocks({ blocks: [...] })` field — ordered array of typed block instances
- Schema: discriminated union `v.union(...)` based on block slug
- Admin UI: block picker (modal or popover), add/reorder/delete blocks, inline edit per block
- `RenderBlocks` component in `@vexcms/react` — takes component map + block data, renders each block
- Type inference: discriminated union of all allowed block shapes for full TypeScript safety

### Richtext Field (`@vexcms/richtext-plate`)

The package exists with stubs. Needs full implementation:
- `richtext({ label, mediaCollection? })` field type in `@vexcms/core`
- Plate.js editor in `@vexcms/richtext-plate/editor`:
  - Bold, italic, underline, strikethrough
  - Headings (H1–H4)
  - Bulleted and numbered lists
  - Blockquotes
  - Code blocks (with syntax highlighting)
  - Links (with URL popover)
  - Images (inline media upload, uses mediaCollection)
  - Horizontal rule
- `PlateStatic` renderer in `@vexcms/richtext-plate/render` — for server-side and frontend rendering
- JSON storage in Convex (`v.any()` — Plate node array)
- `admin.components.Field` wired so `richtext` field uses the Plate editor

**Deliverables:**
- All four field types: array, object, blocks, richtext — core schema + admin UI
- defineBlock exported from `@vexcms/core`
- RenderBlocks in `@vexcms/react`
- `@vexcms/richtext-plate` fully implemented (editor + renderer)

## M5 — DX & Infrastructure

### CLI Completion (`@vexcms/cli`)

The CLI needs to be complete and reliable before launch:
- `vex dev` — watch mode: schema generation + type generation + query generation + `convex dev`
- `vex dev --once` — single-shot generation
- `vex migrate` — run pending migrations
- `.env.local` loading before config import
- Clear error messages when config is invalid
- Hot-reload config file watching

### `create-vexcms` Template

The scaffolding CLI needs a production-ready template:
- `pnpm create vexcms@latest` — interactive setup (project name, auth, template)
- Base template: Next.js + Convex + Better Auth + VexCMS admin panel (pre-wired)
- Marketing site template: includes example collections (pages, posts, media), blocks, richtext
- Bare template: minimal config for advanced users
- Auto-generates: `vex.config.ts`, `convex/` functions, auth routes, admin layout

### Changeset Pipeline + CI/CD

Publishing infrastructure needs to be solid before launch:
- `changeset` workflow: `pnpm changeset` → PR bot → `pnpm release`
- GitHub Actions:
  - `ci.yml` — lint + typecheck + test on every PR
  - `release.yml` — publish to npm on merge to main (triggered by changeset PR)
- All packages: `prepublishOnly` builds
- Package `exports` fields locked down (no accidental deep imports)
- README in each package describing its purpose and usage

### Branch Merge Strategy

The rebuild branch needs to become the primary:
1. `rebuild` → `dev` (merge or rebase, resolving any conflicts)
2. `dev` → `main` (after smoke testing)
3. Tag: `v0.1.0`
4. Deprecate old npm package versions (if any were published from master)
5. Close out the rebuild branch

**Deliverables:**
- CLI fully working end-to-end
- `create-vexcms` template tested against a fresh Convex project
- CI/CD pipeline green
- Changesets configured for all packages
- Merge strategy documented

## Notes

**On the Tabs field:** It's UI-only (no schema impact — just groups fields into tabs in the admin form). It's not hard to implement and makes the admin UI much cleaner for collections with many fields. Include it in M1 as a "should."

**On TypeDoc vs hand-written docs:** Both. TypeDoc generates the API reference automatically from JSDoc. The guides, concepts, and field pages are hand-written. Don't try to generate the guides — they need real explanations and examples.

**On the marketing site dogfooding principle:** The marketing site MUST be managed through VexCMS. Hardcoded content defeats the purpose. If something in the site requires a feature that doesn't exist yet, that's a signal to build the feature, not to hardcode the content.

**On brand before docs:** Define the brand (M7) before writing the docs site styling (M6). The docs site needs the color palette and fonts to look right at launch.

**On naming — "object" vs "group":** Either works. "Group" is what Payload calls it. "Object" is more technically accurate (it maps to `v.object()`). The README currently shows `object()`. Keep it as `object()`.
