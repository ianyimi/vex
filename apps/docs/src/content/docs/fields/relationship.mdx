---
title: relationship field
description: Stores Convex Id references pointing to documents in another registered collection, with a searchable picker in the admin panel.
---

A `relationship()` field stores one or more Convex `Id` references pointing to
documents in another registered collection. The generated Convex schema always
emits `v.array(v.id("slug"))` — `hasMany` is a UI-only hint that controls
whether the admin picker allows a single selection or multiple. VexCMS
auto-generates a `.index("by_<fieldKey>", ["<fieldKey>"])` for every relationship
field, and adds a `.searchIndex("search_<useAsTitle>", …)` on the target
collection whenever one of its fields is referenced — so the picker's search
works out of the box with no extra config.

After running `vex generate`, passing an unregistered collection slug is a
compile-time error.

## Config options

| Option | Type | Default | Description |
|--------|------|---------|-------------|
| `collection.slug` | `CollectionSlug` | *(required)* | Slug of the target collection. Must be a registered collection in `defineConfig`. |
| `hasMany` | `boolean` | `false` | UI hint — `false` shows a single-selection picker, `true` shows a multi-selection picker. Does not change the Convex schema type. |
| `required` | `boolean` | `false` | When `false`, the field is wrapped in `v.optional(…)` in the schema and the form allows leaving it empty. |
| `label` | `string` | `""` | Display label in the admin panel. Inferred from the field key by `defineCollection` when left empty. |
| `admin.hidden` | `boolean` | `false` | Hides the field from the admin edit form entirely. |
| `admin.readOnly` | `boolean` | `false` | Renders the picker as non-interactive — value is visible but cannot be changed. |
| `admin.position` | `"main" \| "sidebar"` | `"main"` | Column in the admin edit layout where this field appears. |
| `admin.width` | `string` | `"100%"` | CSS width of the field in the edit form (e.g. `"50%"`, `"240px"`). Meaningful as a child of `row()`; below a narrow form column every field renders full width regardless. |
| `admin.cellAlignment` | `"left" \| "center" \| "right"` | `"left"` | Horizontal alignment of the value in the list-view table cell. |
| `admin.components.preview` | Component | — | Per-field override for the relationship preview renderer — the only supported location for a custom preview. |
| `admin.condition` | `(props: { data, siblingData }) => boolean` | — | Shows the field only while this returns `true`. A throwing condition counts as met. Hidden fields skip `required`/`validate` on the server too. See the [Conditional fields & masks guide](/guides/conditional-fields-and-masks/). |

## Schema output

```ts
// Single reference (hasMany: false, required: true)
author: v.array(v.id("authors"))

// Single reference (hasMany: false, required: false — default)
author: v.optional(v.array(v.id("authors")))

// Multi-reference (hasMany: true, required: false)
tags: v.optional(v.array(v.id("tags")))
```

Auto-generated indexes:

```ts
// For every relationship field — added automatically, no config needed
.index("by_author", ["author"])

// On the *target* collection — added when another collection links to it
// and useAsTitle is not a system field
.searchIndex("search_title", { searchField: "title", filterFields: [] })
```

## Usage

```ts
import { defineCollection, relationship, text } from "@vexcms/core";

// Single reference — stores the author's Id
const posts = defineCollection({
  slug: "posts",
  fields: {
    title: text({ required: true }),
    author: relationship({ collection: { slug: "authors" } }),
  },
});

// Multi-reference — stores an array of tag Ids
const articles = defineCollection({
  slug: "articles",
  fields: {
    title: text({ required: true }),
    tags: relationship({
      collection: { slug: "tags" },
      hasMany: true,
      required: false,
    }),
  },
});
```

## Custom preview component

By default the picker and list table show the target document's `useAsTitle`
field. Override the renderer via `admin.components.preview` on the
`relationship()` field itself — this is the only supported override location.
A target collection cannot set its own default preview: `CollectionConfig`'s `admin` shape has
no `components.preview` slot at all — only the `relationship()` field's own `admin` carries
one, so a per-field override is the only supported override location.

```ts
// Field-level override — only applies to the `author` field on `posts`
const posts = defineCollection({
  slug: "posts",
  fields: {
    author: relationship({
      collection: { slug: "authors" },
      admin: {
        components: { preview: CompactAuthorPreview },
      },
    }),
  },
});
```

## Admin UI

The relationship field renders as a searchable combobox picker in the edit form,
with a button labeled "Select `<label>`" (the field's own label) that opens a
picker dialog on its Select tab. Typing into the picker searches the target
collection's `useAsTitle` field via the auto-generated search index. The
picker finds existing relationships by field, so re-opening the picker on an
already-filled field shows the current selection. When `hasMany: false`,
selecting a result replaces the current value; when `hasMany: true`, results
are added to the selection list and can be removed individually. In the
list-view table, each referenced document row shows the target collection's
`admin.icon` beside its preview component (or title field as a fallback).

## Populate

A relationship field is stored as raw `Id`s — pass `populate: { <fieldKey>: true }` to
`find`/`get`/`search`/`globals.get` to resolve it into the target document(s) instead
(`depth` does the same automatically, to N levels, for every relationship/upload field on
the collection). The target belongs to its OWN collection, so populate applies that
collection's own `read` rule and field-permission map to every resolved target — the same
decision a direct `get({ collection: <target> })` would make, independent of whatever rule
let the caller read the document the relationship field lives on:

```ts
const post = await get({
  ctx, config, id: postId, collection: "posts",
  populate: { author: true },
});
post?.author; // Author[] — full target docs, when the caller may read "authors"
```

A caller who may not read the target collection at all gets a `HiddenDocument` placeholder
in its place instead of the document — `{ _id, code: "ACCESS_DENIED", resource, action:
"read" }` — and a caller who may read the target but not every field on it gets the target
with its denied fields stripped. The admin panel renders a denied target as a locked row
(`AccessDeniedItemRow` in the list-view table cell, a compact lock badge in the peek
panel's Fields tab) rather than attempting its preview component. See [Access control →
Populated relationships](/guides/access-control/#populated-relationships-honor-the-targets-own-read-rule)
for the full behavior, including how `access: { bypass: true }` propagates.

## Querying by a relationship

Every `relationship` field is stored as `v.array(v.id("slug"))`, whether `hasMany` is `true`
or `false` — a single relationship is a one-element array, not a bare `Id`. Keep that in mind
anywhere you compare against it: in a `find`/`get` call's `where`, in an access rule's
`withIndex`/`where`, or in a plain JS predicate.

**A single relationship (`hasMany: false`) matches an exact value with an array literal,**
and is index-pushable through the field's auto-generated `by_<fieldKey>` index:

```ts
find({
  ctx,
  collection: "posts",
  withIndex: { name: "by_author", range: (q) => q.eq("author", [authorId]) },
});
```

The same shape works unwrapped inside a `where` callback — `find`'s `where` builder (and an
access rule's `where`) normalizes a bare value against a list field for you, so
`q.eq("author", authorId)` also matches. `withIndex`'s raw range callback bypasses that
normalization, so wrap the value yourself there, as above.

**`hasMany` membership — "does this array contain this id" — can't use an index.** An index
range matches a field's whole stored value, not "one of the elements in it," so checking
whether a `hasMany` relationship *contains* a given id needs a `filter`/`where` predicate
instead of `withIndex`:

```ts
find({
  ctx,
  collection: "posts",
  where: (q) => q.eq("tags", tagId), // single-select equivalent only — see above
});

// "contains" membership on a hasMany field — not index-pushable
find({
  ctx,
  collection: "posts",
}).then((rows) => rows.filter((row) => row.tags.includes(tagId)));
```

See the [Access control guide](/guides/access-control/) for the same rule written as an
access check (`indexedOwnerCheck`/`ownerPredicateCheck` get the wrapping right for you
there).
