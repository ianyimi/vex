---
title: Live Preview
description: Stream a document's unsaved editor values into its own public page — a resizable split pane in the admin panel, an overlay hook on the site, and the middleware gate that keeps it private.
---

Live preview renders **the document's real public route** beside the edit form and
updates it as you type — no separate preview route, no draft save, no autosave. The
page being previewed is the same page a visitor gets; only the data is overlaid.

## How it works

1. The edit view resolves the document's preview URL from `admin.livePreview.url` and
   iframes it in a resizable split pane.
2. On every form change (debounced), it posts the form's **complete current values**
   over two transports at once: `postMessage` to the surface it holds a window
   reference for, and a shared `BroadcastChannel`.
3. On the public page, `LivePreviewProvider` keeps an `id → unsaved values` map, and
   `useLivePreview` overlays the entry matching the document your own query already
   fetched.
4. Once listening, the provider posts a ready message; every open edit view replies with
   its current values immediately, so a duplicated tab, or a page you just navigated or
   reloaded to inside the preview, catches up without waiting for the next keystroke.

On a narrow admin viewport — below the 768px mobile breakpoint, distinct from the
simulated-width `breakpoints` toggle described below, which only applies to the
desktop split — the split panel doesn't fit beside the form. Narrowing the browser
past that breakpoint while the panel is open **auto-closes** it instead of rendering
as a full-screen takeover, and remembers the close was automatic; widening back past
the breakpoint reopens it, unless you explicitly opened or closed it while narrow
(which clears that memory and the panel stays however you left it). Opening the panel
below the breakpoint — the header button or the ⋯ menu's "Preview" item — instead
shows it as a bottom sheet that slides up and covers the screen except a thin strip of
the page at the top; Esc, a tap outside, or its own close button all dismiss it. None
of these width-driven transitions touch the saved panel-open preference —
only an explicit toggle does, so a refresh at desktop width always respects your last
deliberate choice.

Both panel preferences — open/closed and the handle position — persist in a
consolidated, `basePath`-scoped admin cookie (`vex-admin`/`vex-admin:<collection>`)
rather than localStorage, scoped per collection or global. The admin page reads them
on the server, so a refresh paints the split at the width you left it at instead of
snapping to it after hydration. See [Admin cookies](/guides/admin-cookies) for the
full cookie layout.

Lifecycle hooks never run on preview data — you see exactly what you typed, before
`beforeChange` would transform it.

## Configure the collection

```ts
import { defineCollection, text } from "@vexcms/core"
import { resolvePagePath } from "~/lib/resolvePagePath"

export const pages = defineCollection({
  slug: "pages",
  admin: {
    useAsTitle: "title",
    livePreview: {
      // A resolver when the URL depends on the document; `doc` is
      // Partial<PagesDocument>, so doc.slug is typed, not unknown.
      url: (doc) => resolvePagePath(doc.slug),
      // Optional:
      debounceMs: 150,   // sync cadence for this collection
      defaultOpen: false, // panel state before the editor ever chooses
      // breakpoints: [...] // overrides the root list, rarely needed
    },
  },
  fields: { title: text({ required: true }), slug: text({ required: true }) },
})
```

`url` also takes a literal path for a collection or global that always previews in one
place — a site header or footer rendered on every page is `url: "/"`, not
`url: () => "/"`.

`admin.livePreview.url` is independent of `routes.map`. `routes.map` answers "every
public path this document renders at" (it drives revalidation and sitemaps);
`livePreview.url` answers "the one URL to iframe", and may point at a different origin
such as staging. Share a helper between them if they agree, as above.

Globals take the identical `admin.livePreview` block.

## Configure the project

```ts
export default defineConfig({
  collections: [pages],
  admin: {
    livePreview: {
      // Origins allowed to post preview frames to a listener. Empty by default,
      // which means the postMessage transport accepts nothing.
      allowedOrigins: ["http://localhost:3000", "https://admin.example.com"],
      // Optional — defaults to 375 / 390 / sm / md / lg / xl / 2xl.
      // breakpoints: [{ label: "sm", width: 640, icon: "Smartphone" }],
      // Optional — defaults to "allow". See "Signing out while preview is open" below.
      // expiredSessions: "deny",
    },
  },
})
```

## Wire the public site

`LivePreviewProvider` reads everything it needs — collections, globals, and
`allowedOrigins` — from `VexConfigContext`, so it takes no props. Mount
`VexConfigProvider` once at the app root, from a **client** component that imports your
config directly: the config carries functions (`admin.livePreview.url`, field
validators), so it cannot cross the server/client boundary as a prop.

```tsx
// components/providers/client.tsx
"use client"

import { VexConfigProvider } from "@vexcms/react"
import config from "~/vex.config"

export default function ClientProviders({ children }: { children: React.ReactNode }) {
  return <VexConfigProvider config={config}>{children}</VexConfigProvider>
}
```

The root mount covers the admin panel and the public site from one provenance. Then wrap
the tree once, in `app/layout.tsx`:

```tsx
<ClientProviders>
  <LivePreviewProvider>{children}</LivePreviewProvider>
</ClientProviders>
```

The provider gates itself (see below), so a normal visitor pays for a disabled provider
and nothing else — and the route stays statically prerenderable, because nothing here
reads `headers()` or `cookies()` on the server.

Projects scaffolded with `create-vexcms` (either template) already ship the provider
mount, the Draft Mode route and the proxy hand-off described below. They stay inert until a
collection or global sets `admin.livePreview.url`.

To switch a page's own query to a draft-reading variant while it is being previewed, read
`useIsLivePreviewActive()`. It returns `false` during the server render and hydration,
then the gate's real answer:

```tsx
const isPreviewing = useIsLivePreviewActive()
const { data: page } = useLivePreviewQuery(
  { ...convexQuery(isPreviewing ? api.pages.getBySlugPreview : api.pages.getBySlug, { slug }), initialData },
  "pages",
)
```

Then overlay your own query result:

```tsx
"use client"

import { convexQuery } from "@convex-dev/react-query"
import { RenderBlocks, useLivePreviewQuery } from "@vexcms/react"

export function PageContent({ slug, initialData }) {
  const { data: page } = useLivePreviewQuery(
    { ...convexQuery(api.pages.getBySlug, { slug }), initialData },
    "pages",
  )
  if (!page) return null
  return <RenderBlocks blocks={page.blocks} components={blockComponents} />
}
```

`useLivePreviewQuery` is sugar for the common `getBySlug`-returns-an-array shape: it
narrows to the first document for you. A query that already resolves to a SINGLE
document — a `getFirst`-style singleton read, or a lookup by id — uses
`useLivePreviewDocumentQuery` with the identical signature.

Every editable document a page renders needs one of these, not just the page's own: the
overlay only reaches documents a consumer hands it, so a site header fetched with a bare
`useQuery` stays frozen at its saved values while the header is being edited.

```tsx
const { data: header } = useLivePreviewDocumentQuery(
  { ...convexQuery(api.headers.getFirst, {}), initialData },
  "headers",
)
```

## Navigating inside the preview

Preview stays on for every page you open inside the panel or the pop-out tab. That holds
for links, back/forward and reloads, including pages whose URL no longer carries
`?vexLivePreview=1`. What updates where depends on how each page reads its data:

| Data | Updates in the preview | What it takes |
|---|---|---|
| A document read through `useLivePreview`, `useLivePreviewQuery` or `useLivePreviewDocumentQuery` (headers, footers, globals in a layout, the page's own document) | On every keystroke | Already wired |
| Lists and related documents on other pages, for a collection with `versions: { drafts: true, autosave: … }` | About a second after typing, once autosave writes the draft | List queries take a `preview` arg and call `find({ …, drafts: true })` when it is set; pass `preview: useIsLivePreviewActive()` |
| A collection without drafts | On Save | A client query (`useQuery`, seeded with server `initialData`), not a server-component-only render |

`find({ drafts: true })` returns one row per document, with a pending draft merged over its
published row, so a preview list shows each document once, as its latest draft, plus
documents that exist only as drafts. A caller without the `readDrafts` permission silently
gets the published rows.

## Declaring previews in one place

Every collection's and global's preview settings can live in the root config
instead of on each `defineCollection`:

```ts
defineConfig({
  admin: {
    livePreview: {
      allowedOrigins: ["http://localhost:3000"],
      collections: {
        headers: { url: "/" },
        pages: { url: (doc) => resolvePagePath(doc.slug), debounceMs: 250 },
      },
      globals: {
        siteSettings: { url: "/", defaultOpen: true },
      },
    },
  },
})
```

Whole settings blocks, not just URLs — the key supplies the slug, so each
entry's `url` resolver is typed against that collection's generated document
with no annotation.

**A collection's own `admin.livePreview` wins, field by field.** Order per
setting, highest first:

1. `collection.admin.livePreview.<field>` / `global.admin.livePreview.<field>`
2. `admin.livePreview.collections[slug].<field>` / `admin.livePreview.globals[slug].<field>`
3. `admin.livePreview.<field>` (root `breakpoints`)
4. the built-in default

Per field, not per block: a collection overriding only `defaultOpen` still
inherits the root entry's `url`.

## Resolving a URL on the server

`url` takes three forms:

```ts
url: "/"                                  // literal path
url: (doc) => `/${doc.slug}`              // resolved in the browser
url: { server: async ({ doc, ctx }) => … }  // resolved on Convex, with ctx
```

The `{ server }` form runs on Convex with a real query context, so it can look
the database up — e.g. find the page that references the document being edited:

`ctx` is typed with no generic and no wrapper: `vex generate` emits your project's
`DataModel` into the `@vexcms/core` module augmentation, alongside `CollectionSlug` and
the document maps, so `ctx.db.query(...)` is checked against your real tables wherever a
resolver is declared. Before the first `vex generate` it falls back to Convex's
`GenericDataModel` rather than erroring.

In the root map — `doc` comes from the key:

```ts
export default defineConfig({
  admin: {
    livePreview: {
      collections: {
        authors: {
          url: {
            server: async ({ ctx, doc }) => {
              const page = await ctx.db
                .query("pages")
                .withIndex("by_author", (q) => q.eq("author", doc._id))
                .first()
              return page ? `/${page.slug}` : undefined
            },
          },
        },
      },
    },
  },
})
```

The resolver also receives **`vex`**, a read-only VexCMS API (`find`/`get`/`search`/
`globals.get`), which returns flat globals and populated relationships and shares the
access resolver — so "find the page that references this document" is one call rather
than a hand-written join:

```ts
url: { server: async ({ vex }) => {
  const [page] = await vex.find({ collection: "pages", limit: 1 })
  return page ? `/${page.slug}` : "/"
} }
```

Or beside the collection — `doc` comes from the sibling `slug`:

```ts
defineCollection({
  slug: "authors",
  admin: {
    livePreview: {
      url: {
        server: async ({ ctx, doc }) => {
          const page = await ctx.db
            .query("pages")
            .withIndex("by_author", (q) => q.eq("author", doc._id))
            .first()
          return page ? `/${page.slug}` : undefined
        },
      },
    },
  },
})
```

`livePreviewUrl(slug, fn)` / `globalLivePreviewUrl(slug, fn)` are still exported for
callers that need to type a resolver away from its config — the slug is the only type
argument, since `ctx` is already the project's own context — but no config file needs
them.

Notes that matter:

- **It stays in the client config**, beside the collection, exactly like a
  field's `validate()` callback. It runs only on Convex, but the closure is
  bundled into the browser — so do not capture secrets in it.
- **It is an object, not a bare async function.** At runtime a function
  returning a promise is indistinguishable from the sync client resolver, and
  guessing wrong would mean calling `ctx.db` in a browser.
- **`doc` is the saved document merged with the editor's unsaved values**, which
  is why this runs per change rather than once.
- **Only this form costs a round trip.** Strings and client resolvers resolve
  synchronously as before, and `NextAdminPage` resolves the first URL
  server-side, so opening an editor never waits on Convex.
- **Wire the endpoint once**: add `livePreviewUrl` to your `convex/vex.ts`
  `collectionsApi` destructure. It runs the collection's own read permission
  check — without it, a resolver reading `ctx.db` would be an open oracle.

## Security: the gate is yours to set

The listener attaches only when **both** are true on the previewed page:

- the URL carries `?vexLivePreview=1` (`LIVE_PREVIEW_QUERY_PARAM`) — the admin panel
  appends this to whatever `admin.livePreview.url` returns, so your resolver returns a
  plain public path and never has to know about it — **or** the window is named
  `LIVE_PREVIEW_WINDOW_NAME`, which the provider writes into an unnamed window the first
  time the gate opens there, so later navigations inside that frame or tab stay in preview,
  and
- the `vex-live-preview` cookie (`LIVE_PREVIEW_COOKIE`) holds `"1"`.

Your middleware sets that cookie, and only after verifying an admin session — session
verification calls your own generated Convex API, so the framework cannot do it for you.
It hands the request off to a Route Handler rather than setting the cookie itself,
because enabling Next.js [Draft Mode](https://nextjs.org/docs/app/guides/draft-mode) —
needed so a previewed document that has never been published can skip its page's own
`notFound()` and still render for the client-side preview layer — can only be done from
a Route Handler or Server Action, never from middleware:

```ts
// middleware.ts / proxy.ts
import { LIVE_PREVIEW_COOKIE, LIVE_PREVIEW_QUERY_PARAM } from "@vexcms/core"
import { DRAFT_MODE_BYPASS_COOKIE } from "@vexcms/next/livePreview"

async function grantPreviewIfRequested(request: NextRequest) {
  if (request.nextUrl.searchParams.get(LIVE_PREVIEW_QUERY_PARAM) !== "1") {
    return NextResponse.next()
  }
  // Already handed off once this request — the route below set BOTH cookies
  // and redirected back here. Skip re-verifying, or this loops forever.
  //
  // Check BOTH cookies, not just the marker: `LIVE_PREVIEW_COOKIE` lives for
  // `LIVE_PREVIEW_COOKIE_MAX_AGE_SECONDS` (1h), but `DRAFT_MODE_BYPASS_COOKIE`
  // (Next's own `__prerender_bypass`) is a browser-session cookie that can
  // disappear well before that — a closed browser, or Draft Mode disabled
  // some other way. Short-circuiting on the marker alone would then skip the
  // hand-off, and never re-enable Draft Mode, for up to the rest of that hour.
  const alreadyHandedOff =
    request.cookies.get(LIVE_PREVIEW_COOKIE)?.value === "1" &&
    request.cookies.has(DRAFT_MODE_BYPASS_COOKIE)
  if (alreadyHandedOff) {
    return NextResponse.next()
  }
  // Unverified callers continue without the hand-off: the route's signed-out
  // branch redirects back to this same URL, so handing them off would loop.
  if ((await resolveSessionStatus()) !== "authenticated") {
    return NextResponse.next()
  }

  const draftModeUrl = new URL("/api/vex/live-preview", request.url)
  draftModeUrl.searchParams.set("redirect", request.nextUrl.pathname + request.nextUrl.search)
  return NextResponse.redirect(draftModeUrl)
}
```

```ts
// app/api/vex/live-preview/route.ts
import { createVexDraftModeRoute } from "@vexcms/next/livePreview"
import { getToken } from "~/auth/server"

export const { GET } = createVexDraftModeRoute({ getToken })
```

`createVexDraftModeRoute` re-verifies the session with your own `getToken` (the same
accessor `createVexRevalidateRoute` takes), calls `(await draftMode()).enable()`, sets
`LIVE_PREVIEW_COOKIE` itself, and redirects to the validated `redirect` target — the
middleware's cookie check above then lets that second pass straight through. A page
that already has a published row never needs this hand-off at all; it only matters for
a document with a draft row and no published one yet, which is exactly when the page's
own published-only query comes back empty.

**Leaving preview mode.** The same route also disables: call it with `?disable=1` (no
session required — turning preview off needs no authorization) to clear both Draft Mode
and `LIVE_PREVIEW_COOKIE` and redirect to `redirect`, or `/` if `redirect` is absent. A
signed-out request that still carries a `redirect` param — the exact shape the
middleware above hands off, always including one — gets the same disable-and-redirect
treatment instead of a bare `401`, so a session that expired between the page load and
this request never leaves Draft Mode stuck on for an anonymous visitor. The one case
that still returns `401` is no session AND no `redirect` param: a caller hitting the
route directly rather than through the middleware hand-off. The open-redirect guard on
`redirect` — same-origin relative paths only — applies to every one of these outcomes.

## Signing out while preview is open

Signing out does not, on its own, touch either preview cookie: they are set by the
Route Handler above, not by your auth library, so a plain `signOut()` call has no way
to know about them. Two things close that gap, and work together:

1. **`getBySlugPreview` never denies the published row.** Pass `drafts: true` to
   `find` with no `access` override, the same as every example on this page — a
   caller without `readDrafts` silently falls back to the published row (or `[]` if
   none exists) instead of being denied the query outright. A session that expires
   mid-preview still sees the live site, not a blank or "not found" page.
2. **Every sign-out calls `disableLivePreview()`.** Import it from
   `@vexcms/next/livePreview` and call it beside your identity-transition hook,
   before the hard navigation or refresh that follows sign-out:

   ```ts
   import { disableLivePreview } from "@vexcms/next/livePreview/client"

   // inside your signOut wrapper, before the hard navigation:
   beginTransition(null)
   void disableLivePreview() // fire-and-forget — never throws, never blocks sign-out
   return signOut().then(goToDestination).catch(goToDestination)
   ```

   It issues a same-origin, credentialed `GET /api/vex/live-preview?disable=1` and
   never follows the redirect it returns — it only needs the cookies cleared, not a
   page load. Pass a different route path as its one argument if your project
   mounted the Draft Mode route somewhere other than `/api/vex/live-preview`.

That covers sign-out in the SAME tab the preview was opened from. A pop-out preview
tab, or sign-out in an unrelated tab, still leaves the cookies on the OTHER tab until
one of two things happens: that tab's own next request, or `admin.livePreview.expiredSessions`.

**`admin.livePreview.expiredSessions: "deny"`** closes that remaining gap at the
proxy/middleware layer instead of the client: set it in your root config, and every
request carrying either preview cookie — with or without `?vexLivePreview=1` — gets
one session check. An unauthenticated one is redirected to
`/api/vex/live-preview?disable=1&redirect=<original path>`, clearing both cookies and
reloading the page published, before it ever reaches your route handlers. The default,
`"allow"`, leaves this check out entirely — not a content-secrecy gap either way
(draft content always stays behind its own `readDrafts` check), but a stale cookie can
keep serving the draft-only base layer's published fallback until it expires on its
own. `"deny"` costs one extra session verification per preview-tagged request; `"allow"`
costs none.

Checklist for any project embedding a preview surface:

- **Fail open on the public route.** An absent or stale session with
  `?vexLivePreview=1` should render the normal published page, not redirect to sign-in.
- **List your admin origins** in `livePreview.allowedOrigins`. An empty list disables
  the cross-origin `postMessage` transport entirely.
- **Never widen the allowlist to `"*"`.** Every incoming payload is still validated
  against the target collection's Zod schema, but same-origin is not the same guarantee
  as trustworthy.
- **Call `disableLivePreview()` from every sign-out entry point.** See above.
- **Set `admin.livePreview.expiredSessions: "deny"`** if a stale preview cookie
  surviving past sign-out until it naturally expires is not acceptable for your project.

## Limits

- **Same browser only.** `postMessage` and `BroadcastChannel` are both same-machine,
  same-browser-process constructs. A preview opened on your phone while you type on your
  laptop will not update — that needs a persisted network channel, which is out of scope.
- **`postMessage` needs a window reference**, which the admin only has for surfaces it
  opened itself. `BroadcastChannel` covers the rest (duplicated tab, reopened from
  history, second monitor, pasted URL) as long as it is the same origin.
- **The preview is pre-`beforeChange`.** Fields derived by hooks at write time will not
  appear until you save.
- **The panel enables client-side**, after hydration — the previewed page renders no
  extra chrome of its own, so nothing shifts when it does.
- **A window that already has a name is not sticky.** The provider never overwrites an
  existing `window.name`, so a preview opened into a named window turns off on the first
  navigation that drops `?vexLivePreview=1`.
