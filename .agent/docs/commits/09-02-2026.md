### Full message

fix(core): deny constrained rules when the caller has no user

**The crash.** `vexcms.dev`'s admin panel returned a 500 with
`TypeError: Cannot read properties of undefined (reading 'email')` thrown from
inside a `constraints` callback. `anonRole` resolves a sessionless caller to a
real role, so an unauthenticated request reaches that role's rules — and a rule
scoping rows to the caller (`fq.eq("email", user.email)`) dereferenced a user
that was not there. `hasPermission` passed `props.user` through untouched, while
the sibling call site in `resolveAccessRule` already defaulted it. The
`base-nextjs` template ships exactly this shape, so every scaffolded project
carries the same fault, not just this site.

**Why the obvious fix was rejected.** Copying `?? {}` from the sibling stops the
throw and replaces it with something quieter and worse: `convexValuesEqual`
treats `undefined === undefined`, so `eq("email", undefined)` compiles to an
index range matching every row whose field is absent. That trades a loud failure
for a silent widening of access. A regression test pins it — with the naive
fallback the check returns `true` for a row with no email.

**What it does now.** The rule's own behavior decides. When there is no user, one
is substituted that records whether the callback reads from it. A rule that asked
who the caller is gets denied, because there is no answer to give. A rule that
never asked — the read-only `anonRole` case, `fq.eq("status", "published")` —
compiles and evaluates exactly as before. Three tests cover the throw, the
widening, and the user-independent rule that must keep working; the guard was
disabled once to confirm they fail without it.

**Release diagnostics.** The alpha.7 publish failed with
`404 Not Found - PUT https://registry.npmjs.org/create-vexcms` on a package the
account owns, with every package still at alpha.6. `.npmrc` reads
`_authToken=${NPM_TOKEN}`; an unset or empty secret is substituted silently, the
request goes out unauthenticated, and npm answers 404 rather than 401 because it
will not confirm a package exists to a caller it cannot authorise. A preflight
step now fails the workflow before the build with the real reason, prints
`npm whoami`, and warns when the token's package permissions do not cover both
the `@vexcms` scope and the unscoped `create-vexcms` — the granular-token case
that would 404 on that package alone.
