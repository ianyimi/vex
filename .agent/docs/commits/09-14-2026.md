## 01:33 — fix(react)!: make bulk selection reachable and the admin usable on phones

Raw message: `.agent/docs/session-log/2026/09/2026-09-14.commit.md`

fix(react)!: make bulk selection reachable and the admin usable on phones

**Bulk selection is reachable, and gated on delete permission.** `DataTable`
mounted `BulkDeleteModal` but never rendered `DataTableBulkActions` — the only
call to `setDeleteModalOpen(true)` lived in a commented-out block — so ticking
rows did nothing, and `enableRowSelection` was hardcoded `true`, so a role that
cannot delete saw dead checkboxes. The bar is now rendered whenever an
`onBulkDelete` handler is supplied, and `CollectionListView` /
`MediaCollectionListView` drive `enableRowSelection` and `enableBulkActions`
from `canDelete`, so a read-only visitor sees no checkbox column at all. The
commented block had been written against an older prop shape; the component had
since been rewritten to consume a `useTableSelection` object that `DataTable`
never holds. Rather than adopt that hook (replacing the checkbox column, row-id
derivation, and every selection assertion in two suites), `DataTableBulkActions`
takes what `DataTable` already has — `selectedCount`, `onDelete`, `onClear`,
`isDeleting` — and the `all` / `inverse` badges, unreachable without a
select-all-across-pages control, are gone. `useTableSelection` is now
production-dead; spec I reintroduces it with that control. `dataTableSuite` and
`viewSuite` lose their absence-assertions and gain real ones: the bar renders,
deletes exactly the selected ids, clears, and never appears without a handler;
a role without `delete` gets no checkboxes and a role with it does. Two viewer
fixtures that asserted "the select column stays" — true only because selection
was unconditional — now hold `delete: true`, keeping the assertion's real intent
that read-field filtering leaves non-field columns alone.

**The admin no longer overflows at phone widths.** Audited every admin view at
375 / 390 / 768 / 1024. Three genuine overflows shared one cause: the header
action groups (`Revalidate · Save · Cancel` at 270px, `Revalidate all · + New
Theme` at 275px) are `shrink-0 whitespace-nowrap` and never wrapped, pushing the
layout viewport to 394px on a 375px screen. All five view headers gain
`flex-wrap gap-y-2`, and the edit headers' fixed `h-16` becomes `min-h-16` so a
wrapped second line is not clipped. `CreateDocumentModal` and `CreateMediaModal`
hardcoded `w-[50svw]` at every breakpoint — a 187px dialog with 115px inputs on a
phone — and are `w-full` below `sm`, the create form also `h-[80svh]` there since
its field region scrolls. The new bulk bar is `max-w-[calc(100vw-2rem)]` with
`flex-wrap` so it cannot overflow either. The 768 sidebar flip, the mobile
Sheet, the media picker, and both `www` routes were clean; the roadmap tab
strip scrolled correctly but showed no scrollbar, so `Roadmap/index.tsx` adds
`<ScrollBar orientation="horizontal" />`. Audit matrices live under the spec's
`audit/`; a 16px-tall title-link touch target is filed to the backlog for spec G.

**The auto-migration stubs leave the public API.** `diffSchema`,
`planMigration`, `makeFieldsOptional` and `addRemovedFieldsAsOptional` were
exported from `@vexcms/core` and stubbed: `diffSchema` returned an empty diff for
every input, so any caller silently migrated nothing. They move to a new
`@vexcms/core/internal` subpath — sibling packages only, no stability guarantee
— because `cli/src/lib/generateSchema.ts` carries a complete orchestration built
on them that would be wrong to delete. `schema.autoMigrate: true` now throws at
`defineConfig` instead of no-opping; `autoMigrate` was never declared on
`SchemaConfigInput`, only claimed by its JSDoc, and the CLI reads it under
`@ts-nocheck`. That JSDoc and `TypesConfigInput`'s (which stated the wrong
default path) are corrected, and `core/README.md` drops its Auto-Migration
section.

**Root README shows the product and the step that was missing.** The admin

## 03:57 — fix(www): let anonymous visitors read media so og:image and site images render

Raw message: `.agent/docs/session-log/2026/09/2026-09-14.commit.2.md`

fix(www): let anonymous visitors read media so og:image and site images render

**Public-site media was denied to every anonymous request.** `vex/media:getUrl`
is the RBAC-gated media query: `hasPermission(read, images)` with
`throwOnDenied`. `anonRole: user` applies that role to every unauthenticated
public-site request — including the build-time metadata fetch — and the `user`
role in `apps/www/src/auth/access.ts` had no `images` entry, so `"*": false`
denied it. `resolveMediaUrl` in `lib/metadata.ts` swallowed the throw and
emitted no `og:image` on any build; `MediaImage` (Header, Footer, Split)
rendered `null`, so anonymous visitors saw no logo or split images at all. The
`user` role now carries `images: { "*": false, read: true }` with a docblock
explaining why it is load-bearing. `templates/base-nextjs/src/auth/access.ts`
had the same hole, and the marketing overlay ships no `access.ts` of its own,
so every scaffold inherited it — fixed there too, with a note to narrow via a
`constraints` rule rather than remove. Proven against the real matrix: anon
read allowed, update still denied.

**The large-image card is emitted whenever an image resolves.** Discord, Slack
and X choose the large layout from `twitter:card`, not `og:image`, and Next
auto-fills `card: "summary"` (a small thumbnail) when `twitter` is omitted.
`metadata.ts` only set it when a handle existed; now `summary_large_image`
whenever `ogImageUrl` resolved, `site` only with a handle. Mirrored into
`templates/marketing-site/src/lib/metadata.ts`. Takes effect on the next
deploy, since the page is a static prerender; Discord has cached the imageless
embed for the bare URL, so the first share should carry a query string.

**Two production symptoms diagnosed, neither changed.** Stale content after
`seed:reinit` from the Convex dashboard is the documented limitation — seed and
dashboard writes bypass the admin panel's purge route, the ISR backstop is
3600s, and the admin Revalidate button is the remedy. The React #482 crash
("An unknown Component is an async Client Component") ~2s after hydration is
the backlog's `CodePane` entry: a live `useQuery` update that introduces or
changes a `split` / `code_showcase` block re-renders the async `CodePane`
inside `PageContent`'s client tree. It was recorded as "confirmed non-fatal";
it is fatal, and the live-reactivity that motivated deferring the fix never
worked for code panes. Entirely an `apps/www` defect — `RenderBlocks` and
`packages/*` are uninvolved — so the fix stays deferred; the backlog entry now
states the real failure mode and the workaround.

**Repo cleanup.** `.pi/` (199 files), `.rebuild/` (232), `.claude/` (9 tracked
plus 131 MB untracked), `.mcp.json`, `.playwright-mcp/`, the root
`tailwind.css` (a bare `@import`), and eleven rebuild-era or already-executed
one-shot scripts are gone; `claude` leaves `manifest.json#platforms.active` so
`harness sync` retires its bridge files and `.gitignore` block instead of
regenerating them. Everything `roadmap.md` cites as a source or a live spec
points at was moved with history: six planning documents and the pre-rebuild
`core-migrations` implementation into `research/legacy-planning/` behind a
provenance README; `core-convex` and `core-valueTypes` into the versioning
spec's `reference/`, with `research.md` repointed; `CUSTOM-COMPONENTS-SYSTEM.md`
into `research/custom-field-components-hkt-design.md`; and the retired Claude
memory note on type-generator / schema-generator divergence into `backlog.md`.
`naming-conventions.md` swaps its deleted script examples for live ones.

**Header session control and auth modal.** `SessionButton` replaces
`LogoutButton` in the www `Header` block: one slot that is always occupied —
disabled while the session resolves, "Sign in" for a visitor, "Sign out" for
a real account — so the bar's right edge no longer jumps on load and a
signed-out visitor has a way in. Anonymous demo sessions count as signed out.
The `@auth` modal `view.tsx` drops its `<main>` wrapper: the Dialog portals
into `<body>`, so the wrapper was an empty element after the footer that
Next's post-navigation scroll handler targeted, jumping the page to the bottom
behind the modal. Same hunks applied to `templates/base-nextjs`.
