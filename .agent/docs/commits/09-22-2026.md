## 22:45 — feat(core,react,next)!: preview globals and resolve preview urls server-side

feat(core,react,next)!: preview globals and resolve preview urls server-side

**Globals were never previewable.** `LivePreviewProvider` matched an incoming
`collectionSlug` against `collections` only and returned before validation on a
miss, so every update a `GlobalEditView` sent was dropped. It now falls through
to `globals` and validates with `getGlobalInputSchema(...).partial()`. The
overlay map is keyed by preview key rather than document id — `_id` for a
collection document, the slug for a global, which is what the edit view sends;
a global has one document and its `_id` is an implementation detail neither side
should have to agree on. `useLivePreview` and `useLivePreviewDocumentQuery` take
a `VexResourceSlug`, so a global slug is no longer a compile error.

**Server-resolved preview URLs silently were not previews.** `NextAdminPage`
passed `fetchQuery(vexConvexApi.livePreviewUrl, …)`'s result straight to
`initialPreviewUrl` — a plain public URL with no `vexLivePreview=1`, so the
iframe and the pop-out link loaded an ordinary page that listens to nothing.
`appendLivePreviewParams` moved out of `LivePreviewPanel.tsx` into
`@vexcms/core`, and both the collection and global branches now route through
one `resolveInitialPreviewUrl`, so the server and browser paths cannot drift.
`useLivePreviewServerUrl` holds the last resolved URL while a later edit's query
is in flight (`placeholderData: keepPreviousData`) instead of falling back to
the server-rendered one — that fallback changed the iframe's `src` and reloaded
the preview, repainting the saved document between edits.

**Config has one provenance.** `LivePreviewProvider` takes no props at all; it
reads `collections`, `globals`, and `admin.livePreview.allowedOrigins` from
`VexConfigContext`. `VexConfigProvider` moved to the app root, serving the admin
panel and the public site from one mount, which deletes
`app/(vexcms)/admin/clientProviders.tsx` and `SiteLivePreviewProvider.tsx` from
`apps/www` and both templates. Public routes stay statically prerenderable: the
provider is a client component that reads nothing on the server and gates itself
on `?vexLivePreview=1` plus the session-verified cookie.

**Root preview maps and `{ server }` resolvers.** `admin.livePreview.collections`
and `.globals` declare preview settings centrally, resolved against the
per-collection form by one `resolveLivePreviewSettings` precedence function. A
`url` may be a literal path, a client resolver, or `{ server }` — invoked in a
Convex query with `ctx` and a read-only `vex` api, for previews whose path lives
in the database.

**`VexCallbackApi`.** Config callbacks receive `vex` — `find`, `get`, `search`,
`globals.get`, `globals.find` — bound to the caller's `ctx` and config. Access is
bypassed by default: a uniqueness check that silently skipped rows the caller
cannot read would let a duplicate through, a correctness bug that reads as a
flake.

**Typed `ctx` without type parameters.** `vex generate` emits the project's
`DataModel` into the `GeneratedVexTypes` augmentation, so `VexQueryCtx` and
`VexMutationCtx` name the project's own context, and the `TCtx`/`TDataModel`
parameters are gone from `validate()`, the preview resolvers, and the
`livePreviewUrl`/`globalLivePreviewUrl` helpers — TypeScript has no partial
type-argument inference, so a parameter there would have dropped the inference
that types the fields. Lifecycle hooks keep their per-method `TDataModel`, which
is inferred fresh from the `ctx` each dispatch passes and is load-bearing there. `toVexQueryCtx`/`toVexMutationCtx` in `api/utils.ts` are now the only
place the generic-to-project conversion is written; it cannot be a subtype
relation, because `GenericQueryCtx` is invariant in its model.

**Field validators throw.** `validate()` raises a `ConvexError` instead of
returning a string, and `validateFields` normalizes every failure to one shape.
Field generics are slug-first (`VexResourceSlug`, `DocumentByResourceSlug`).

**`<ThemeLive />` joins on the client.** `api.theme.getActive` resolves
`siteSettings -> theme` on the server and is structurally blind to an unsaved
`activeTheme`, so the site never re-skinned in preview. It now reads the global
through `useLivePreviewDocumentQuery` and resolves the theme via a new
`api.theme.byId`. Element ownership moved to a mount-scoped effect — creating the
`<style>` inside the effect that writes it meant every dependency change ran that
effect's cleanup first and removed it, flashing the saved theme for the length of
the round trip.

**Removed:** the floating `LivePreviewIndicator`. It could not be expanded in the
full-page preview route and earned nothing; the previewed page now renders no
chrome of its own. The gate tests used its button as their observable and were
rewritten against what defines the gate — whether a broadcast update reaches the
overlay.

**Docs, including a sweep back to `0.1.0-alpha.18`.** Four parallel audits over
every commit since that release found rot the live-preview work had masked, all
fixed here. `packages/next/README.md` and `packages/react/README.md` both still
told readers live preview "is not implemented yet" and showed `VexConfigProvider`
mounted around the admin route only. `packages/core/README.md` and
`fieldValidator`'s own TSDoc `@example` still taught the pre-amendment `validate`
contract — `return \`…\``and an explicit`DataModel`type argument — so the
generated API reference shipped a snippet that no longer type-checks; the core
README also linked a lifecycle-hooks guide that was never written. Three roadmap
items in`apps/www`'s `Roadmap`block carried`status: "coming-soon"`, which is
not one of the select's options, so the renderer grouped them into nothing and
they were invisible on the live page — the same four-item fault ships in
`templates/marketing-site`. Lifecycle hooks were still "planned" in
`convex/seed.ts` while the same file's FAQ said they had landed.

The live-preview guide teaches the propless provider and the root
config mount, and its root-config snippet moves `livePreview` under `admin`;
`framework-adapters.md` and `access-control.mdx` drop `admin/clientProviders.tsx`
for the root mount; the theming guide's "Live updates" section now teaches the
client-side `siteSettings -> theme` join and the mount-scoped `<style>` effect,
since the old pattern it taught is exactly the one that flashes. Live preview
moves to shipped in all three roadmap surfaces — `apps/docs/roadmap.md`, the
`Roadmap` block config, and `convex/seed.ts` — with the FAQ copy that called it
in-progress corrected.

Mirrored to `templates/marketing-site` (`ThemeLive`, `theme.byId`, both layouts,
`vex.config`) and `templates/base-nextjs` (root config mount). Marketing copy and
seed content deliberately not mirrored — the template ships starter content.

BREAKING CHANGE: `LivePreviewProvider` no longer accepts `allowedOrigins` or
`collections` — mount `VexConfigProvider` at the app root and it reads both from
context. Field `validate()` must throw instead of returning a string. Config
callbacks no longer take `TCtx`/`TDataModel` type parameters; a project that ran
`vex generate` before this must run it once more or `ctx` stays
`GenericDataModel`. `livePreview` on the root config moved under `admin`.
