feat(core)!: split vex.config into client-safe and server halves

`sanitizeConfigForClient` nulled every function it sent across the RSC boundary — its
`Sanitized<T>` mapped `(...args: any[]) => any` to `null` — and `ClientVexConfig` was
`Sanitized<Omit<VexConfig, "access">>`, so the access matrix was dropped outright. Every
field `validate`, `admin.condition`, and custom `admin.components` entry arrived on the
client as `null`, and three providers existed only to smuggle the live values back around
that hole. Remove the boundary instead of continuing to work around it: the config splits
into a client-safe half the browser imports directly and a server-only half that layers on
adapters, so nothing that must stay a real function ever crosses a serialization edge.

**Two config files.** `vex.config.ts` resolves through `defineConfig(input):
VexClientConfig` and is imported straight into the browser bundle; `vex.config.server.ts`
wraps it with the new `defineServerConfig({ config, server })`, which adds only
`server.auth.adapter` and `server.storage.adapters`. `VexConfig extends VexClientConfig`
and spreads it rather than nesting, so every existing `config.collections` /
`config.access` reader compiles untouched — the migration for the 24 server-side importers
was an import repoint, nothing more. A field is server-only when putting it on the client
half would break the client bundle, not when the server reads it: `schema` and `types` are
inert path strings and stay on `vex.config.ts`, the one file a developer edits for
settings. `sanitizeConfigForClient`, `stripNonSerializable`, and `ClientVexConfig` are
deleted rather than deprecated, and access validation moves into `defineConfig`, where the
merged collections are already known.

**One React context.** `VexAccessProvider` and `StorageAdapterContextProvider` are gone;
`VexConfigProvider` carries the single `VexClientConfig`, with `useVexAccess()` and
`useStorageAdapterMap()` kept as derived reads of `useVexConfig()`. `useVexConfig()` now
throws outside the provider instead of silently returning an empty config, restoring the
contract the deleted storage provider had; `useVexAccess()` deliberately still returns
`undefined` there, because `useCanAccessAdminPanel` runs on public pages where no provider
is mounted. Every config-shaped prop crossing server → client is deleted:
`AdminLayout`/`AppSidebar`/`AdminTopNav`/`DashboardView`/`GlobalsListView` read context,
and the view and modal `collection` / `global` props now take a slug the component resolves
from context — which is the stronger type, since `CollectionSlug` is a generated literal
union while the old object prop accepted an unregistered collection and failed at runtime.
Both "read from context, else fall back to the RSC prop" blocks are gone with it, leaving
one provenance.

**Auth collections come from a function, not codegen.** The auth adapter cannot run in a
browser graph — real Better Auth options read `process.env.BETTER_AUTH_SECRET` and pull
`better-auth/next-js` → `next/headers` — so the new client-safe
`@vexcms/better-auth/client` exports `betterAuthCollections(schema)`, which resolves a
declarative plugin-descriptor map against a schema snapshot committed inside the package
and runs it through the same conversion `betterAuthAdapter` uses. Measured: Better Auth's
`getAuthTables` over plain `{ id, schema }` descriptors costs 1.1 KB gzip, where
instantiating the real plugin factories client-side costs 154 KB. Apps author one
client-safe `auth/schema.ts` that both `authOptions` (spread) and `vex.config.ts`
(`betterAuthCollections`) read, so model names and `user.additionalFields` have one home.
The snapshot stays honest inside this repo: `gen:auth-schemas` regenerates it, a parity
test asserts it still equals what the installed Better Auth produces, and a compile-time
exhaustiveness assertion over a type-only `import type * as` of `better-auth/plugins` fails
the package's typecheck when an upstream release adds a plugin. Unmodelled plugins route
through `extraSchema`.

**Verification moved server-side and lost its artifact.** `defineServerConfig` compares the
client config's declared `authCollections` against the live `auth.adapter.collections` and
throws `VexAuthConfigError` naming the divergent collection or field. `server.auth` is
optional — omit it for a project with no auth, or to skip the check. It paid for itself
immediately: it caught `apps/test`'s organization plugin losing `teams: { enabled: true }`
during the refactor, which had silently stopped the adapter producing `team`/`teamMember`.

**Client entry points for the two packages that used to drag servers in.**
`@vexcms/file-storage-convex/client` exports `defineMediaCollection` and `uploadFile`
(traced: 2 modules, no `convex` import), so media collections can be declared on the client
config; `convexFileStorage()` no longer takes a collection list, because
`defineMediaCollection` was always the thing stamping `meta.storageAdapter`.

**CLI.** `vex dev` / `vex generate` / `vex deploy` resolve `vex.config.server.*` before
falling back to `vex.config.*`, and fail with a message naming both families when only a
client config exists. `vex generate` is types-only again.

**Docs, roadmap, and llms.txt.** Every guide, README, and TSDoc example moves to the
two-file pattern. Two inaccuracies fixed while there: the roadmap published `tabs`/`ui`
under **Not planned**, contradicting `fields/coming-soon.mdx`, which lists both as
near-term — they are Planned, with the core-invariant cost named; and the root README's
Theming section is cut, since the theming guide owns it. `starlight-llms-txt` was
configured with nothing but a description, so `llms-small.txt` was 1.27 MB against
`llms-full.txt`'s 1.29 MB — the generated `api/**` tree was never excluded, making the
abridged set useless. Excluding and demoting it brings `llms-small.txt` to 181 KB, and the
`llms.txt` entrypoint now carries interpretation notes, a repo link, and Guides/Fields
subsets. The commit checklist gained a "Must be current" item so the framing block is
maintained and currency is verified against the rebuilt artifact rather than assumed.

BREAKING CHANGE: `sanitizeConfigForClient`, `stripNonSerializable`, `ClientVexConfig`, and
`VexConfigInput` are removed from `@vexcms/core`; use `defineConfig` →
`VexClientConfigInput`/`VexClientConfig` and `defineServerConfig` →
`VexServerConfigInput`/`VexConfig`. Projects split their config in two: keep
`vex.config.ts` for `admin`/`access`/`collections`/`globals`/`mediaCollections`/`routes`/
`schema`/`types`/`storage.clientUploads`, add `vex.config.server.ts` exporting
`defineServerConfig({ config, server: { auth: { adapter }, storage: { adapters } } })`, and
repoint server and Convex imports to it. `VexConfig.auth` changes from a bare
`VexAuthAdapter` to `{ adapter }`. `@vexcms/react` removes `VexAccessProvider` and
`StorageAdapterContextProvider` in favour of one `VexConfigProvider config={config}`;
`useVexConfig()` now throws outside it. `AdminLayout`, `DashboardView`, and
`GlobalsListView` no longer take `config`, and the view/modal `collection` / `global` props
take a slug instead of a config object. `@vexcms/next`'s `NextAdminLayout` and
`NextAdminLayoutClient` no longer take `config`. `@vexcms/file-storage-convex` drops
`convexFileStorage({ mediaCollections })` — declare them on the client config via
`defineMediaCollection` from `@vexcms/file-storage-convex/client` — and
`@vexcms/better-auth` moves client-side collection building to
`betterAuthCollections` in its new `/client` entry.
