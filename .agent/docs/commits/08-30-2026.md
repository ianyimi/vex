fix(packages): ship type declarations for all published packages

**Declarations.** Every one of the seven published packages advertised
`types: "./dist/index.d.ts"` and emitted no `.d.ts` whatsoever: all seven
`tsup.config.ts` files carried `dts: false`, annotated "Temporarily disable DTS
to fix CPU issue". Installing any `@vexcms/*` package therefore gave consumers
`any`. Each `build` script now runs
`tsup && tsc -p tsconfig.build.json --emitDeclarationOnly`. `dts: false` stays
on purpose and its comment now says why — tsup's rollup-dts pegs the CPU on this
dependency graph, so tsup builds JS and tsc builds types.

**Why it was disabled.** The real blocker was TS6059, `File is not under
rootDir`. Workspace dependencies resolved through the `source` export condition,
which pulls sibling `src/` trees into each package's program. The build configs
now set `"customConditions": []`, so dependencies resolve through their
published `types` entry instead; Turbo's `dependsOn: ["^build"]` already
guarantees upstream `dist/` exists first. `react` and `richtext-plate` gained a
`tsconfig.build.json`; the other five had one and gained the condition. Dev
configs are untouched and still resolve siblings through `source`, keeping
go-to-definition and single-pass typecheck.

`@vexcms/better-auth` needed more than a resolution flag: `adapter.ts` imported
`AuthFieldMeta` through `../../core/src/auth/types`, reaching into another
package's source. A package that does that cannot emit a correct declaration, so
`AuthFieldMeta` is now part of `@vexcms/core`'s public surface and the adapter
imports it from the barrel.

**Release script.** `scripts/sync-template-versions.mjs` crashed
`pnpm version:packages` outright — it read a `packages/create-cli/templates`
directory that no longer exists, and its hardcoded package list still named
`@vexcms/admin-next`, `@vexcms/ui`, and `@vexcms/richtext` from before the
renames. It now derives the package set from the workspace and warns about
template directories without a `package.json` rather than throwing.

Verified by packing `@vexcms/core`: the tarball contains `dist/index.d.ts` and
its `catalog:` specifiers are resolved to real ranges. Publishing must go through
`pnpm` — `npm pack` leaves `catalog:` literals in `dependencies`.

fix(core): narrow LucideIconName to the names that actually render

`LucideIconName` accepted 5,843 strings; only 1,702 of them render. The cause is
one import in `core/src/utils.ts`: `import type icons from "lucide-react"` takes
the *default* export, and `lucide-react` has none, so `esModuleInterop`
synthesized one from the module namespace and `keyof typeof icons` widened to
every export of the package. That admitted alias spellings (`AlertCircle`, which
is `CircleAlert` re-exported), the `*Icon`-suffixed duplicates (`UsersIcon`), and
non-icons — `createLucideIcon`, `icons`, `Icon` itself. None of those are keys of
the `icons` map that the `Icon` component indexes, so roughly 4,100 names
type-checked and then rendered nothing at all.

Both packages now derive the type from the named `icons` map, which is exactly
the set `Icon` can resolve. `@vexcms/react` no longer declares its own copy — it
re-exports core's. Two independent `keyof typeof icons` declarations that
disagreed is what hid this: the three `@ts-expect-error` directives in
`AdminSidebar`, annotated "unknown lsp error", were core's wide type failing to
satisfy react's narrow one, and are now removed as unused.

`Icon` still returns `null` for an unresolved name so untyped CMS data cannot
throw mid-render, but it no longer fails invisibly: outside production it warns
once per offending name, deduped through a module-level set.

Consumers using an alias or `*Icon` spelling in `admin.icon` will now see a type
error. Use the canonical name from https://lucide.dev/icons — those values never
rendered. No config in this repo used one.

chore(harness): review every outstanding change in /commit, not one session

The commit skill assumed the session running it was the only one with work in the
tree. In practice several agent sessions and the developer leave changes behind
across a day, often without a log entry, so running `/commit` from whichever
window happened to be open produced a message for that window's slice and left
everything else uncommitted and unattributed.

Scope is now the working tree. Preflight makes `git status` + `git diff` the
authoritative work list, and two new steps run before anything is written:
**cluster the tree into commits** (disjoint file lists that together cover every
changed path, split by concern rather than by author) and **attribute each
cluster to a session** from conversation, log entries, mtimes, and
`git log -S` on introduced lines. A cluster this session did not produce still
gets logged, messaged, and named.

Each cluster gets its own log entry, including a reconstructed one for a session
that never logged — opened with a blockquote marking it recollection-free so a
cold-start reader can tell evidence from memory. `references/session-log-format.md`
documents that entry shape.

Multiple commits per day are now first class. `harness log commit-msg` reads only
the last log entry and emits one message, which the skill now states outright:
its output is the first draft for cluster 1, the rest are written by hand as
`YYYY-MM-DD.commit.2.md`, `.commit.3.md`, … The day's ledger carries one
`## HH:MM — <commit title>` section per commit, each with a copy-pasteable
`git add`/`git commit -F` block for exactly its files. Harness bookkeeping —
session log, ledger, standards, state, tasks — rides the last commit, since those
files aggregate the whole run and cannot be split honestly.

Renaming follows the same widening: each entry takes the title of the commit its
own cluster produced, and the earlier-sessions sweep may use `git log -S` on a
line a commit removes to find the session that introduced it.

Two smaller corrections from running this on itself: the gate now warns that a
restored-from-cache banner is not evidence the check ran and must be re-run with
the runner's force flag, and `harness_model_role` moves `smol` → `default` —
clustering a diff and reconstructing an unlogged session is judgement work, not
the mechanical transcription the old flow described.

All three files are pushed to the upstream harness template
(`chezmoi/harness/src/templates/skills/commit/`) so other projects can take them
via `/harness-pull`; `harness fetch commit` now reports them `same` here. The
cache warning is written runner-agnostically for that reason — Turborepo's
`FULL TURBO` is named as one example, not the rule. `commit-checklist.md` is
deliberately not pushed: it is customized per project at init, and still reports
`changed` against upstream. `resume-session`'s session lookup was widened to
`.commit*.md` upstream, since the numbering convention is new.

fix(deps): publish peers as ranges, pin the catalog exact

**Published peers were exact, so consumers could not install.** `peerDependencies`
said `catalog:`, and catalog entries are substituted at pack time, so `@vexcms/core`
shipped `"convex": "1.44.0"`, `"lucide-react": "0.577.0"` and
`"@tanstack/react-table": "8.21.3"`. Convex ships fortnightly (1.45.0 landed
2026-08-21), so a current consumer hit a peer conflict on install. `@vexcms/core` was
also a `peerDependency` of three siblings as `workspace:*`, which packs to the exact
`0.1.0-alpha.1`. Peers now resolve from a dedicated `catalogs.peers` block of 12
deliberate ranges, and core peers as `workspace:^`. Verified with an `npm i` probe: a
scratch consumer on convex 1.45.0 installs the packed tarball clean (42 packages),
where the previous exact peers produced `npm ERESOLVE`.

Peer floors are set per dependency from what the code uses, not by a blanket rule.
`react >=18.0.0` stays generous because no React-19-only API appears anywhere in
`packages/*/src`; `convex`, `better-auth`, `@tanstack/react-form` and `lucide-react`
get tested floors because they churn. `@vexcms/next` moves `next` from `>=14.0.0` to
`>=15.0.0`, correcting a claim that never held — `NextAdminPage` awaits
`props.params`, which Next 14 types as a plain object.

**Nothing inward was bound.** 69 of 88 catalog entries were ranges and four more specs
bypassed the catalog entirely, so only the lockfile held versions in place; one
lockfile-less resolve moved 21 of them, and `turbo: ^2.8.10` had already drifted to
2.10.4. The default catalog is now 85 sorted, exact entries, every value read from what
the lockfile already resolved. Six dead entries and `@tanstack/zod-form-adapter`
(imported nowhere) are deleted. Sweeping `apps/www`'s `convex: ^1.44.0` in fixed a
live build break rather than a style nit: a fresh resolve installed convex 1.44.0 *and*
1.45.0, and `www#build` failed with `TS2322: GenericQueryCtx<{ user … }> is not
assignable to GenericQueryCtx<GenericDataModel>`.

**Every peer is now also a `catalog:` devDependency of the package declaring it.** pnpm
auto-installs an unsatisfied peer at the range's maximum, so it lands beside the pinned
copy. `packages/react` declared none of its 7 peers while `packages/core` already
declared all 6; a from-scratch resolve produced `@tanstack/react-query` at both 5.101.2
and 5.102.8 and `docs#build` died on `relationship/Input.tsx`. Ten devDeps added across
`react`, `next` and `cli`.

**`strict-peer-dependencies=false` is gone**, replaced by `strictPeerDependencies: true`
plus three narrow, commented `allowedVersions` entries and one `override` — strictly
less suppression than the repo-wide flag, since any new mismatch now fails the install.
Achieved without touching `@convex-dev/better-auth@0.11.5` or its patch, so decision D1
stands. The setting must live in `pnpm-workspace.yaml`: pnpm 10 reads it from `.npmrc`
as a no-op, printing the conflict and exiting 0.

Blast radius is covered separately from intent, since pinning `nanoid` says nothing
about nanoid's own tree: `minimumReleaseAge: 4320` (72h, excluding `@vexcms/*`) and an
explicit `onlyBuiltDependencies: []`.

**`scripts/check-packed-manifests.mjs` enforces all of it** rather than leaving it to
review — `--sweep` asserts every dependency spec is `catalog:`/`workspace:`, `--packed`
packs all 8 publishable packages with pnpm and rejects any exact peer, ranged dependency
or leaked `catalog:`. Baseline was 30 violations; the gate now requires 0. WP-1's planned
CI assertion should call this rather than add a second script. `create-vexcms` is in the
changeset despite an unchanged manifest: its `dependencies` are `catalog:` entries, so
its published output changes with the pinning.
