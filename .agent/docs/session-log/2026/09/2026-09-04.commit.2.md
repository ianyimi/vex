fix(www): call convex deploy directly so the vercel build resolves a binary

The `buildCommand` shipped in `7200c67` never reached Next.js. Vercel failed on
its first line:

    > www@0.1.1-alpha.4 vex:deploy /vercel/path0/apps/www
    > vex deploy
    sh: line 1: vex: command not found

**The command exists; the binary does not.** `vex deploy` is implemented in
`packages/cli/src/commands/deploy.ts` and wired at `src/index.ts`'s
`case "deploy"`, so this is not a missing feature. `@vexcms/cli` declares
`bin: { "vex": "./dist/index.js" }`, and `dist` is gitignored — `.gitignore:24`
is `/**/dist`, and `git ls-files packages/cli/dist` returns nothing. On a fresh
CI clone that target does not exist until the CLI is built, so pnpm has no
usable shim to link into `apps/www/node_modules/.bin`. It resolves locally only
because the CLI has already been built there, which is why the script passed
review and failed in CI.

**The build now calls `convex deploy`.** `apps/www`'s `vex:deploy` script is
replaced by `deploy:convex`, and `vercel.json`'s `buildCommand` becomes
`pnpm deploy:convex && pnpm build`. `convex` is a *published* dependency of the
app (`convex@1.44.0`, `bin: { "convex": "bin/main.js" }`), so its binary is
present the moment `pnpm install` finishes and there is no build ordering to get
wrong. The alternative — building `@vexcms/cli` ahead of the app inside the
app's own build — inverts the dependency and slows every deploy to regain
something the repo already has.

**Dropping the codegen step costs nothing here.** `vex deploy` adds schema
generation and auto-migration on top of `convex deploy`, but all three generated
artifacts are committed — `convex/vex.schema.ts`, `convex/schema.ts` and
`src/vex.types.ts` — so `convex deploy` ships exactly the schema `vex deploy`
would have produced. `turbo typecheck` already fails when those artifacts drift,
which keeps schema freshness enforced at the commit rather than at deploy time.
The tradeoff is recorded: auto-migration no longer runs in CI, so a schema
change that needs it must be migrated against production by hand before the
commit that depends on it lands.

`ADR-008` is corrected rather than superseded. It was written in the same run
that introduced the broken command, so its Decision section documented something
that never executed; its Context — the stale-backend failure and the two
unrelated-looking bugs it produced — is unchanged and still accurate.

No published package is touched, so this needs no changeset and no version bump.
