## The one thing that matters most

Read **`## Test Authoring Protocol`** in `spec.md` and obey it literally. It is binding on
every group.

**Every assertion encodes INTENDED behavior and the edge cases a real user hits — never the
behavior that happens to be implemented.** A test that pins a bug passes forever while the bug
ships.

Derive intent in this order, stopping at the first that answers:

1. The component's or hook's own JSDoc.
2. The type contract in `@vexcms/core`.
3. The plain meaning of the function or prop name. A parameter accepted and ignored is a defect.
4. The sibling implementation — where three views gate a control and the fourth doesn't, the
   three define intent.

If none answers, the behavior is unspecified: add it to the spec's open questions. Do not
invent a contract and do not pin the current output.

The Protocol also carries a **"Read the code before writing anything"** table — per surface, in
order, and what each file tells you. Follow it. Several assertions in this spec were corrected
during authoring by reading installed library source or running it rather than assuming.

When implementation diverges from intent: assert the intended value, let it fail, record it via
`scripts/record-test-findings.mjs`, add it to `BUGS-REPORT.md`, and tag the test with a one-line
`// FAILS: … see BUGS-REPORT <ID>` comment. **Do not** edit the component to make it pass —
fixes are a separate follow-up spec. **Do not** soften, skip, or `it.todo` anything.

Verify with a bare `vitest run`.

## Gate

Step 8 is a **baseline comparison, not "all green"**:

- The ~918 pre-existing tests must still pass. A regression there is your bug.
- Every new-suite failure must appear in this spec's `findings.md`.
- A failure outside that baseline is a defect in this spec's own work.
- **A green test that pins as-built behavior is also a defect.** A shrinking failure count with
  no corresponding component fix means someone softened an assertion.
- `statements: 80` on the post-exclusion denominator. Branches/functions/lines are
  measure-then-paste — run the command, paste the real number, never guess (AP-012).

Coverage is unaffected by the failures: a failing assertion still renders the component.

## Constraints that will bite you

1. `convexTest(schema, testModules)` — **always both args**. One arg throws
   `import.meta.glob is not a function`.
2. A test file containing JSX must be `.tsx`.
3. `pnpm --filter <pkg> exec vitest run <file>` — `test -- <pattern>` does **not** forward.
4. Resolve field controls with `getControl(container, label)`, never
   `screen.getByLabelText(label, { exact: false })` — substring matching collides.
5. **ADR-009:** no `../../form` barrel import inside `components/fields/**`. Import leaf modules.
   The `fields` ⇄ `form` cycle is still in the module graph, only unexercised.
6. **Do not re-split `packages/react/tsup.config.ts`.** Two tsup invocations cannot share a
   chunk; each would bundle its own `AppFormContext` and every consumer mounting a component
   would throw. One config, `splitting: true`.
7. `<AppForm>` via `createElement` needs the documented `AppFormBoundary` cast (AP-006).
8. Base UI popovers/portals render into `document.body`, outside RTL's `container`.
9. Base UI's focus trap and react-dropzone's drag state both defer through
   `requestAnimationFrame`/microtask — wrap those assertions in `waitFor`, they are not defects.
10. No `any`/`as any`; no `ReturnType<typeof fn>` exports (use RTL's `RenderResult`); single
    `options` object params; JSDoc with `@param props.x` + `@returns` on every export —
    `pnpm lint` runs eslint-plugin-jsdoc and 0 errors is a commit gate.
