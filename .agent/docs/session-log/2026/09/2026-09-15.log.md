### Decisions made
- **Descriptors accept schema-affecting options only** (`true | { schema? }`, plus `organization.teams`). Accepting full plugin options would invite moving `sendInvitationEmail` into the client-safe module and shipping a server callback to the browser; options that don't change tables can't change what the admin renders, so nothing is lost.
- **Reimplemented better-auth's `mergeSchema` (~12 lines) instead of importing it.** Measured: importing it from `better-auth/db` defeats that barrel's tree-shaking and costs 77 KB gzip vs 1.1 KB for `getAuthTables` alone. Parity test covers the semantics.
- **Rejected passing `authClient`** (developer's first idea): better-auth client plugins carry `$InferServerPlugin: {} as …` — a type-only cast, `{}` at runtime — so the client can never yield field definitions.
- **Rejected instantiating real plugins client-side:** measured +684 KB min / +154 KB gzip.
- Added then reverted a post-install `vex generate` in create-vexcms: it cannot fix `--orgs` typecheck, because the templates commit non-org `convex/vex.schema.ts` and `convex/_generated/dataModel.d.ts` and Convex codegen needs a live deployment. Pre-existing; template README already opens with `pnpm vex:dev`.

### Problems hit
- Blind enumeration of `better-auth/plugins` to harvest schemas is unsafe — several exports are request handlers that throw, one asynchronously enough to kill the process. Hence: name union from types, instantiation from a curated probe table.
- Plugins spread `schema[table].additionalFields` themselves, so a snapshot generated without overrides can't contain them; `resolvePluginStubs` applies them (and clones first — the merge writes in place).
- Type-level schema exposure is inconsistent upstream: `ReturnType<typeof organization>["schema"]` has literal keys, `admin`'s does not — so schema DATA can't be derived from types even where names can.
