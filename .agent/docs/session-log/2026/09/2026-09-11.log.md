  stays the only gate and still returns `boolean`.

  `stripDeniedFields`, `SYSTEM_FIELD_KEYS`. The read-only "which fields?" counterpart.

  with the resolver, the map fold, `isPayloadBearingWrite`, `deniedFieldIn`.
- `access/types.ts` — `FieldPermissionMap`, `FieldPermissionKey`, `ValidateFieldMaps`, and a

- `apps/www`: the `user` role may now change only `siteSettings.adminTheme`.

### Decisions made

- **`spec-tasks.md` was stale** (prompt_version 1 vs the spec's 4) and described an abandoned
  `fields?:` sibling on the resource entry that DD 1/DD 2 explicitly reject. Regenerated it to
  mirror the spec's 9 steps; `harness implement` was driving the dead design.
- **DD 3's missing-`changes` guard only fires under `throwOnDenied`.** The spec contradicted
  itself: Step 7 documents `usePermission({action:"update", data})` projecting so Save stays
  enabled, but DD 3 made that exact shape throw — GlobalEditView would have crashed on Site
  Settings rather than gating fields. `throwOnDenied` is what separates enforcement from
  advice; all four write paths set it, so the fail-open stays closed. Chosen over
  duplicating a `canEdit` workaround across the three views.
- **A create has no stored document.** Step 3's call site passes the payload as both `data`
  and `changes`, so `deniedFieldIn` diffed every value against itself and could never reject.
  The fold now passes `stored: undefined` when the action is `create`.
- **`FieldPermissionKey` degrades to `string` when a document enumerates no keys.** The spec
  assumed pre-generation degradation that did not exist: `DeclaredDoc<Record<string, unknown>>`
  collapses to `{}`, so `keyof` was `never` and EVERY map key read as excess.
- **Restored the role-key exactness guard.** Inferring `TPermissions` for `ValidateFieldMaps`
  silently dropped excess-property checking on `permissions`, so an unknown role stopped
  erroring. Re-added the `never`-mapped guard `customActions` already uses.
- **`upsertGlobal`'s `defaultAction` moved `read` → `create`/`update`.** The spec called this a
  landed prerequisite; it had not landed. Without it `siteSettings.read: true` authorized
  overwriting the whole global. Also made the patch MERGE rather than replace the `data` blob,
  and moved validation onto the merged document.
- **Read-denied fields are hidden, not disabled** (developer call), and `useVisibleFields`
  hides only when the decision DISCRIMINATES — a blanket "nothing readable" returns every
  field, because that is the document-level gate's job and the RBAC matrices assert
  disabled-not-hidden there.
- **A read-denied field is kept out of the form entirely** — out of `defaultValues` AND the
  Zod schema (`components/form/readableFields.ts`), so a required one cannot block submission.
  Developer-directed after an earlier validation-only narrowing was rejected as over-built.
- **Coverage can no longer fail a run** (developer directive): removed every `thresholds`
  block and `coverage.enabled: true`, so `pnpm test` runs tests only and `pnpm coverage` owns
  coverage.
- **`changedValues.ts`/`readableFields.ts` live in `components/form/`, not `hooks/`** — they
  are not hooks, and `harness struct --check` enforces `use*` naming in `hooks/**`.

### Problems hit

- **Field maps could never deny on create** — payload compared against itself. Found by the
  write-path subagent, fixed centrally in the fold rather than at the call site.
- **`usePermission` threw whenever a map resolved**, which would have crashed the headline
  acceptance scenario. Reported before any fix and resolved in one place (above).
- **`ValidateFieldMaps` rejected every map pre-generation** — see the `FieldPermissionKey`
  degradation decision. Verified afterwards against the real generated registry: a typo'd
  `admnTheme` in `apps/www` reports `✖ field map returns a field not on this resource`.
- **A required read-denied field silently blocked Save.** `useGlobalForm` validated the full
  schema; the stripped document had no `name`, so `handleSubmit` aborted and the error had
  nowhere to render (its input was never mounted). Fixed by narrowing the form.
- **`pnpm test` failed on coverage thresholds, not tests.** `apps/www/src/auth/access.ts`
  dropped to 0% functions purely by declaring permission callbacks its own tests never invoke.
- **`ENOENT coverage/.tmp/coverage-0.json`** — reproduced deterministically: two concurrent
  `vitest run` in one package both die, because vitest wipes `coverage/.tmp` at startup.
  Triggered by a backgrounded agent run overlapping the developer's. Removing
  `coverage.enabled` from the test path eliminated the race surface.
- **`Object.hasOwn(map, key) !== undefined`** — a developer refactor left the old `!== undefined`
  comparison applied to `hasOwn`'s boolean, so it was always true and the per-role wildcard
  fallback became dead code. Caught by the one test that isolates a role whose map omits the
  key; fixed by dropping the comparison.
- **19 `eslint-plugin-jsdoc` errors** across the new exports, invisible to `tsc`. All fixed.
