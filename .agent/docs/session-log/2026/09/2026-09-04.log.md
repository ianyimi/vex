### Decisions made

**`convex deploy` instead of making `vex deploy` work.** The developer's first read was
that `vex deploy` did not exist and needed writing, plus a changeset and a re-version of
`@vexcms/cli`. It does exist — `packages/cli/src/commands/deploy.ts`, wired at
`src/index.ts`'s `case "deploy"` — so none of that was needed. The failure is binary
resolution, not a missing command: `@vexcms/cli`'s `bin` is
`{ "vex": "./dist/index.js" }`, and `dist` is gitignored (`.gitignore:24` — `/**/dist`,
`git ls-files packages/cli/dist` returns 0). On a fresh CI clone the shim target does not
exist until the CLI is built, so pnpm links nothing usable. It works locally only because
the CLI has been built here.

Two fixes were available: build the CLI ahead of the app in CI, or call `convex deploy`.
The second was chosen, and it is what the developer asked for once the command was
confirmed to exist. `convex` is a *published* dependency of the app
(`convex@1.44.0`, `bin: { "convex": "bin/main.js" }`), so its binary exists the moment
`pnpm install` finishes — no build ordering to get wrong.

**Nothing is lost by dropping the codegen step**, which was the thing worth checking
before agreeing. `vex deploy` adds schema generation and auto-migration on top of
`convex deploy`, but all three generated artifacts are tracked
(`convex/vex.schema.ts`, `convex/schema.ts`, `src/vex.types.ts` — confirmed with
`git ls-files --error-unmatch`), so `convex deploy` ships exactly the schema `vex deploy`
would have produced. Schema freshness is already enforced at the commit by
`turbo typecheck`, which is a better place for it than the deploy.

**No changeset, and no re-version.** The fix touches only `apps/www` and one ADR;
`@vexcms/cli` and every other published package are untouched. The developer had
expected to version packages again for this — they do not need to.

### What was built

Third deploy attempt, and the first one verified before pushing. `b1b4340` got
`convex deploy` running — it authenticated and reached `usable-bee-730` — then died in
the bundler:

```
✘ [ERROR] Could not resolve "@vexcms/core/server"
    convex/theme.ts:1:26
  The module "./dist/api/server.js" was not found on the file system
```

- `apps/www/vercel.json` — `buildCommand` is now
  `pnpm turbo run build --filter=www^... && pnpm deploy:convex && pnpm build`.
- `apps/www/package.json` — `deploy:convex` restored (the developer had removed it while
  troubleshooting, leaving `vercel.json` referencing a script that did not exist).
- `scripts/vercel-build-check.mjs` (new) + root `pnpm check:vercel` — reproduces the
  Vercel build locally from a pristine tree.
- `apps/www/README.md` — Deployment section rewritten around the three build steps and
  the new harness.
- `.agent/docs/decisions/ADR-008.md` — amended with the dependency-build requirement.

### Decisions made

**Build the workspace dependencies in the build command, rather than committing `dist`
or adding a `postinstall`.** A fresh clone has no `packages/*/dist`, and every
`@vexcms/*` package resolves through an `exports` map pointing into it, so the Convex
bundler and Next.js both fail on the same missing files. Committing `dist` would put
build output in git; a `postinstall` build would run on every install everywhere, including
developer machines that do not need it. `--filter=www^...` selects exactly the app's
dependencies and excludes the app, so Turborepo orders them and nothing builds twice —
verified against `--dry=json`, which lists the seven expected packages.

**A local Vercel harness, because two failures in a row were invisible here.** Both were
"a gitignored build output does not exist yet", which by construction cannot reproduce in
a working copy where `dist` is always populated. `scripts/vercel-build-check.mjs` copies
`git ls-files -c -o --exclude-standard` — tracked plus untracked-but-not-ignored — so it
takes **uncommitted** work and drops every build output, which is what makes it usable
before a commit rather than after. It then installs with `--frozen-lockfile` and runs the
`buildCommand` read from `vercel.json`, so the harness cannot drift from what Vercel
actually runs.

**The push is substituted, not simulated.** `convex deploy --dry-run` was the obvious
choice and is unusable: it prompts for confirmation and cannot run in a non-interactive
terminal, and it never reaches the bundler. The harness replaces the deploy segment with
an esbuild bundle of `convex/**` using Convex's own resolution conditions
(`conditions: ['import']`), which is the step that failed. Auth, env vars and the upload
are explicitly out of scope and the harness says so on exit.

**`convex deploy` stays, even though `vex deploy` would now work.** The `turbo` step
builds `@vexcms/cli` too, so the binary that was missing in the first failure now exists.
It still buys nothing: the generated artifacts are committed and `turbo typecheck` guards
their freshness.

### Problems hit

**The harness found a second failure the deploy log had not reached yet.** With only the
convex step fixed, `next build` still failed with module-not-found across
`SiteHeader.tsx`, `providers/server.tsx` and all ten block renderers. Fixing the bundler
alone would have produced a third failed deploy; the fix had to cover both, which is
exactly what the harness was built to reveal.

**Two harness bugs, both mine, both caught by running it.** `git ls-files -o` collapses a
wholly-untracked directory into one entry with a trailing slash, so `cpSync` needed a
directory branch. And esbuild rejects multiple entry points without `outdir` even when
`write: false`. The second surfaced as a "bundle failed" line that looked like a real
resolution error — it now exits `2` and reports "harness could not run the probe" so a
harness fault can never be misread as a build fault.

**`esbuild` is not resolvable from `apps/www`** in a pristine install; it is a transitive
dependency of `convex`. The probe resolves it through
`createRequire(require.resolve('convex/package.json'))`, which is also the honest choice —
it uses the same copy Convex itself bundles with.

**The install log is now direct evidence for the first failure.** `pnpm install` in the
pristine tree prints
`WARN Failed to create bin ... .bin/vex. ENOENT: ... packages/cli/dist/index.js` — the
`vex: command not found` root cause, observed rather than inferred.
