fix(www): public admin access, real favicon, collection-to-schema showcase

**The admin panel is now reachable by anyone, read-only.** The header's admin
link was wrapped in `useCanAccessAdminPanel()`, which reads `VexAccessProvider`
— mounted only inside `/admin`. On the marketing site the hook returned `false`
for every visitor, so the affordance rendered for nobody. It is unconditional
now, in a new `AdminDemoButton`. Making it *work* for a signed-out visitor took
more than removing the gate: `/admin` checks authentication before
authorization, and `canAccessAdminPanel` denies `user: null` deliberately —
`hasPermission`'s `anonRole` fallback keys off an empty role list, not a missing
user. Rather than loosen the server gate, the button mints a Better Auth
anonymous session (the `anonymous()` plugin was already registered) and then
navigates. What that session can do is decided entirely by `src/auth/access.ts`:
the `user` role gets `adminPanel.access` plus `read` on `pages` and
`siteSettings`, and `"*": false` denies the rest. An anonymous visitor sees only
those two entries and `+ New Page` renders disabled — the boundary is the access
matrix, not the component.

**A way back out of the panel.** `AppSidebar` grows an `ExternalLink` button
beside `ThemeToggle`, linking to `/`. The panel mounts under `basePath` inside
the host app, so the site it manages is always at the root — nothing to
configure and nothing to go stale. The topbar's existing "Home" is a breadcrumb
to `/admin`, not an exit. It uses the anchor-as-button pattern already
established in `CollectionListView` (`nativeButton={false}` +
`render={<VexLink/>}`), so Base UI emits `aria-disabled`, which is what
`buttonVariants` actually styles.

**The home code showcase now shows a collection becoming a database.** It
previously paired a block definition with the interface generated from it, which
demonstrated types rather than the thing vex is for. It is now a blog `posts`
collection next to the Convex schema `vex dev` emits from it. The collection is
invented — an example anyone would recognise rather than one of this site's own
— but the output is not: `posts` was written into `apps/www`, registered in
`vex.config.ts`, and the right-hand pane taken verbatim from the generator, down
to `.index("by_author", ["author"])`, which vex infers from the relationship and
which nobody would have written by hand. The throwaway collection was then
reverted. Nine field types survive the round trip visibly — `select` narrows to
a literal union, `upload` and `relationship` become typed id arrays, `group`
becomes a nested object.

**The site was shipping Next.js's favicon.** `public/favicons/favicon.ico` was
the framework's default black circle and white triangle; nothing about
`metadata.icons` would have revealed it, since the file existed and loaded.
Decoding the ICO directory and pulling out its 256px entry did. All three assets
— `favicon.svg`, a regenerated `favicon.ico` at 16/32/48, and a new
`apple-touch-icon.png` — are now rendered from `BrandMark`'s chevron geometry in
ember, matching the mark in the header.

**Docs links and the install tag.** `Header`, `Footer` and `CTA` block defaults
pointed at a relative `/docs` that this site does not serve; they now point at
`https://docs.vexcms.dev`, as does `access.ts`'s `@see`. Every install string
moves from `@latest` to `@alpha`, including `apps/www`'s `vex:update` script,
where `@latest` resolves to the stale `0.0.20` line and would have silently
downgraded a project off the alphas.

**Two defects found while verifying.** `CodeShowcase` mapped over its panes
returning a bare `<>` with keys on the children, so React logged "Each child in
a list should have a unique key prop" on every homepage render — now a keyed
`Fragment`. And the seeded header `menuItems` carried its own admin entry, which
rendered beside the new button; removed from www's `seed.ts`.

**Both templates synced, minus the one thing that must not ship.** Without this,
`create-vexcms@0.1.0-alpha.10` would scaffold Next.js's favicon, `/docs` links
that 404, and install copy pointing at `0.0.20`. `marketing-site` takes
`convex/seed.ts`, `src/app/layout.tsx`, the seven touched block configs,
`CodeShowcase/index.tsx` and a new `public/` tree with all three favicon assets;
`base-nextjs` takes `component-example.tsx` and the replaced `favicon.ico`.
`AdminDemoButton` and the unconditional header button are deliberately excluded:
base's matrix sets `adminPanel: { access: false }` for the `user` role, so the
anonymous-demo flow would sign a scaffolded project's visitor in and bounce them
to `/unauthorized`, and granting that access in the template would make every
user's admin panel publicly readable. `apps/www` is a demo *of* the CMS; someone
else's project is not. The template keeps its `useCanAccessAdminPanel()` gate and
its seeded `Admin` nav item as the owner's route in.

**alpha.10, with no changeset for the template work.** `pnpm version:packages`
had already consumed `admin-sidebar-view-site` into `pre.json` and bumped all
eight packages through the `fixed` group, so a new changeset would have landed in
alpha.11 while describing files that ship in alpha.10. The description went into
the already-created `create-vexcms@0.1.0-alpha.10` CHANGELOG entry instead, which
the fixed-group bump had left empty. Publishing stays on `--tag alpha`; `latest`
remains `0.0.20`.

**`seed.ts` being right does not make the live site right.** `seed:init` is
insert-only-if-absent, which is understood for `page:home` — but the
`header`/`footer` rows in the dev deployment also predated the current
`seed.ts`, still rendering the `/docs` links seed had already fixed. Verifying
the seeded values meant dropping those rows and re-seeding. Recorded as P-021,
now the standing workflow: content changes go into `seed.ts`, then the affected
rows get wiped and re-seeded from the Convex dashboard. `pages`, `headers` and
`footers` are safe to wipe together; `themes` is not, because
`siteSettings.activeTheme`/`adminTheme` hold theme ids and `init` skips an
existing singleton.
