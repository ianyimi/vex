fix(www): build workspace deps before deploying, add a local vercel build check

`b1b4340` got `convex deploy` running — it authenticated and reached
`usable-bee-730` — and then died in the bundler:

    ✘ [ERROR] Could not resolve "@vexcms/core/server"
        convex/theme.ts:1:26
      The module "./dist/api/server.js" was not found on the file system

**The workspace packages were never built.** A fresh clone has no
`packages/*/dist`, and every `@vexcms/*` package resolves through an `exports`
map pointing into it — `@vexcms/core`'s `./server` subpath is
`./dist/api/server.js`. This is the same fault as the previous failure, one layer
in: a gitignored build output that does not exist yet. `vercel.json`'s
`buildCommand` becomes
`pnpm turbo run build --filter=www^... && pnpm deploy:convex && pnpm build`.
`--filter=www^...` selects the app's dependencies and excludes the app itself, so
Turborepo orders them and nothing is built twice. `deploy:convex` is restored to
`apps/www/package.json`; it had been removed while troubleshooting, leaving
`vercel.json` pointing at a script that no longer existed.

Committing `dist` or adding a `postinstall` build were the alternatives. The
first puts build output in git; the second runs on every install everywhere,
including machines that do not need it.

**`next build` was going to fail next, and nothing had revealed that yet.** With
only the bundler fixed it still failed with module-not-found across
`SiteHeader.tsx`, `providers/server.tsx` and all ten block renderers. Fixing the
deploy step alone would have bought a third failed deploy.

**`scripts/vercel-build-check.mjs` (new, `pnpm check:vercel`) reproduces the
Vercel build locally.** Both failures so far were invisible in a working copy by
construction — `dist` is always populated here, so the command that fails in CI
always passes locally. The harness copies exactly what a fresh clone would have
(`git ls-files -c -o --exclude-standard`: tracked plus untracked-but-not-ignored),
which keeps uncommitted work and drops every build output, so it is usable
*before* a commit rather than after. It installs with `--frozen-lockfile` and
runs the `buildCommand` read out of `vercel.json`, so the harness cannot drift
from what Vercel runs.

The deploy segment is substituted rather than simulated. `convex deploy
--dry-run` prompts for confirmation, cannot run non-interactively, and never
reaches the bundler; the harness instead runs an esbuild bundle of `convex/**`
with Convex's own resolution conditions, which is precisely the step that broke.
The push, the deploy key and Vercel's environment are out of scope and the
harness says so when it exits.

Verified before pushing, which is the point: `pnpm check:vercel` passes from a
pristine tree — 6 dependency builds, 21 `convex/**` modules bundled with every
`@vexcms/*` import resolving, `next build` compiled. The same harness reproduces
both earlier failures when the fix is removed, so it is known to be capable of
failing rather than merely reporting success.

`ADR-008` gains the dependency-build requirement. `apps/www/README.md`'s
Deployment section is rewritten around the three build steps, why each is
load-bearing, and how to run the harness.

No published package changes, so no changeset and no version bump.
