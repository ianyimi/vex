build(dev): resolve workspace packages to source so package edits hot-reload

Editing a file under `packages/*/src` stopped reaching the browser: the apps resolved
`@vexcms/*` through the `import` condition to `dist`, so every change had to round-trip
through that package's `tsup --watch` first — and that watcher silently drops filesystem
events for some directories. `packages/react/src/components/livePreview/**` never fired
while `src/hooks/**` and `src/context/**` did, with the OS delivering events for all of
them (verified against raw `fs.watch` and a standalone chokidar process). tsup's ignore
predicate is `globSync(path, { ignore }).length === 0`, and tinyglobby defaults to
`onlyFiles: true`, so directory paths glob to nothing and read as ignorable. Scoping the
watchers with `tsup --watch src` helped but did not fix it.

**Dev resolves source.** `apps/www/next.config.ts` and `apps/test/next.config.ts` gain
`workspaceSourceAliases()`, feeding `turbopack.resolveAlias`. It derives the map from each
package's own `exports.*.source` condition rather than hardcoding paths, so adding a
subpath export needs no edit here, and it skips string exports carrying no `source`
(`@vexcms/react/styles` is a CSS file). 17 specifiers across `core`, `react`, `next`,
`better-auth`, and `file-storage-convex`. Next now watches the real `.tsx` files: real
Fast Refresh, and no bundler in the dev loop. `transpilePackages` is deliberately absent —
the alias bypasses `node_modules` entirely, so it would buy nothing.

**Production is unchanged.** The helper returns an empty map when
`NODE_ENV === "production"`, so builds keep resolving `dist` and what ships is exactly what
the published packages contain. Verified: after the change, `apps/www`'s production build
still lists `packages/react/dist/index.js` in its client-reference manifest, and `/` is
still statically prerendered.

**Alias values are relative to the app directory, not `turbopack.root`.** The comment on
`apps/test`'s pre-existing nuqs aliases claims the latter; following it produced an alias
that resolved to nothing and fell back to `dist` with no error, which is why the first
attempt appeared to do nothing at all. Absolute paths are rejected outright (Turbopack
prefixes `./` and reports "server relative imports are not implemented yet"). Paths are now
computed with `relative(appDir, absoluteSource)`, proven by the same manifest flipping from
`packages/react/dist/index.js` to `packages/react/src/index.ts`. By that evidence the nuqs
aliases are themselves inert; they are left alone here because correcting them changes
runtime behavior and wants its own verification.

**`@vexcms/react`'s client boundary moves into the source barrel.** `src/index.ts` and
`src/testing/index.ts` now open with `"use client"`, and `tsup.config.ts` drops the `banner`
that used to inject it. A banner only exists in the bundle, so an app importing
`src/index.ts` directly would fail its first RSC import with "You're importing a module that
depends on useState into a React Server Component module". Marking the barrel reproduces the
banner's semantics exactly — everything reachable from a client entry joins the client
graph — rather than auditing ~90 modules individually. esbuild preserves an entry's
directive prologue, so `dist/index.js` and `dist/testing/index.js` still open with exactly
one `"use client";`; keeping the banner too emitted it twice.

**Templates are deliberately not synced.** `scripts/template-diff.mjs` flags
`next.config.ts` as CHANGED and it stays that way: a scaffolded project has no `packages/`
directory, so these aliases are meaningless there. Everything else the diff reports is
pre-existing drift this commit does not touch.

Also folded in: two formatting-only edits made in the same working tree —
`LivePreviewPanel.tsx` unwraps a redundant flex `div` around the preview link, and
`CollectionEditView.tsx` re-indents the split-pane block under its wrapper element.
