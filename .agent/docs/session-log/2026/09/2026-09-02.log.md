### Problems hit

- **`select` fields unusable below the fold** — the session's hardest bug, and I was wrong
  about the cause three times before measuring it. Scroll locks (`modal` defaults on
  `MultiSelect`/`Select`/`DropdownMenu`), `alignItemWithTrigger`'s deliberate page scroll,
  and a global `scroll-behavior: smooth` I had introduced were all real members of the same
  defect family but none was the writer. **Actual cause:** a floating popup is positioned
  a frame or two after it mounts, and until then sits at the end of `<body>`; cmdk
  `scrollIntoView`s its highlighted item in a mount-time layout effect inside that window,
  which walks every scrollable ancestor and drags the page to the popup's pre-position
  location. Caught with a stack trace (`pageScroll 1380 → 39`, a 1341px jump).
  `scrollIntoView` has no `preventScroll`, so it cannot be made safe — only a no-op:
  `MultiSelectContent` now holds its content at `display: none` until positioned, then
  reveals, focuses with `preventScroll`, and does the item scroll itself. **Verified on the
  live admin edit form** (developer-supplied session token, home page's roadmap block):
  0px movement with the trigger at top, middle and bottom of the viewport, through full
  open → pick → close cycles.
- **Two false negatives from my own instrumentation.** The browser tool evaluates in an
  isolated JS world (`window.next` undefined), so v1's prototype patches were installed
  where the page never runs — both "zero logs" results were meaningless. Fixed by having
  the page bundle mirror forensics into the DOM. Separately, `page.click` scrolls via CDP
  before clicking, which produced a phantom −570px reading; re-measured with in-page
  `element.click()`.
- **Five template defects, all invisible to typecheck/build**, found only by running a
  scaffold: `turbopack.root` pinned to the app dir broke every `--monorepo` build;
  `(frontend)/page.tsx` collided with the marketing home on `/` and won; base's fail-closed
  proxy sent `/features` and `/roadmap` to sign-in; `anyApi` in user-project code discarded
  types the generated `api` already has; `<img src={uploadField}>` set `src` to a Convex
  document id, so logos never rendered. All fixed; the overlay cannot delete or edit
  `package.json`, so the route removal and the `shiki` dep live in a new
  `finalizeMarketingOverlay()`.
- **A fail-open I introduced and then caught.** `useCanAccessAdminPanel` initially deferred
  to `hasPermission`, which returns `true` when handed no access config — correct
  server-side, wrong client-side where the absence just means "no provider on this public
  route". Reproduced in the browser (no cookies, Admin link rendered), now fails closed
  with three tests.
- **A destructive mistake:** a type-stripping regex over-matched and gutted four renderers
  (`Header`, `Footer`, `FAQ`, `HowItWorks`). `apps/www` is untracked so there was no git
  restore; all four were rewritten against the generated types.
- **`vex dev` typecheck failure** — `convex/tsconfig.json` lacks
  `customConditions: ["source"]`, so it resolved `@vexcms/*` through dist. Three packages'
  dist carried no `.d.ts` at all (turbo had cached a build recorded before the emit
  landed), and with `allowJs` tsc inferred degraded types from the bundled JS. A forced
  rebuild re-recorded the caches; `pnpm --filter` bypasses turbo entirely, which is why
  direct builds always looked fine.
