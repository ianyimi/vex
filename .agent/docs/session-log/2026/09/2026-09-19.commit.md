feat(core): add lifecycle hooks and server-side field validation

Implements launch-plan item F end to end for `@vexcms/core`, wires it into `apps/www`,
`apps/test`, and `create-vexcms`'s `base-nextjs` template, and adds a slug-uniqueness
`validate()` to the `marketing-site` overlay (ADR-010, ADR-011). The `lifecycle-hooks.mdx`
guide and two verify-script assertions are tracked as follow-up in `docs/tasks.md` — not part
of this commit.

**Lifecycle hooks (ADR-010).** Collections gain `beforeChange`/`beforeDelete`, run inline in
the shared write path and able to reject a write by throwing, and `afterChange`/`afterDelete`,
run via `convex-helpers` triggers after the write commits. `afterChange`/`afterDelete` require
wrapping the app's `mutation`/`internalMutation` builders with the new `createVexMutations`
(`@vexcms/core/server`, `api/triggers.ts`) — they never fire for a write through the raw
`_generated/server` builder, the Convex dashboard, or `npx convex import`. Author hooks inline
or via the new `beforeChangeHook`/`beforeDeleteHook`/`afterChangeHook`/`afterDeleteHook`
factories (`collections/hooks.ts`), which type `doc`/`ctx`/`collection` against the real
`DataModel` and collection config without a cast — each hook property is generic-per-call over
`TDataModel` rather than fixed to the interface's own type params, which is what lets a
dispatch call site infer `TDataModel` from the real `ctx` it passes in with no cast, mirroring
`validateFields`. Shared hook plumbing (`BaseHookProps`) moves to a new `hooks/` package folder.

**Field validation (ADR-011).** Fields gain an async, server-only `validate()`, run after the
generated Zod schema passes, with `ctx` for a transactional uniqueness check via
`ctx.db.query(...).withIndex(...)`. Each field type's `validator.ts` exports a typed wrapper
(`textValidator`, `numberValidator`, `arrayValidator`, etc., built on the shared
`fieldValidator` factory) so `value`/`doc`/`field` are typed against the real
collection/`DataModel`/field config instead of `unknown`. `create`/`update` run
`beforeChange` → Zod → `validateFields` before writing; `remove` runs `beforeDelete` before a
hard delete. This makes true the `text`/`number` validator docstrings' long-standing claim that
validation "happens in the admin panel and mutation handlers" — previously false, since no
`inputSchema`/`validate` reference existed anywhere in `api/create` or `api/update`.

**Fix: min/max independent of `required`.** `array`/`blocks`/`upload`/`relationship` (new
`min`/`max` on the latter) previously coupled the two incorrectly: an optional field's own
empty default could fail its own `min`, and — found via `packages/react`'s pre-existing test
suite after the first fix — a required field's custom `min`/`max` message could become
unreachable when its threshold equaled the required floor, since skipping the check on an
empty array hid the message behind the generic "This field is required." `min`/`max` now runs
whenever a value is supplied; only an empty array on an *optional* field skips the check.

**`@vexcms/react`: sonner replaces the Base UI `Toast` wrapper.** The hand-built
`vexToastManager`/Base UI toast implementation is deleted outright, not left as a second path —
sonner ships stacking/exit-animation behavior Base UI's headless toast does not. `useVexMutation`'s
`onError` now calls `toast.error()` via a new `getVexErrorMessage` (extracts the most specific
message from any thrown error, including the new validation `ConvexError`s). `<Toaster>`
(`AdminLayout`) detects an ancestor `<Toaster>` via a context marker and skips mounting a
duplicate viewport — verified from sonner's own source that, unlike Base UI's, `toast()` never
throws regardless of provider presence, so that could not be used as the detection signal.
`CreateDocumentModal` now renders only a collection's required fields (a quick create);
`RenderFieldInputComponents` gained a `fieldKeys` filter to support it.

**`apps/www`, `apps/test`, and `create-vexcms`'s `base-nextjs` template.** Each app/template's
`convex/vex.ts` now inlines `createVexMutations`, exporting `vexMutation`/`vexInternalMutation`
for `vex/globals.ts` and `vex/media.ts` to build their mutations on — mirrored file-for-file
across all three so a freshly scaffolded project gets `afterChange`/`afterDelete` by default,
not just the two hand-maintained apps. `apps/www/src/vexcms/collections/pages.ts` and
`create-vexcms`'s `marketing-site` overlay's `pages.ts` both wire the `slug` field with a real
`textValidator` uniqueness check.
