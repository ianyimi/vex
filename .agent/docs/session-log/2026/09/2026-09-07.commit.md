feat(next)!: prerender and cache public pages, purge on admin writes

Every public route in `apps/www` was server-rendered on demand, serving
`Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate` with a
Convex round trip per request, and `.next/prerender-manifest.json` listed only
`/_global-error`. Two independent causes: the root layout's `AuthServerProvider`
put a `getToken()` cookie read on every route's render path — proven with a probe
page containing no data fetching that still built as dynamic — and `fetchQuery`
(`convex/nextjs`) hard-codes `cache: "no-store"`. Either alone forces a route
dynamic. `/` now prerenders with `s-maxage=3600` and serves `x-nextjs-cache: HIT`,
`/[slug]` prerenders per published slug, and a save in the admin panel purges the
paths that document renders on.

**Cache and SEO surface (`@vexcms/next`).** Two new entry points.
`@vexcms/next/cache` exports `createVexServerClient`, a server-only Convex read
client that never sets `no-store` and dedupes through `React.cache`, so a page and
its `generateMetadata` share one round trip instead of two — which is why each app
exports a single shared instance from `src/lib/vex.ts` rather than constructing one
per file. It also exports `createVexRevalidateRoute`. `@vexcms/next/seo` exports
`vexStaticParams`, `createVexSitemap`, `createVexRobots`, and `vexMetadata`; each
degrades on an unreachable deployment instead of throwing, so a CI build with
placeholder env still produces a valid route table.

**Route mapping (`@vexcms/core`).** `vex.config.ts` takes `routes: { map }` —
document in, public paths out. `resolveTargets` invokes it once per document
*state*, not once per write, so renaming a slug purges both the old and the new
path without the map knowing a rename happened. Named for what it describes rather
than for its first consumer: an admin "View page" link and sitemap URL generation
want the same answer, and neither is a cache concern. The ISR window is
deliberately absent from config — Next reads `export const revalidate` by static
analysis before any module executes, so it accepts only an inline literal in the
route file. See ADR-009.

**Revalidation (`@vexcms/core`, `@vexcms/next`, `@vexcms/react`).**
`POST /api/vex/revalidate` is session-authorized and re-checks `hasPermission`
server-side; it holds no secret and adds no credential the signed-in caller did not
already present. The wire contract (`VexRevalidateChange`,
`VexRevalidateRequest`/`Response`, `VEX_REVALIDATE_BATCH_SIZE`) lives in core
because `@vexcms/react` builds it and `@vexcms/next` parses it, and neither depends
on the other. `useVexMutation` fires the purge after a successful write,
fire-and-forget — a failed purge is a stale page, a failed save is lost work, so it
never delays or fails the mutation. `RevalidateButton` adds a user-initiated purge
whose failures surface, covering what no client-driven purge can reach: Convex
dashboard edits, `npx convex import`, or a tab closed mid-request.

**Automatic `updatedAt` (`@vexcms/core`).** `defineCollection` injects an optional
`updatedAt` field and `create`/`update` stamp it through one shared helper, so the
two write paths cannot drift. Three ownership-based exclusions: `{ timestamps:
false }` opts out, `meta.protected` skips auth-adapter-owned collections entirely,
and a `meta.locked` field the auth adapter declared itself is never overwritten.
The `meta.protected` gate is load-bearing — `jwks` declares no `updatedAt` of its
own, so a per-field check alone added a column to an auth table nothing would ever
populate. Globals carry none: `vex_globals` is one shared `{ slug, data }` table
with no per-global `defineTable`, so there is no column to stamp.

**Templates and gates.** Both `create-vexcms` templates carry the full change and
are re-verified by real scaffolding. `scripts/verify-scaffold.mjs` gained
route-table and SEO assertions read from build manifests plus a `--negative-routes`
self-test that forces a route dynamic and fails if the assertion still passes; its
exit code discriminates, because returning non-zero on both branches would have let
a broken assertion pass CI forever. `base-nextjs/package.json` gained the
`pnpm.overrides` and `peerDependencyRules` block the monorepo already used — a
fresh scaffold's `pnpm install` was already failing with
`ERR_PNPM_PEER_DEP_ISSUES` once `@better-auth/passkey` published a minor whose peer
range excluded the pinned `better-auth`.

**Fixes found while verifying.** `createVexSitemap` resolved `getUpdatedAt` per
call rather than per item, so a row never written through the API produced
`new Date(undefined)` and an unparseable `<lastmod>`. `SidebarMenuSkeleton` derived
its width from `Math.random()` inside a `useState` initializer, which runs during
render on both server and client — a live hydration-mismatch hazard, now a hash of
`React.useId()` that keeps the intended per-row variety.

BREAKING CHANGE: `defineCollection` injects an `updatedAt` field into every content
collection, so `convex/vex.schema.ts` and `src/vex.types.ts` must be regenerated
and the schema pushed — run `vex dev` (or `vex dev --once`) before the next write,
or Convex rejects the stamped column. A collection declaring its own field named
`updatedAt` is now a compile-time and runtime error: rename it, or opt the
collection out with `{ timestamps: false }`.
