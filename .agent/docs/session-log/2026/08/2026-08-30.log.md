## 2026-08-30 — 03:52 — fix(core): narrow LucideIconName to the names that actually render

**Spec:** (none)
**Commit:** (pending)

### What was built
- `packages/core/src/utils.ts` — `LucideIconName` re-derived from the named `icons` map
  (`import type { icons }`) instead of a default import of `lucide-react`. The type went
  from **5,843** members to the exact **1,702** that render.
- `packages/react/src/components/Icon.tsx` — deleted the duplicate local `LucideIconName`
  declaration; the file now re-exports core's. `Icon` gained a dev-only `console.warn`,
  deduped per name via a module-level `warnedNames` set, for a name that misses the map.
- `packages/react/src/components/AdminSidebar.tsx` — removed 3 `@ts-expect-error Lucide
  Icon names match here, unknown lsp error` directives; they were masking exactly this
  bug and now report `TS2578: Unused '@ts-expect-error' directive`.
- `.changeset/lucide-icon-name-exact.md`.

### Decisions made
- Narrow the type to the `icons` map rather than widen `Icon`'s runtime lookup to the
  module namespace. The map's keys are the canonical lucide.dev names; the extra module
  exports are alias spellings, `*Icon` duplicates, and non-icons (`createLucideIcon`,
  `icons`, `Icon`) that no icon-name type should offer.
- `@vexcms/core` owns the canonical type and `@vexcms/react` re-exports it. Two
  independent `keyof typeof icons` declarations is what let them silently diverge.
- `Icon` still returns `null` rather than throwing — untyped CMS data must not break a
  render — but no longer fails invisibly. The warn is behind
  `process.env.NODE_ENV !== "production"` so bundlers eliminate it.
- `Set` for `warnedNames`, not `Record`: keys are runtime-dynamic (project `ts-set-map`
  rule).

### Problems hit
- Root cause was `import type icons from "lucide-react"` — a **default** import. The
  package has no default export, so `esModuleInterop` synthesized one from the module
  namespace and `keyof typeof icons` widened to every export. One character class
  (default vs named) cost ~4,100 phantom names that type-checked and rendered nothing.
- The two same-named types disagreeing was already known to someone: the three
  `@ts-expect-error`s in `AdminSidebar` were the symptom, annotated "unknown lsp error".

### Where I left off
Done and verified. Rendered all 1,703 map entries through `renderToStaticMarkup` — 0
produce non-SVG output; post-fix type probe rejects `"AlertCircle"`, `"UsersIcon"`,
`"createLucideIcon"`, `"icons"` and accepts `"CircleAlert"`; warn fires once per bad name
in development and zero times under `NODE_ENV=production`. No existing config used a
phantom name, so nothing needed migrating. Watch-out for consumers: alias spellings in
`admin.icon` are now type errors — the canonical name is the fix.
