### Decisions made
- Narrow the type to the `icons` map rather than widen `Icon`'s runtime lookup to the
  module namespace. The map's keys are the canonical lucide.dev names; the extra module
  exports are alias spellings, `*Icon` duplicates, and non-icons (`createLucideIcon`,
  `icons`, `Icon`) that no icon-name type should offer.

  independent `keyof typeof icons` declarations is what let them silently diverge.
- `Icon` still returns `null` rather than throwing — untyped CMS data must not break a
  render — but no longer fails invisibly. The warn is behind
  `process.env.NODE_ENV !== "production"` so bundlers eliminate it.

  package has no default export, so `esModuleInterop` synthesized one from the module
  namespace and `keyof typeof icons` widened to every export. One character class
  (default vs named) cost ~4,100 phantom names that type-checked and rendered nothing.
- The two same-named types disagreeing was already known to someone: the three
  `@ts-expect-error`s in `AdminSidebar` were the symptom, annotated "unknown lsp error".

### Decisions made
- **Exact inward, ranged outward.** Peers are resolved in the *consumer's* tree, never
  from our lockfile, so pinning them buys zero security and costs every consumer a
  conflict on the next convex release. Named catalogs are what let one package name
  carry both roles.
- **Per-dep peer floors, justified individually** rather than one blanket floor:
  `react >=18.0.0` (verified no React-19-only API anywhere in `packages/*/src`),
  `next >=15.0.0` (`NextAdminPage.tsx` awaits `props.params`, so `>=14.0.0` was a false
  promise), tested floors for anything churning weekly (convex, better-auth,
  `@tanstack/react-form`, lucide-react — the last because `LucideIconName` derives from
  the `icons` map, so an older lucide silently lacks names the type promises, P-009).
- **Strict peers without the auth upgrade.** Measured 4 scenarios: it works today on
  `@convex-dev/better-auth@0.11.5` with the existing patch untouched, so decision D1
  stands. The upgrade would *not* have sufficed on its own.
- **`@convex-dev/better-auth>better-auth` allowedVersions is stale upstream metadata,
  not a real incompatibility** — 0.12.5 peers `>=1.6.11 <1.7.0`, which our 1.6.23
  satisfies. Net effect is *less* suppression than the repo-wide flag it replaces.
- **Sorting split from pinning** (step 1 vs step 3) so one diff is pure moves and the
  other pure values; combined they would be unreviewable, defeating the point.
- **Deferred, deliberately:** `@convex-dev/better-auth` → 0.12.5. Still latest after 64
  days, `#422` unfixed in both halves, PR #423 open. Convex's edge appears rolled back
  (control matrix re-run against our deployment returns 200/401 under every header), but
  the library still sends the header — keep the patch.

### Problems hit
- **Four of my own spec's acceptance criteria were wrong, found by executing them.**
  (1) Steps 1–3 demanded `git diff --exit-code pnpm-lock.yaml`, impossible when you
  remove a dep or repoint a specifier — replaced with "lockfile only shrinks, no
  `version:` pair moves". (2) Step 5's "clean re-resolve ⇒ zero version differences"
  gate was unachievable: pinning the catalog pins *direct* deps only, and ~250
  transitive packages float without the lockfile. (3) `onlyBuiltDependencies: []` was
  justified from a *pruned* `.modules.yaml` claiming zero blocked scripts; a fresh
  install blocks 7. All corrected in the spec.
- **Peer ranges duplicated a type-bearing library and broke a fresh build.** pnpm
  auto-installs an unsatisfied peer at the range's *maximum*. `packages/react` declared
  none of its 7 peers as devDeps while `packages/core` already declared all 6, so a
  from-scratch resolve produced `@tanstack/react-query` 5.101.2 **and** 5.102.8 and
  `docs#build` died on `relationship/Input.tsx:78` (`TS2322`); `convex` doubled the same
  way. Fixed by following core's existing convention — 10 devDeps across react/next/cli.
  This was added work, not in the spec.
- **`strict-peer-dependencies` in `.npmrc` is a no-op in pnpm 10.** Set there, a plain
  install printed the unmet peer and still exited 0. My earlier scenario tests had always
  passed the CLI flag too, so the `.npmrc` route was never actually exercised. Correct
  location is `strictPeerDependencies: true` in `pnpm-workspace.yaml`. Had it shipped as
  specced, strict peers would have been decorative.
- **`apps/www`'s uncatalogued `convex: ^1.44.0` was a live build break**, not hygiene:
  a lockfile-less resolve gave convex 1.44.0 + 1.45.0 and `www#build` failed with
  `TS2322: GenericQueryCtx<{ user … }> is not assignable to GenericQueryCtx<GenericDataModel>`.
  A `--frozen-lockfile` baseline built 10/10; the re-resolved tree did not.
- Turbo caches task *logs*, so my repeated non-TTY `pnpm test` runs poisoned the cache
  with colorless output and the developer's `pnpm test` replayed it. Diagnosed, not
  fixed — cache-only, resolved by any `--force` run. Note turbo's cache lives at
  `/Users/zaye/Documents/Projects/.turbo/cache`, *above* the repo and shared with
  sibling projects.
