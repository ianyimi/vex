fix(core): narrow LucideIconName to the names that actually render

`LucideIconName` accepted 5,843 strings; only 1,702 of them render. The cause is
one import in `core/src/utils.ts`: `import type icons from "lucide-react"` takes
the *default* export, and `lucide-react` has none, so `esModuleInterop`
synthesized one from the module namespace and `keyof typeof icons` widened to
every export of the package. That admitted alias spellings (`AlertCircle`, which
is `CircleAlert` re-exported), the `*Icon`-suffixed duplicates (`UsersIcon`), and
non-icons — `createLucideIcon`, `icons`, `Icon` itself. None of those are keys of
the `icons` map that the `Icon` component indexes, so roughly 4,100 names
type-checked and then rendered nothing at all.

Both packages now derive the type from the named `icons` map, which is exactly
the set `Icon` can resolve. `@vexcms/react` no longer declares its own copy — it
re-exports core's. Two independent `keyof typeof icons` declarations that
disagreed is what hid this: the three `@ts-expect-error` directives in
`AdminSidebar`, annotated "unknown lsp error", were core's wide type failing to
satisfy react's narrow one, and are now removed as unused.

`Icon` still returns `null` for an unresolved name so untyped CMS data cannot
throw mid-render, but it no longer fails invisibly: outside production it warns
once per offending name, deduped through a module-level set.

Consumers using an alias or `*Icon` spelling in `admin.icon` will now see a type
error. Use the canonical name from https://lucide.dev/icons — those values never
rendered. No config in this repo used one.
