## 2026-11-10 — 00:56 — fix(react): filter builder scroll, OR groups on top, last-row clear

**Spec:** .agent/docs/specs/2026-10-26-list-view-overhaul/spec.md
**Commit:** (pending)

### What was built
- `ListViewFilterBuilder/index.tsx`: the filter popover now scrolls with a plain native-scroll `div` instead of `ScrollSection`. Its max height is `max-h-[506px]`, sized to fit the OR button plus about 3.25 single-row OR groups. It opens with `sideOffset={8}`, so it lines up with the table frame below the toolbar.
- The OR button moved above the groups, and `handleAddGroup` now puts the new group first. Existing groups move down, so a new group always appears right under the button.
- When the builder has only one condition, its × clears it to a fresh row (`removeMode="clear"`, labelled "Clear condition") instead of removing it. The button is disabled while that row is still the untouched default. The builder never shows zero conditions while open.
- `DataTableResponsiveMenu` gains an optional `sideOffset` prop (default 4).
- Changeset `list-filter-builder-scroll-or-clear` (`@vexcms/react` patch).

### Decisions made
- Dropped `ScrollSection` (Base UI `ScrollArea`) for this popover. Its `max-height` never reached the viewport, so it drew a scrollbar that did nothing while the content spilled past the panel. Plain `overflow-y-auto` is the fix the shadcn/Base UI threads converge on.
- Smooth-scroll-to-bottom on OR was built first, then replaced at the developer's request with OR on top plus prepending. The scroll code and its jsdom `Element.scrollTo` stub were removed again.
- "Empty" for the only condition means the row is still the fresh default (first field, first op, no value). Changing only the field or op re-enables × so the row can be reset.
- Rows and groups stay keyed by index, even though new groups are now prepended. The filter inputs only hold transient open state, and nothing is open when OR is clicked. Removing a group already shifts indices the same way.

### Problems hit
- Rewriting `DataTableResponsiveMenu.tsx` by hand dropped `open`/`onOpenChange` from its props interface. The typecheck caught it and the props were restored.
- The test "removing a chip for one row keeps a different, still-open incomplete row" assumed new groups go at the end. It was updated to index 0, still checking the same behavior.
