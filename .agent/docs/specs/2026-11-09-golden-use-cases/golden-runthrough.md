### VexCMS / template bugs found (symptom + file:line)

1. **npm install of base-nextjs fails (ERESOLVE).** `better-auth@1.7.18` is pinned as a direct dep
   while `@daveyplate/better-auth-ui@3.4.0` pulls `@better-auth/passkey@latest` (1.7.20) requiring
   `better-auth@^1.7.20`. The `pnpm.overrides` pin to 1.7.18
   (`packages/create-vexcms/templates/base-nextjs/package.json:71`) is pnpm-only — npm doesn't
   read it, so `npm install` (the CLI's own "Installing dependencies with npm..." path) reliably
   fails. Worked around by always invoking via `pnpm create vexcms@alpha` per the spec's literal
   command.
2. **`scripts/create-demo-accounts.mjs` (Step 9) omits the `Origin` header.** Better Auth rejects
   a plain `fetch` POST to `/api/auth/sign-up/email` with `403 MISSING_OR_NULL_ORIGIN` because
   Node's `fetch` doesn't send an `Origin` header the way a browser does and `trustedOrigins`
   requires one. Fixed in the example's own script by adding `headers: { origin: SITE_URL }`.
3. **`convex/seed.ts`'s `process.env[author.emailEnv]` reads Convex's own env store, not
   `.env.local`.** The seed mutation runs server-side on the Convex deployment, where
   `process.env` is whatever `npx convex env set` put there — entirely separate from the Next.js
   dev server's `.env.local` the demo-accounts script reads. The spec's Step 9 text never mentions
   also running `npx convex env set DEMO_AUTHOR_A_EMAIL …` (×3) on the deployment, so `pnpm seed`
   silently skips every author-byline patch and every article (logged as `"... run demo:accounts
   first"` even after `demo:accounts` succeeded). Documented as a required extra step here, not a
   library bug, but worth a one-line mention in Step 9's own text.
4. **`CopyPublicLinkAction.tsx`'s spec-given `import { env } from "~/env.mjs"` breaks Convex
   function pushes.** `vex.config.ts` registers this client component under
   `admin.components.edit.header.actions`; Convex's function bundler traces imports from every
   `convex/*.ts` file, including the shared `vex.config.ts` the whole app re-exports, and executes
   `env.mjs`'s `createEnv()` validation at bundle-analysis time — where `NEXT_PUBLIC_*` vars are
   undefined (Convated never injects Next.js env). Every `vex dev` push failed with "Invalid
   environment variables" until the component was changed to read `window.location.origin`
   instead (no env import at all). `packages/create-vexcms/templates/base-nextjs`'s own slot
   components should avoid `~/env.mjs` for the same reason if any ever import it.
5. **`articles.listPublished`/`getBySlug`/`publishedSlugs`/author-and-category article queries as
   spec'd leak draft rows.** The spec's literal Step 10 code uses `access: { bypass: true }` with
   no status filter; `bypass` skips the whole access/versions resolution pipeline, so a
   `draft-only` row (never published) and an unpublished revision both appeared on the public
   homepage and in the sitemap. Fixed by adding an explicit `where: (q) => q.eq("vex_status",
   "published")` to every public-facing query — `@vexcms/core`'s own `find()` does not
   default-filter to published status under `access.bypass`, contrary to what the Step 10/Step 15
   (real-estate) prose implies ("anonRole already resolves... so these read through ordinary
   find/search with no bypass" — true for RBAC-gated reads, but the versions/draft-status filter is
   a separate concern `bypass` also turns off).
6. **`relationship()` fields don't auto-populate `index` metadata despite auto-creating a Convex
   index.** `indexedOwnerCheck`/`indexNameFor` (`packages/core/src/access/buildChecks.ts`,
   `indexNameFor`) reads `resource.fields[field]?.index`, which is empty unless the field
   explicitly declares `index: "by_<field>"` — even though `vex dev` already creates a `by_<field>`
   Convex index automatically for a relationship field. `readOwn(articles, "author")` in
   `access.ts` throws `"author" on "articles" leads no declared index"` at config-load time until
   `author: relationship({ ..., index: "by_author" })` is added explicitly.
7. **base-nextjs template's own `.gitignore` blocks `.env.example` from ever being committed.**
   `.env` / `.env.*` has no `!.env.example` negation, contradicting the file's own header
   ("committed to version control — never put secrets in it"). Fixed locally in the example's
   `.gitignore`.
8. **`convex/schema.ts`'s hand-written `[TABLE_SLUG_USERS]` table definition is never synced with
   fields added to the `users` collection.** `vex dev`/`vex generate` correctly regenerates
   `vex.schema.ts`'s auto-derived `user` export (adds `slug`/`bio`/`avatar` once declared on the
   `users` `defineCollection`), but `convex/schema.ts` hand-rolls its own, separate
   `[TABLE_SLUG_USERS]: defineTable({...})` for Better-Auth-specific typing and is never
   regenerated — so the byline fields Step 7 adds to `users` never reach the real deployed schema
   until `convex/schema.ts` is manually edited too. Confirmed via `pnpm typecheck` (`Doc<"user">`
   lacked `slug`/`bio`) before the manual fix.

### VexCMS bugs found (symptom + file:line)

1. **A custom mutation action (`access: { action: "<name>" }`) is silently denied for EVERY
   caller, including the true document owner, unless the mutation handler itself resolves and
   passes `auth` into `update()`/the server API call.** The spec's literal `convex/listings.ts`
   (`markSold`) never computes `auth` — `update({ ctx, collection, id, data, access: { action:
   "markSold" } })` with no `auth` key. `prepareEdit` (`packages/core/src/db/prepareEdit.ts`
   dist: `hasPermission({ user: props.auth?.user ?? null, ... })`) then resolves `user: null`,
   which `resolveRolePermissions` (`packages/core/src/access/hasPermission.ts`) falls back to
   `anonRole` for — so the custom action is checked against the **anonymous** role's rules, not
   the signed-in caller's, no matter who calls it. The built-in `collectionsApi`-registered
   `update`/`create`/etc. resolve `auth` internally; a **hand-written** custom mutation (the
   documented, spec-prescribed pattern for a custom action like `markSold`) does not, and nothing
   in the Local API guide's "per-call access overrides" section flags this. Fixed in the example by
   computing `const auth = await resolveGetAuth({ config, ctx, getAuth })` (both exported from
   `@vexcms/core/server` / the project's own `convex/vex.ts`) and passing `auth` into `update()`.
   Confirmed via a debug `console.log` inside the role's own check function that it was **never
   invoked** before the fix (proving resolution never reached the `agent` role at all), and
   invoked/correctly allowed/denied after.
2. **`demoAccounts.ts`'s agent-linking-by-email only works if the demo login email matches the
   seeded agent roster's own `email` field exactly** — not documented as a constraint anywhere in
   Step 16's prose (it reads as if any email works). Using an unrelated `@vexcms.test` email for
   `DEMO_AGENT1_EMAIL`/`DEMO_AGENT2_EMAIL` signs the account up fine but never links it to the
   seeded `agents` row (silent no-op, no error). Fixed by setting those two env vars to the exact
   emails `convex/seed.ts` hardcodes (`dana.reyes@example.com`, `marcus.webb@example.com`).
3. Real-estate's `src/auth/access.ts` needed an explicit `adminPanel: { access: true }` for both
   `broker` and `agent` roles — omitted from the spec's TODO list (unlike magazine's, which
   explicitly called it out for `editor`/`author`) but required for either role to reach `/admin`
   at all; without it both roles were redirected straight back to the public site.
4. Same `.gitignore`/`.env.example` conflict as magazine (bug 7 in that run-through) — fixed
   identically.
