# Schema Generation & Generated-vs-Hand-Written Boundaries

- `apps/test/convex/vex.schema.ts` is AUTO-GENERATED (banner: `// AUTO-GENERATED BY VEX CMS
  — DO NOT EDIT`). Regenerate with `vex dev` / `vex generate`; never hand-edit.
- `apps/test/convex/_generated/**` is Convex CLI output — never edit.
- Hand-written code lives in subdirectories: `convex/vex/media.ts` (media factories),
  `convex/auth/` (auth config + DB helpers), `convex/vex/collections.ts` (collection
  handlers), `convex/vex.ts` (factory registration).
- Config flow: `apps/test/src/vex.config.ts` `defineConfig()` composes
  `betterAuthAdapter()`, `convexFileStorage()`, and collection definitions; the CLI reads
  it and writes `vex.schema.ts` + `vex.types.ts`.
- Index naming: `by_fieldName` / `by_field1_and_field2`.
- Generated TS files include eslint-disable headers for perfectionist sort rules
  (member order follows user config, not alphabetical).
- Generated `vex.types.ts` default path is `src/vex.types.ts` (next to `vex.config.ts`),
  resolved relative to the config at runtime.
- Convex query discipline (verified from old standards): prefer `.withIndex()` over
  `.filter()` on large sets; avoid `Date.now()` inside queries (breaks caching/reactivity).
