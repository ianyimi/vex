# Preferences

Style and API patterns the developer has ratified. Append `- P-NNN (YYYY-MM-DD) rule`;
compact only via `harness pref compact`.

- P-001 (2026-08-12) Config props holding a slug string are named `<thing>Slug` (`userCollectionSlug`, `orgCollectionSlug`) — never the bare entity name; pass slugs, not config objects, when the referenced config may not exist at authoring time (auth-adapter-merged collections).
- P-002 (2026-08-12) Builder outputs that travel as values are value-level type-erased: authoring-time checking lives on the `*ConfigInput` generics, call-site inference on ONE phantom generic (`__subjects`-style); never thread authoring generics through traveling types (callback contravariance makes instantiations mutually unassignable).
- P-003 (2026-08-12) Literal unions derive from `as const` constant maps (`PERMISSION_MODES` → `PermissionMode`); reuse an existing map instead of adding a parallel one (no `ACCESS_DEFAULTS` beside `PERMISSION_MODES`), and runtime code references the constants, never inline literals.
- P-004 (2026-08-12) RBAC/permission checks run client-side by calling `hasPermission` **directly** (no server-computed permission snapshot). The `access` config reaches the client via a **direct client-bundle import** into a provider (`VexAccessProvider`), NOT the serialized RSC/config prop (which strips it); `user`/`organization` arrive as serializable props from the server layout into a context. Both are synchronous at first render (no FOUC). Shipping permission rules to the client is accepted for **advisory** UI gating — server API guards remain the enforcement point; a hidden/disabled affordance is UX, not security.
- P-005 (2026-08-12) `sanitizeConfigForClient` strips only the *serialized* boundary (functions/adapters/`access`); values that must reach the client WITH functions intact (e.g. `access` callbacks) travel by direct client-bundle module import instead — a bundler import and an RSC serialization are different boundaries, and only the latter strips.
- P-006 (2026-08-21) Per-call access overrides ride ONE grouped `access: { action?, bypass? }` param, exposed ONLY on raw server functions and `vexServerApi` output — never in a client-callable Convex `args` validator. Enforcement is single-seam: `resolveAccessCall` resolves `{ access, action, resource }` once per call, and `bypass` works by returning `access: undefined` (the documented RBAC-off path) — no second enforcement branch may exist, and every downstream guard reads the RESOLVED access, never `config.access` directly.
- P-007 (2026-08-21) The undeclared-permission posture is pinned to deny with no config knob — `defaultPermissionMode` was removed from `VexAccessConfigInput` after measuring that undeclared actions/subjects resolved to allow. An allow posture is expressed as a role-level `"*": true`: per-role and greppable, which a global default never was.
- P-008 (2026-08-21) Slug-keyed type information reaches server-function params only via `GeneratedVexTypes` registry emission (`CustomActionsBySlug` beside `IndexFieldsBySlug`/`AuthSlugs`), with permissive pre-generation fallbacks so core's unaugmented suite still compiles; post-generation exactness is pinned by app-side `*.typecheck.ts` files of pure `@ts-expect-error` assertions that `tsc` enforces on every typecheck — no test runner involved.
- P-009 (2026-08-30) A type derived from a library's exports names the exact **runtime lookup** the consumer will perform, not the module surface. `LucideIconName` came from `keyof typeof <default import>` — a namespace with 5,843 members — while `<Icon>` indexed the `icons` map's 1,702 keys; the ~4,100-name gap type-checked and rendered nothing. Derive from the same object the code indexes (`import type { icons }`), and prefer a **named** import: a default import of a package with no default export silently becomes the whole namespace under `esModuleInterop`.
- P-010 (2026-08-30) A shared type has exactly ONE declaration, in the package lowest in the dependency graph, and every other package re-exports it. `LucideIconName` was declared independently in `@vexcms/core` and `@vexcms/react`; both read `keyof typeof icons` but bound `icons` differently, so they drifted and the mismatch was papered over with `@ts-expect-error` rather than diagnosed.
- P-011 (2026-08-30) Build outputs are split by tool where one tool is bad at one job: tsup emits JS with `dts: false`, `tsc -p tsconfig.build.json --emitDeclarationOnly` emits types (ADR-005). Build-only tsconfigs set `"customConditions": []` so workspace deps resolve through published `types` rather than the `source` condition; dev configs keep `source`. A `dts: false` that is deliberate must carry a comment saying which tool owns declarations — the original said "Temporarily … CPU issue" and shipped untyped packages for months.
- P-012 (2026-08-30) Published `peerDependencies` are ranges and every floor is justified from the API surface the code actually consumes — never one blanket floor. Generous where the consumed surface is ancient and stable (`react >=18.0.0`, verified by grepping for React-19-only APIs), tested-version floors where the library churns (`convex`, `better-auth`, `@tanstack/react-form`, and `lucide-react` — whose `LucideIconName` derives from the `icons` map, so an older release silently lacks names the type promises, P-009). A ceiling is only worth writing when it encodes a real wall: `better-auth <1.7.0` exists because 1.7.x violates `@convex-dev/better-auth@0.11.5`'s peer.
- P-013 (2026-08-30) Internal `@vexcms/*` peer dependencies are `workspace:^`, never `workspace:*` — pnpm packs `workspace:*` to the *exact* version, so a consumer with any version skew gets a hard peer error. `dependencies` on siblings may stay `workspace:*` (exact is correct inward).
- P-014 (2026-08-30) Every `peerDependency` is ALSO a `catalog:` devDependency of the package that declares it. pnpm auto-installs an unsatisfied peer at the *maximum* of its range, so a peer left unpinned installs a second copy beside the catalog-pinned one, and two copies of a type-bearing library are two nominally distinct type identities. `packages/core` is the reference: 6 peers, 6 matching devDeps.
- P-015 (2026-08-30) `pnpm-workspace.yaml` is the single source of version truth and the only home for resolution/install settings. No version literal may appear in any manifest — every `dependencies`/`devDependencies` value is `catalog:` or `workspace:`, asserted by `scripts/check-packed-manifests.mjs --sweep`. Unused catalog entries are deleted, not pinned. `.npmrc` keeps only npm-generic keys (`shamefully-hoist`, `save-exact`, auth token); pnpm-specific settings there are silently ignored (AP-013).
- P-016 (2026-08-31) The commit skill produces ONE commit per run covering the entire working tree — never split a session's work into multiple commits, regardless of how many concerns the diff contains (multi-concern bodies use bold-headed paragraphs instead). The developer will introduce per-concern commit splitting only after the first official release.
- P-017 (2026-09-02) Admin readability is part of a field definition, not a later polish pass. `FormLabel` falls back to the field's *path* when `label` is absent, and `group()`/`array()` default `label` to `""` (only `defineCollection` infers one), so an unlabelled repeatable renders as `[10] - blocks[3].items[9]`. Every collection and global declares `admin.icon`; every field declares `label`; and the `group()` passed as an array's `items` carries a SINGULAR label, because it names one row (`Roadmap Item`, not `Roadmap Items`).
- P-018 (2026-09-02) Marketing/site design is expressed as seedable block field data, never bespoke per-page JSX — the whole site must stand up from an empty deployment via one idempotent `convex/seed.ts` `init`. This is what lets the same design ship twice, as `apps/www` and as the `create-vexcms` marketing template. It also bounds design: a section that cannot be represented in the 12 field types (or that requires seeded binary media, e.g. a logo cloud) is redesigned or cut, not special-cased.
- P-019 (2026-09-02) A `select` nested in a block, group or array generates a literal-union array (`("full" | "compact")[]`) exactly as it does in a collection — all three builders route through the shared `childInterfaceType()` helper. Renderers then DERIVE their unions from the generated types; a hand-written union beside a generated one is a duplicate that will drift (`RoadmapItemStatus` was the last of them).
- P-020 (2026-09-02) CI steps that build an app supply placeholder env values rather than `SKIP_ENV_VALIDATION`. `apps/test` needs env at two distinct points — the `@t3-oss/env-nextjs` parse when `next.config.ts` loads, and the Convex client during prerender — so skipping validation clears only the first and the build still dies at "Failed to collect page data". Placeholders clear both AND keep validation enabled, so a newly added required env var that nobody wired up still fails CI; the skip flag would mask exactly that. Only safe for apps that are never published or deployed (`apps/test` is in the `.changeset` ignore list), since `NEXT_PUBLIC_*` values are inlined into the bundle at build time.
