# ADR-002: Permission scopes, and binding config/auth into the server API

- Status: accepted
- Date: 2026-08-19

## Context

Two problems surfaced while implementing RBAC (spec 2026-08-12) against `apps/www`.

**1. "No `data`" is an ambiguous question.** A permission check may be a callback that inspects
the document (`update: ({ data }) => data.ownerId === user.id`). Callers who ask "may this user
update images?" *without* a document are not asking one question — they are asking one of two
opposite ones. The sidebar wants "may they update *at least one*?" (optimistic → show the
section, filter rows later). A bulk "select all" affordance wants "may they update *every*
one?" (pessimistic). Answering either silently gives the other caller a wrong answer, and
answering `false` for a forgotten `data` in an edit view produces a permanently disabled control
that reads like a misconfigured matrix — the most expensive failure mode to trace.

**2. Every server call site had to pass `config` and `auth`.** `get`/`find`/etc. only enforce
access when `config` is present (`if (args.config?.access !== undefined)`), and they read the
caller from `auth`. That yielded two silent failures: omitting `config` disabled RBAC for that
call (observed live — `convex/pages.ts` served every page unchecked), and passing `config`
without `auth` denied or threw on every check. Neither is visible at the call site.

## Decision

**Permission evaluation is scoped, with three values.** `PERMISSION_SCOPES` = `doc` / `any` /
`all`, supplied as `scope` on `hasPermission`. It only governs a callback check whose document
was not supplied; static booleans are unaffected, and any scope runs the callback normally once
`data` is given.

| `scope` | Question | Callback needing `data` resolves to |
| --- | --- | --- |
| `doc` | "for *this* document?" | throws `VexAccessError` |
| `any` | "for *at least one*?" | `true` |
| `all` (default) | "for *every* one?" | `false` |

The default is `all`: fail-closed, and it never throws, so a caller who forgets `scope` cannot
over-permit. `doc` is opt-in for edit views and row actions, where a thrown error at the
offending call site is more useful than a silently disabled button.

**`config` binds once; `auth` resolves per call.** `vexServerApi({ config, getAuth })` returns
the whole server surface (`get`/`find`/`search`/`create`/`update`/`remove`/`globals`) with both
injected, so call sites pass neither. `getAuth` is a *callback*, not a value, because `auth`
derives from `ctx` on every request while `config` is static. `skipAccess: true` is the explicit
per-call opt-out for genuinely public reads; it is implemented by passing a config whose `access`
is `undefined`, reusing the documented "RBAC not configured" path rather than adding a second
bypass mechanism.

`DataModel` is a **required** type argument on `vexServerApi`. It cannot be inferred (`getAuth`
is optional, so there is no reliable inference site), and allowing it to fall back to
`GenericDataModel` produced an unreadable `ctx` assignability error at every call site instead of
one error at the factory.

## Consequences

- Callers must choose a scope deliberately for subject-level checks. `AdminSidebar` uses `any`;
  bulk affordances should use `all`; edit views should pass `data` (or `doc`).
- The `all` default means a forgotten `scope` under-permits rather than over-permits. Accepted:
  an incorrectly hidden control is a visible bug, an incorrectly available one is not.
- Rejected: collapsing to a boolean-only `hasPermission` with no scope parameter. It cannot
  distinguish "denied" from "you asked the wrong question", and it silently removes the
  forgot-`data` diagnostic.
- Rejected: core discovering `config` implicitly via a module-level singleton set once by the
  consumer. Import-order dependent, breaks across bundles, and untestable; the one-file
  re-export of `vexServerApi(...)` costs nothing at call sites.
- Migrating a query to the bound API turns RBAC **on** for it. That broke the public site
  (anonymous visitors have no roles, and `hasPermission` denies on an empty role set) until the
  two public page reads were marked `skipAccess: true`. Any future migration of a public read
  must make the same explicit choice — which is the point.
- `access: undefined` still disables enforcement entirely. That is the deliberate escape hatch
  for projects that do not want RBAC, not a fail-open bug.
