# ADR-010: Lifecycle hooks split — `before*` in the write path, `after*` on triggers

- Status: accepted
- Date: 2026-09-12

## Context

VexCMS has no lifecycle hooks. Grep for `beforeChange`, `afterChange`,
`beforeRead`, `afterRead`, `beforeDelete`, `afterDelete` across `core/src` and
`next/src` returns nothing. They were deliberately deferred in
`2026-09-04-seo-prerendering-and-lifecycle-hooks`, whose Overview states: "The
general lifecycle-hook system is deliberately deferred; see Out of Scope."

This is the largest extensibility gap in the framework. Without hooks a user cannot
slugify a title, derive a field, sanitize input, enforce uniqueness, or fire a
webhook — and there is no workaround inside the framework. Every Payload migrant
hits it in the first hour.

The obvious implementation is `convex-helpers`' triggers, already a dependency of
`@vexcms/core` (`convex-helpers: catalog:`, pinned `0.1.120` in
`pnpm-workspace.yaml:54`). Two questions had to be answered first.

### Is it a Convex component?

No. Verified against `get-convex/convex-helpers`,
`packages/convex-helpers/server/triggers.ts:57-89`. It is a plain TypeScript
library: a `Triggers` class with `register(tableName, handler)` and a `wrapDB`
context wrapper, used as

```ts
const triggers = new Triggers<DataModel>();
export const mutation = customMutation(rawMutation, customCtx(triggers.wrapDB));
```

There is no `convex.config.ts` entry and no `app.use()`. Components such as
`@convex-dev/aggregate` and `@convex-dev/table-history` *consume* triggers but are
separate installs.

### Can triggers implement `before*` hooks?

No. A trigger fires *as part of* a write. Its handler signature is
`(ctx, change)` where `change` carries `operation: "insert" | "update" | "delete"`
plus `oldDoc`/`newDoc`. It never sees the incoming payload before it lands, so it
cannot transform it.

Veto semantics are also ambiguous. The maintainers state a throwing trigger
rethrows from the `ctx.db.*` call that caused it, while elsewhere describing the
write as committed — which does not obviously reconcile with Convex's normal
transaction rollback. Building rejection on an ambiguity is not acceptable for an
access-adjacent code path.

## Decision

Split by direction, not by library.

| Hook | Implementation | Rationale |
|---|---|---|
| `afterChange`, `afterDelete` | `convex-helpers` triggers | `change` gives operation + `oldDoc`/`newDoc` atomically in the same transaction. Exactly the right shape for cascading deletes, denormalized counters, webhooks, revalidation dispatch. |
| `beforeChange`, `beforeDelete` | The shared server write path, alongside `hasPermission` and `stampUpdatedAt` | Transforms and rejection require seeing the payload before it lands. Rejection here is unambiguous: throw, and the mutation rolls back. |

**Two hook points, not four.** One transform stage plus one validation stage
(ADR-011) subsumes Payload's `beforeValidate` / `afterValidate`. The full ladder is
not ported.

**Codegen guarantees the wrapper.** The triggers maintainers' loudest caveat —
"forget to use the wrapper and triggers silently never run; use eslint rules" — is
fatal in a hand-written Convex app and a non-issue here, because we *generate* the
mutations. Codegen emits the wrapped builder unconditionally, and a codegen test
asserts no generated mutation uses the raw builder. This is a structural advantage
over a normal Convex app and should be exploited rather than worked around.

## Consequences

- **Hooks fire on writes through the vexcms API, never "always".** Triggers do not
  run for Convex dashboard edits, `npx convex import`, or another component's
  direct writes. This is the same coverage hole `backlog.md` already records under
  "Server-side revalidation dispatch (no admin panel open)". The hook documentation
  must state the limit rather than imply a database-level guarantee.
- **Veto semantics must be probed before anyone relies on them.** Even though
  `before*` hooks do not need trigger-based rejection, someone will eventually try
  to throw from an `afterChange`. Establish empirically what happens and document
  it.
- **Recursion is breadth-first.** Triggers that write fire more triggers, queued
  BFS. Multiple triggers on one table can observe each other's intermediate
  denormalized state — the maintainers warn about exactly this. Document it.
- **`before*` hooks run after `hasPermission`.** Required, and the reason is
  subtle enough to be re-derived wrongly: field-level RBAC inspects the `changes`
  argument, so a `beforeChange` that ran first would let a slugify hook add `slug`
  to `changes` and be **denied** for a role holding `update: () => ({ title: true })`.
  This mirrors the rule `stampUpdatedAt` already follows and documents at
  `api/create/server.ts:92-94`.
- **This ships before versioning/drafts, deliberately.** An earlier plan had drafts
  land first and carry a constraint to "route draft writes through a shared write
  pipeline" so this ADR's stage could be inserted later — i.e. drafts building
  structure whose only payoff was this ADR. Inverted: hooks ship first, and
  `saveDraft`/`publish`/`unpublish` call the existing dispatcher. Nothing here is
  built speculatively for drafts, and the single insertion point never becomes
  five. Verified there is no reverse dependency — `_status`/`_version` are
  framework-owned and read-only, so they pass validation the way `updatedAt`
  already does, and "which hooks fire on a draft save" is a semantic question the
  drafts spec answers by calling this dispatcher.
- **No new dependency.** `convex-helpers` is already pinned and consumed.
