# ADR-014: Globals share the collection write pipeline and gain beforeChange/afterChange hooks

- Status: accepted
- Date: 2026-10-02

## Context

The globals system (spec 35) adopted **D21**: globals get parallel, independent mirrors of
the collection helpers (`getGlobalInputSchema` beside `getCollectionInputSchema`, and so on),
and collection helpers are never widened to accept a `GlobalConfig`. Hooks on globals were
listed out of scope there, and again in the lifecycle-hooks spec ("Hook/validate support on
`GlobalConfig`"). Both were deferrals, not rejections: `hooks/types.ts` already names a
future `globals/hooks.ts`.

The versioning-drafts spec (`2026-09-20-versioning-drafts`) changed the picture in three ways:

- `prepareEdit` (Step 5) extracted the shared write pipeline — `hasPermission → merge →
  beforeChange → diff → validate → validateFields` — for `update`, `saveDraft`, and `publish`.
  `upsertGlobal` was a third hand-rolled copy of the same pipeline, minus two pieces.
- One missing piece was a real bug: `upsertGlobal` never runs field `validate()` hooks, even
  though `FieldValidateProps` is typed to accept a global slug. A `validate` on a global
  field is silently skipped.
- Once globals need a lenient `partial` mode for drafts, `getCollectionInputSchema` and
  `getGlobalInputSchema` are the same loop over a field map. The mirror keeps two copies of
  identical code.

## Decision

**The write pipeline and its helpers are shared across resource kinds. D21 is superseded for
these pieces.**

- Field-map helpers live in `fields/utils.ts`, exported from `fields/index.ts`, so globals
  and future field-carrying features (adapters, plugins) share them:
  `getFieldsInputSchema` (replaces `getCollectionInputSchema`/`getGlobalInputSchema`),
  `getFieldsDefaultValues` (replaces `getCollectionDefaultValues`/`getGlobalDefaultValues`),
  `fieldsToFieldTypeMap` (replaces `collectionConfigToFieldTypeMap`/
  `globalConfigToFieldTypeMap`), and `validateFields`, moved from `collections/` and
  changed to take `fields` instead of a collection. Every caller in `@vexcms/core` and
  `@vexcms/react` migrates.
- `prepareEdit` takes a tagged `target: { kind: "collection"; config } | { kind: "global";
  config }` and also accepts the `create` action. The tag is a real discriminant: each
  kind's `beforeChange` names its config prop differently (`collection` / `global`), so
  telling the kinds apart by object shape would be fragile.
- `upsertGlobal` writes through `prepareEdit`, on both its non-versioned path and its
  draft-save path.

**Globals gain `beforeChange` and `afterChange`; there are no delete hooks for globals.**
A user never deletes a global. The only delete on `vex_globals` is `publish` removing a
draft row, which is internal bookkeeping and not a lifecycle event. `beforeChange` runs
inline in `prepareEdit`. `afterChange` runs through one `convex-helpers` trigger on the shared
`vex_globals` table, which dispatches by the row's `slug` and passes `flattenGlobalRow`
documents, so the hook sees the same flat shape `getGlobal` returns.

**`afterChange` fires for every row write, draft rows included, and exposes status rather than
filtering.** On a versioned resource, `newDoc.vex_status` tells a draft save from a publish,
and the hook decides what it cares about. `operation` describes the row, so a bootstrapped
draft row is `"create"`. The same rule is documented for collection `afterChange`, which
closes the "draft-aware hook semantics" item the lifecycle-hooks spec deferred to the
versioning spec.

## Consequences

- One pipeline to maintain and test. Globals gain field `validate()` and `beforeChange` for
  free on every write path that goes through `prepareEdit`.
- `beforeChange` sees user fields only, never `vex_*` columns, on every path: `prepareEdit`'s
  caller contract strips system columns from `storedDoc`.
- A global's first save now passes `data: undefined` to `hasPermission`, as collection
  `create` already does. The legacy code passed the incoming fields.
- A global's Zod failure message becomes "Validation failed" (was "Global validation
  failed").
- Hook authors on versioned resources must check `vex_status` themselves if they only care
  about published content.

## Alternatives rejected

- **Keep D21 and mirror.** Pass `fields`/`hooks`/`slug` values into `prepareEdit` so no
  helper is widened. That avoids the union, but keeps two identical schema builders and
  leaves globals without hooks, so `prepareEdit` would still branch on whether hooks exist.
- **All four hooks on globals.** `afterDelete` would fire on every publish of a versioned
  global, for an internal draft-row delete no user initiated.
- **Fire `afterChange` only for published rows.** Hides draft saves from projects that want
  to react to them; filtering in the hook is one line, while un-filtering in the framework
  is impossible.
