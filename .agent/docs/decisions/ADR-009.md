# ADR-009: Route mapping is config; cache lifetime is not

- Status: accepted
- Date: 2026-09-07

## Context

`2026-09-04-seo-prerendering-and-lifecycle-hooks` needed two things from
`vex.config.ts`: a way to learn which public paths render a given document, and
a way to set the ISR window for those paths. The spec drafted both into one
block:

```ts
revalidate: {
  mapper: ({ collection, doc }) => [...],
  revalidateSeconds: 3600,
}
```

Neither half survived contact with the platform or with a second reader.

**`revalidateSeconds` cannot work.** Next reads `export const revalidate` by
static analysis, before any module executes. Measured on Next 16.3.3: both a
member expression (`vexConfig.revalidate?.revalidateSeconds ?? false`) and a
plain imported `const` fail `next build` with *"Invalid segment configuration
export detected"*. Only an inline literal in the route file is accepted. The key
was therefore a value that no framework adapter could ever read — configuration
in appearance, dead weight in fact. Worse than absent, because it reads as
though setting it does something.

Grepping confirmed it: `revalidateSeconds` had exactly one consumer class — the
two page-level `export const revalidate` lines it could not reach.

**`revalidate` was the wrong name for the other half.** The mapper is a pure
lookup: document in, public paths out. No I/O, no framework coupling, no cache
semantics. Cache revalidation is its *first* consumer, not its definition. Three
more consumers were already visible in the roadmap and in this spec's own
follow-ups: an admin "View page" link, sitemap URL generation, and preview
links. Naming the block after one consumer forces every later one to either
import route information from a cache-named config or re-declare the mapping —
and re-declaration is exactly the duplication class the same review had just
finished removing (`VexRevalidateSnapshot` was a redundant `Partial<VexDocument>`).

Calling it `cache` was considered and rejected as actively misleading: a reader
who sees `cache` expects TTL, tags, and modes, and would find a single function —
while the real TTL sits in a route file that this config provably cannot
influence.

## Decision

**Split the two concerns, and keep only the one that is real configuration.**

1. `vex.config.ts` takes `routes: { map }`, and the route-mapping vocabulary
   (`VexRouteMapper`, `VexRoutesConfig`) lives in its own `@vexcms/core`
   module, `packages/core/src/routes/`. It is named for what it describes, not
   for a consumer, and it does not live inside `revalidate/` — a `routes` config
   inside a revalidation module would reproduce the same
   name-does-not-match-function problem one level up.

2. **Cache lifetime is not configurable.** It is an inline literal in each
   route file, where Next requires it, with a comment stating why. `VexRevalidateConfig`
   lost `revalidateSeconds`; `defineConfig` no longer defaults it.

3. `packages/core/src/revalidate/` keeps only purge machinery — `resolveTargets`,
   `VexRevalidateChange`, the wire request/response types,
   `VEX_REVALIDATE_BATCH_SIZE` — and *consumes* `routes.map`. The dependency
   points one way: revalidation needs the route map; the route map knows nothing
   about caching.

The property is `map` rather than `mapper` (developer's call): `routes.map`
reads as "the route map" at the config site.

## Consequences

**A second consumer of route mapping costs nothing.** An admin "View page"
button reads `config.routes.map(...)` directly. No cache-named import, no
duplicated mapping, no migration.

**A future `cache` key stays available and honest.** If cache policy ever
becomes configurable it gets its own block, without having to first evict a
route-mapping function from it. That is not hypothetical: `cacheComponents`
(Next 16) forbids `export const revalidate` and moves lifetime to a runtime
`cacheLife()` call, which *would* be reachable from config. When that is
adopted, `cache: { life: … }` lands beside `routes: { map }` and neither has to
move. Assessment:
`.agent/docs/research/nextjs-cache-components-and-tags.md`.

**Path-based purging remains the only invalidation mechanism** until tags land.
`routes.map` must therefore enumerate every URL that renders a document, which
holds for one-document-one-path collections and breaks for category listings,
collection-driven navs, and "related posts" widgets. Accepted knowingly; tags
are additive and require no change to `routes.map` or the purge route.

**Adapters other than Next inherit the split cleanly.** A TanStack Start adapter
gets the same `routes.map` and supplies its own lifetime mechanism, rather than
inheriting a `revalidateSeconds` shaped around Next's ISR that its own router
may not have.

**The cost is one more top-level config key** and the loss of a single place to
read "everything about caching". That trade was accepted because the alternative
put a lie in the config: a key implying control it did not have.
