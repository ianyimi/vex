# ADR-009: `@vexcms/react`'s entries share one bundle graph

- Status: accepted
- Date: 2026-09-07

## Context

`@vexcms/react` gained a second entry point, `./testing`, exporting the test kit
(`runVexReactSuite` and friends) so a consumer project can run the admin panel's
own component suite against its own config.

`docs/standards/tooling/tsup-and-exports.md` documents the array-of-configs
pattern for a package whose entries need different banners — one config's
`banner` stamps every entry it builds, and `packages/next/tsup.config.ts` uses
an array precisely so its server entries stay un-banered while the client leaf
gets `"use client"`. The test kit looks like exactly that case: it runs in a
vitest/Node process, never in a React Server Components graph, so stamping
`"use client"` on it is factually wrong.

That reasoning is correct about banners and wrong about everything else.

Two separate tsup invocations cannot share a chunk. Each one bundles its own
copy of every module it reaches, including modules whose *identity* matters.
`components/form/AppFormContext.ts` calls `createContext(null)` at module scope.
Built twice, it produces two distinct React contexts:

- a consumer importing `TextFieldInput` from `.` gets the context from
  `dist/index.js`
- the same consumer importing `AppForm`/`runVexReactSuite` from `./testing` gets
  the context from `dist/testing/index.js`

`createFieldInput` then throws `Field "…" must be rendered inside <AppForm> or
receive an explicit field prop` for every field it mounts, because the provider a
test rendered is not the provider the component reads. Measured in `apps/www`:
26 of 27 tests failed on that single cause. The test kit's entire purpose —
letting a consumer mount `@vexcms/react`'s components — was inoperative.

This is invisible inside the package. `packages/react`'s own suite imports from
`src/`, where there is one module instance and one context, so every test passes.
Only a consumer resolving through `dist` sees it.

## Decision

One tsup config, both entries, `splitting: true`:

```ts
export default defineConfig({
  entry: { index: "src/index.ts", "testing/index": "src/testing/index.ts" },
  splitting: true,
  banner: { js: '"use client";' },
  // …
});
```

Code splitting emits a shared chunk (`dist/chunk-*.js`) that both entries import,
so every shared module — contexts above all — is evaluated exactly once.

**`"use client"` is accepted on the test bundle.** It is an inert string literal
in a vitest process, and the test kit is never part of a Next module graph. A
wrong-but-ignored directive is strictly cheaper than two React contexts. This is
the trade the standards doc did not anticipate, and it inverts that doc's default
for this package: runtime correctness outranks banner hygiene.

**`entry` must stay in object form.** The array form makes `src/testing` the
common base directory and emits the testing entry as `dist/index.js`, silently
overwriting the main bundle.

## Consequences

- **Do not split these into two configs again.** The failure it reintroduces is
  silent inside the package and only reproduces from a consumer, which is the
  worst possible place to discover it. `docs/standards/tooling/tsup-and-exports.md`
  now carries a pointer here.
- **`splitting: true` made a latent circular import fatal, and that was load-bearing
  information.** `components/form/{FormArray,FormGroup,FormBlocks}.tsx` import
  `fieldToInputComponent` from `../fields`, while every `fields/*/Input.tsx` imported
  `createFieldInput` from the `../../form` barrel — a genuine cycle. Under separate
  bundles it was survivable; under shared chunks esbuild ordered it the other way,
  `fieldToInputComponent("text")` returned `undefined`, and consumer suites
  collected **zero tests**. Fixed by pointing all 14 field files at leaf modules
  (`../../form/createFieldInput`, `../../form/FormLabel`, …) instead of the barrel.
  Import paths only, no behavior change. **Barrel imports inside `fields/` must not
  come back** — the cycle is still there in the module graph, only unexercised.
- **A shared chunk is now part of the published contract.** `dist/` contains
  `chunk-*.js` files that both entry points import. `package.json#files` already
  ships all of `dist`, so nothing changes there, but any future `exports` entry
  must be built by this same config to keep sharing the chunk.
- **Adding a third entry is now cheap and correct by default** — it joins the same
  graph automatically. An entry that genuinely must *not* carry `"use client"`
  needs a real decision, not a second config: either accept the directive as this
  ADR does, or split the shared modules into a subpath both configs mark external.
- **The dual-context class of bug is only detectable from a consumer.** `apps/test`
  and `apps/www` now import the kit through the published subpath specifically so
  this is caught by the commit gate rather than by a user. Keep them wired.
