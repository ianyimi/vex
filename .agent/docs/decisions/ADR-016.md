# ADR-016: Localization — nested per-field locale maps, built into the free core

- Status: accepted
- Date: 2026-10-22
- Launch-plan item: **B2** (decision only, zero production diff)

## Context

`core/src` has no localization today. The launch plan requires the model to be decided
before 0.1.0 because the **stored shape of localized data is the only irreversible part**:
once users have data, changing it is a migration, not a config change. Launch spec G
(`2026-10-16-field-input-consistency-pass`) is about to build server-side condition
enforcement (Step 9, `data` / `siblingData`), the form renderer (Step 11, form value paths),
and stored array-item ids; launch spec I builds sort, search and saved views. All of these
read field values by path, so the shape must be fixed first.

Already shipped and constraining the design:

- **Versions & drafts** (`2026-09-20-versioning-drafts`): a two-row model (published row +
  draft row linked by `vex_publishedId`) and **whole-document snapshots** in `vex_versions`.
- **Richtext** stores `v.array(v.any())` (Plate JSON) — the largest values a document holds.
- **Search**: `collections/validator.ts` auto-generates `search_<useAsTitle>` and emits a
  `.searchIndex()` per field that declares one.
- **Field-level RBAC** keys field maps by top-level field name.

Convex constraints (docs, verified 2026-10-21): documents ≤ **1 MiB**; nesting depth ≤ 16;
**32 indexes** and **4 search indexes per table**; index and search fields may use
dot-separated nested paths (`title.en`).

Localization is a **free core feature** (decided 2026-10-17; code-first competitors ship it
free). A paid add-on may later cover translation *workflow* (AI translation, per-locale
approvals), not storage or reading.

## Decision

### 1. Built into core, not an adapter
Localization changes schema generation, type generation, validation, reads, writes and the
admin form. No existing adapter (`VexAuthAdapter`, `VexStorageAdapter`, `VexEditorAdapter`)
touches schema generation, and a pluggable storage contract would freeze an interface before
a second implementation exists. Built in.

### 2. Storage: a nested map per localized field, keyed by configured locale codes
```ts
// stored
title: { en: "Hello", fr: "Bonjour" }
```
- Schema generation emits `v.object({ <defaultLocale>: <inner>, <other>: v.optional(<inner>) })`
  with keys **generated from the configured locales** — a fixed object, not `v.record`, so
  types and nested-path indexes stay precise.
- Adding a locale adds an optional key: additive, no migration. Removing a locale leaves its
  data until cleaned up. Changing `defaultLocale` is a migration (documented).
- Inner validators are the field's existing validator unchanged (text → `v.string()`,
  richtext → `v.array(v.any())`, relationship → its id array, and so on).

### 3. Opt-in at collection and field level; the field wins
- Root config: `localization: { locales: [{ code, label }], defaultLocale, fallback }`.
- Collection (or global): `localized: true` localizes every localizable field by default.
- Field: `localized: true | false` overrides the collection default — a field saying `false`
  is not localized even when its collection says `true`.

### 4. Containers localize their whole subtree (Payload's rule)
A localized `group`, `array` or `blocks` stores one complete value per locale
(`content: { en: [...], fr: [...] }` — French can have a different block list). A child of a
localized container **may not** declare `localized` itself; doing so is a config-resolution
error naming the field path. A non-localized container may hold localized children
(`content: [{ title: { en, fr }, image }]`). Per-locale arrays carry independent stored item
ids (G's array-item id decision applies inside each locale's array).

### 5. Publishing is whole-document
One draft row and one publish covers every locale, matching the shipped two-row model;
`vex_versions` snapshots keep storing the whole document (all locales). Per-locale publish
status is **not designed**; it is believed additive later (a per-locale status map) and would
be decided in its own spec.

### 6. Reads are flattened by `locale`, with fallback
- `find` / `get` / `search` take an optional `locale` key. `locale: "fr"` returns
  `title: "Bonjour"` — the same shape as an unlocalized field, so site code stays
  locale-agnostic. Missing or empty values fall back per `localization.fallback`
  (default: the default locale; `false` disables; an ordered chain is allowed).
- `locale: "all"` returns the raw maps; the admin editor uses it.
- Omitting `locale` reads the default locale.
- **`locale` is an independent read key, like `drafts`**, and relationships populated within
  a read inherit it (see "Read-key rule" below).
- Generated types: reads return the flattened field type; `locale: "all"` returns
  `Record<LocaleCode, T>`-shaped maps (precise keys from config).
- **Storage is therefore an implementation detail behind the read API.** A future
  per-collection alternative storage (e.g. a side table, for collections outgrowing the
  1 MiB cap) can be added without changing anyone's read code — only that collection's data
  migrates.

### 7. Writes target one locale or all
- `create` / `update` take `locale`: `locale: "fr"` merges values into the `fr` key of each
  localized field (other locales untouched); `locale: "all"` accepts full maps.
- `required` is enforced for the **default locale** on a strict (publish / non-draft) write;
  other locales are optional and covered by fallback. The lenient draft mode (ADR-011) is
  unchanged.
- `beforeChange` receives the merged document with full maps plus the write's `locale`;
  field `validate()` receives the value for the locale being written. Exact prop names are
  set in the implementation spec.

### 8. Query paths, sort and conditions resolve through the read locale
- B3's `where` (builder and plain form) names fields as today (`title`); for a localized field
  it compiles to `title.<locale>` using the read's locale.
- Sorting or indexing a localized field uses per-locale indexes (`title.en`, `title.fr`).
  Each counts against the **32-indexes-per-table** limit — documented as a cost of indexing
  localized fields across many locales.
- G's `admin.condition({ data, siblingData })` receives values flattened to the locale being
  edited, so conditions are written once, locale-agnostic.

### 9. Search on localized fields does not use per-table search indexes
Convex allows **4 search indexes per table**, so one search index per locale per searchable
field breaks at five locales. Localized searchable fields (including a localized
`useAsTitle`) are instead indexed in **one framework table** (`vex_`-prefixed, e.g.
`vex_search`) with a single search index and filter fields for collection and locale,
maintained by the write pipeline. Non-localized fields keep today's per-table search indexes.
Table and column names are set in the implementation spec.

### 10. Permissions, preview and admin
- Field-level RBAC maps stay keyed by field name; a permission applies to every locale.
  Per-locale permissions belong to the possible paid translation-workflow add-on.
- Live preview overlays the locale being edited; preview URL resolvers receive the locale.
- The admin edits one locale at a time with a locale switcher (a built-in contribution in
  H's `edit.header` slots once localization is implemented) and shows the fallback value as a
  placeholder for empty translations.

### Read-key rule (applies beyond localization)
Read options are **independent top-level keys**, not a grouped object: `drafts`, `locale`,
and later `branch`, `variant`, `asOf`. Each key is meaningful on its own and any combination
is valid (e.g. `drafts: false, branch: "spring"` = the published state of that branch).
Relationships populated within a read inherit every read key. No `perspective` object.
Decided 2026-10-21 (`post-v0.1.0-plan.md` § Cross-feature seams).

## Consequences

- **Zero production diff now.** Implementation is its own spec, post-0.1.0 (Track FR,
  free core).
- G, H and I need no localization code, but must not hard-code assumptions the model breaks:
  form values and conditions go through field paths (not raw top-level keys), and I's
  sort/search must be index-driven so per-locale indexes and the `vex_search` table can be
  slotted in.
- Documents grow roughly linearly with locale count for localized fields; large rich-text
  pages in many locales approach the 1 MiB cap. Documented, with alternative storage as the
  escape hatch (decision 6).
- Indexing localized fields multiplies indexes by locale count (32 per table).
- Payload migrations map directly: Payload's MongoDB storage uses the same per-field locale
  map.

## Rejected alternatives

| Alternative | Why rejected |
|---|---|
| **Row per locale** (Strapi v5) | Relationships must target a locale group, shared fields duplicate or split into a base row, uniqueness becomes per-locale, and rows multiply with the two-row drafts model (locale × draft/published). Per-locale publishing is its only strong advantage, and it was not chosen (decision 5) |
| **Side table for localized fields** (Payload on Postgres) | An extra read per document and no single-query filter across main-row and localized fields. Kept as a possible future per-collection storage, made non-breaking by flattened reads |
| **Locale array per field** (`[{ locale, value }]`, Sanity plugin) | No precise nested-path indexing; sort and search by locale become array scans |
| **Sibling columns** (`title_en`, `title_fr`) | Every locale changes the field list, permissions, form and types; generated schema explodes |
| **`v.record(string, T)` maps** | Loses precise keys in validators and types; fixed generated keys cost nothing since locales come from config |
| **Collection-level-only opt-in** | Can't keep slugs, prices or images shared within a localized collection |
| **Per-locale publish** | Requires per-locale status on every versioned row and per-locale history — a large change to the shipped drafts system for a need not yet requested |
| **A `perspective` read object** | Read options are unrelated; grouping them forces nested typing for a single setting |
| **Paid localization package** | Payload, Strapi Community and Sanity ship localization free; charging would put Vex behind its migration source |
