# ADR-012: Live preview is driven by unsaved form state, not by saved documents

- Status: accepted
- Date: 2026-09-12

## Context

Live preview is unshipped. `livePreview: { url }` is accepted on collection and
global admin config and stored on the resolved config, but there is no preview
panel and no rendering integration — the field exists purely so that adding the
feature later is non-breaking (`core/README.md:192-197`).

Sequencing changed twice while planning the 0.1.0 track: live preview was
originally slated before versioning/drafts so that save and autosave behavior could
be observed against a preview window, then moved to after drafts. Either ordering
raises the same question, which is what the preview actually reads.

Two transports are possible.

**Saved-document preview** is nearly free today. The admin already runs on Convex
live queries (`react/src/hooks/useLiveFieldMerge.ts`), and the marketing template's
`PageContent.tsx` is a client component with a live `useQuery`. Pointing an iframe
at the public route produces a preview that updates on save with essentially no new
code.

**Form-state preview** transports the editor's unsaved values to the preview
surface, so the preview reflects keystrokes that have not been written.

The decisive observation is about autosave. Autosave does not exist — `autosave`
appears nowhere in `packages/` except roadmap marketing copy
(`blocks/Roadmap/config.ts:92`, `convex/seed.ts:710`) — and it belongs to the
versioning/drafts feature. Critically, **autosave without drafts writes the live
published document on every keystroke**, which would also fire the path-based
revalidation added in `2026-09-04-seo-prerendering-and-lifecycle-hooks`. So
"verify autosave updates the preview" is not a coherent goal before drafts exist,
under either transport.

## Decision

Drive the preview from **unsaved form state**, over `postMessage`, layered on top
of the consumer's own query result.

Saved-document reactivity is retained as the baseline — the preview surface is a
normal query-backed route, so a save or a publish is reflected the same way any
other client sees it. Form state shadows that result; it does not replace it.

### Transport: `postMessage`, not `localStorage`

`localStorage` was considered and rejected as the primary transport. One reason is
decisive: **`livePreview.url` is user-configured and may be a different origin**
(a staging deployment, a separate marketing domain). `localStorage` is partitioned
by origin, so a cross-origin preview can never read the admin's store — and a
cross-origin iframe gets partitioned storage in current browsers regardless. A
`postMessage` transport handles same-origin and cross-origin identically, so it
has to exist anyway; once it does, `localStorage` adds cost without adding
capability.

The secondary reasons are all real:

- **Synchronous, main-thread, disk-backed.** Serializing a full `blocks` or
  richtext document to JSON on every keystroke is a genuine jank source. It would
  need throttling and a size guard that `postMessage`'s structured clone does not.
- **~5 MB per-origin quota**, shared with everything else on the origin.
- **It persists.** Stale preview state outlives the editing session and needs
  explicit cleanup.
- **Reading it can throw.** `ui/ThemeProvider.tsx:36-56` already documents this
  for this codebase: Safari private mode and any "block all cookies" setting make
  the property access itself raise `SecurityError`, and a jsdom or worker
  environment can expose the global with no backing store. Any `localStorage` use
  here would have to replicate `readStoredTheme`'s guarded pattern.
- **Any script on the origin can read and write it**, persistently. A
  `postMessage` is auditable per message and arrives with an origin attached.

The one thing `localStorage` uniquely offered — surviving a preview reload before
the next keystroke — is solved better by a **handshake**: on mount the preview
announces which document it renders, and the admin replies with current values.
That removes the need for any persistence layer.

`BroadcastChannel` remains available as an optional addition for driving several
same-origin previews without holding a window handle. It is not required: both
an iframe (`contentWindow`) and a popped-out tab (`window.open`) give a handle
that `postMessage` can target.

### Shape: overlay the consumer's result; do not own the query layer

A `useVexQuery` wrapper around TanStack Query was considered and rejected. The
preview does not need to control fetching — it needs to **shadow the result**.
Wrapping the query layer would force every consumer onto one fetching library and
would commit us permanently to re-exposing TanStack's full option surface, for one
feature's benefit.

Instead the provider holds an **`id → unsaved values` map**, and a hook overlays
whatever the consumer already fetched:

```tsx
const { data: pages } = useQuery({ ...convexQuery(api.pages.getBySlug, { slug }), initialData })
const page = useVexPreview(pages?.[0])
```

This is agnostic to how the document arrived — TanStack Query plus `convexQuery`
as the marketing template does today (`apps/www/.../PageContent.tsx:31-34`), a raw
Convex `useQuery`, or an RSC-passed `initialData`.

An `id → values` map rather than "the one document under edit" is the load-bearing
choice: it solves nesting for free. A page rendering a `relationship` to an author,
while the author is the document being edited, overlays correctly because each
render site resolves its own document by id.

**A `useVexQuery` convenience may still ship, as sugar over this primitive rather
than as the mechanism.** Once `useVexPreview` exists, a thin
`useVexQuery = useQuery + useVexPreview` composed helper is a few lines and gives
consumers the transparent call they would reasonably want. What is rejected is
making the wrapper the *only* path: that is what forces a fetching library, owns
an option surface we would have to maintain forever, strands RSC `initialData`
consumers, and fails to compose at nested render sites. Sugar over a primitive has
none of those properties, so build the primitive first and add the helper if the
ergonomics warrant it.

### Matching: on `doc._id`, with no key convention

The admin knows `(collection slug, document id)`. The preview route fetches by
slug and does not know the id up front — but the fetched document carries `_id`,
so `useVexPreview(doc)` matches on that. No storage-key scheme, no URL contract,
no configuration.

`livePreview.url` may additionally carry `?vexPreview=<id>`. It is not needed for
this spec and should not be relied on now; it is what versioning/drafts will use
to fetch the draft as the base layer.

Two cases `_id` alone does not cover, both resolved in the same handshake payload:

- **A document being created has no `_id`.** Preview-while-creating matches on a
  client-generated temporary id carried in the preview URL, alongside the
  collection slug.
- **Merging is not a shallow spread.** `{ ...doc, ...values }` destroys nested
  `group` and `blocks` values whenever the form holds a partial subtree. The merge
  must walk the field config, which is the same problem `useLiveFieldMerge` already
  solves in the opposite direction (server values into form state) — extract the
  shared logic rather than writing a second merge.

### There is no preview route; the preview target is the real route

A single application-wide `/preview` route that receives a path plus the live data
and renders the corresponding page was considered and rejected.

Next's App Router has no `renderRoute(path, data)` primitive — routes are
filesystem-bound. Making one route render any page requires a
`/preview/[...path]` catch-all that re-implements the application's own routing
and dispatches to shared page components. Two costs follow, both borne by the
*user's* app rather than the framework: every previewable page must be refactored
into a data-injectable component, and the preview then renders through a different
code path than production, so it can silently drift from what ships.

Instead, `livePreview` resolves a document to its **real** URL, the admin frames
that URL, and the real route picks the overlay up through `useVexPreview`. The
preview is pixel-identical to production because it *is* production, and no new
route exists to secure.

A dedicated route earns its place only for documents with no public URL at all.
Deferred until something needs it.

**The path resolver depends on the config-split spec, which supersedes an earlier
constraint recorded here.** As the config stands, `sanitizeConfigForClient` strips
every function before it reaches the browser — `fields/relationship/preview.tsx:11-16`
relies on exactly that, and `config/sanitizeConfig.test.ts:93-102` demonstrates a
`livePreview.url` resolver arriving as `null`. Since the admin is client-side, a
`url: (doc) => string` would be dead, which forced a serializable interpolating
template (`"/blog/:slug"`).

A separate spec now splits the config into client and server entry points imported
per runtime, so authored functions survive to the client. That is the better fix
and it lands before this spec, so `livePreview.url` **is** a function here. Two
consequences worth noting:

- It buys paths interpolation cannot express — locale prefixes, nested category
  segments, conditional routes.
- **Live preview is not the only beneficiary.** `resolveRelationshipPreview`'s
  docstring (`fields/relationship/preview.tsx:11-16`) states that a
  collection-level `admin.components.preview` "could never resolve to a real
  component in the browser" for precisely this reason. The config split removes
  that limitation too, so the relationship field gains a capability its own code
  currently documents as impossible.

If the config split slips, fall back to the interpolating template — the overlay
architecture is unaffected either way.

**`livePreview` currently exists only on globals.** `globals/types.ts:36` and
`:63` declare `livePreview?: { url: string }`; `collections/types.ts`'
`AdminCollectionConfigInput` declares nothing. `core/README.md:192-197` claims it
is "accepted on collection/global admin config", which is half false. Adding the
collection-side config is part of this spec's work, not a pre-existing surface it
inherits.

### Lifecycle hooks do not run on preview data

Running F's `beforeChange` hooks over the form state before handing it to the
preview — so a derived `slug` or `readingTime` appears live — was considered and
rejected for this spec. Three reasons:

1. **`beforeChange` is not contractually pure.** It is server code receiving a
   mutation `ctx` (ADR-010), so a hook may legitimately write another document or
   call an external service. Nothing distinguishes a pure transform from a
   side-effecting one statically, so running arbitrary `beforeChange` on every
   keystroke could fire webhooks or insert rows per character typed.
2. **It would require a server round trip per keystroke**, destroying the local
   -overlay latency that is the entire point of this ADR.
3. **Doing it properly means a new hook class**, not a new call site — a
   contractually pure `derive` hook, distinct from `beforeChange`. That is scope
   creep on F.

The forward path, if preview fidelity for derived fields is ever wanted: add a
pure `derive` hook class. Because it is pure by contract it can run **client-side**
against form state, so preview becomes its second consumer with no server call at
all. Until then the limitation stands and must be documented: the preview renders
what the editor typed, not what would be persisted.

## Consequences

- **The transport is drafts-independent.** It works identically before and after
  spec C, so live preview is not blocked on versioning/drafts and does not have to
  be rebuilt when drafts land.
- **Autosave becomes a durability feature, not the preview mechanism.** When drafts
  ship, autosave persists a draft; the preview is already ahead of it. Had the
  preview been built on saved-document polling, autosave would have been load-
  bearing for preview latency and the transport would have needed replacing.
- **It delivers the per-keystroke loop, which is the actual product value.** The
  saved-document half was always nearly free; paying for it alone would have been
  building the cheap half of the feature.
- **The preview route is public, so preview mode must be gated, not always-on.**
  This is the sharpest risk in the design. The preview surface is the customer's
  live marketing site. A route that unconditionally listens for `postMessage` and
  renders the payload lets anyone iframe it and inject arbitrary content —
  content spoofing today, and outright XSS on the customer's own domain once
  richtext renders markup. Four mitigations, all required:
  1. **Origin allowlist**, explicitly configured rather than inferred. Reject any
     message whose `event.origin` is not listed.
  2. **Opt in per request.** Preview mode activates on an explicit signal plus a
     real check — in the default scaffold the admin is same-site and
     authenticated, so the route can verify the session cookie rather than share
     a secret.
  3. **Validate the payload against the field schema before rendering.** The
     generated Zod schemas (`adminFieldToInputSchema`) exist for exactly this.
  4. **Richtext renders through the sanitizing renderer**, never raw payload HTML.
- **Preview must honor RBAC.** Form state originates client-side, so the preview
  cannot be treated as trusted merely because it renders in the admin. A field the
  role cannot read must not reach the preview surface — field-level RBAC already
  strips denied read fields server-side (`api/get/server.ts:57-90`) and the form
  never holds them, so the correct behavior falls out of not re-fetching. Do not
  add a privileged read path for the preview.
- **Per-editor preview state is strictly better under concurrent editing, and this
  is an independent argument for the decision.** An autosave-to-shared-draft design
  gives every editor of a document one shared preview state — which is the
  last-write-wins problem `backlog.md`'s "Concurrent-edit conflict-resolution UX"
  entry describes, surfacing in the preview as well as in the form. Reading each
  editor's own unsaved state means two people editing one document each see their
  own changes, and live preview stops being blocked on the concurrency design.
- **The preview shows pre-hook state, and that is inherent.** A `beforeChange` hook
  deriving `slug` from `title` (ADR-010) runs server-side with `ctx`, so it cannot
  run against client form state. The preview therefore renders what the editor
  typed, not what would be persisted. Document the limitation; no ordering or
  transport choice fixes it.
- **Blocks are the hard case.** A `blocks` field's preview must re-render on
  reorder and on per-block field edits, not only on top-level field changes.
  Additionally, `backlog.md` records that `CodePane` in `apps/www` is an async
  Server Component reached from a client subtree; pre-highlighting decisions there
  interact with how live a block preview can be.
