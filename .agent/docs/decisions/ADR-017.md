# ADR-017: `@vexcms/react` and `@vexcms/core` ship one dist file per source module, split by reach

- Status: accepted
- Date: 2026-11-08
- Supersedes: ADR-009

## Context

`apps/www` loaded about 3.0 MB of JavaScript on every route — 1.1 MB admin UI, 671 KB
TanStack Table, 505 KB of lucide icons, 338 KB auth UI — and CI Lighthouse TBT ran
277–570 ms against a 200 ms budget. A visitor never opens the admin panel, never sees a
data table, and sees at most a handful of icons, so almost none of that was reachable
code for them. The same cost hit any consumer who imported one hook.

Shipped against `apps/test` and `apps/www` production bundles (2026-11-08):

| App | `/` before | `/` after | `/auth/sign-in` after |
|---|---|---|---|
| `apps/test` | 3346.1 KB | 1777.9 KB (budget 1956) | 2082.6 KB (budget 2291) |
| `apps/www` | 3198.4 KB | 1805.8 KB (budget 1987) | 2116.4 KB (budget 2329) |

Local Lighthouse after the server-import split alone moved TBT from ~195 to ~110 ms; the
full CI numbers land after the push.

The package import-cost gate measured per fixture against the built `dist`:

| Fixture | Before | After | Budget |
|---|---|---|---|
| `cn`-only | 2,316,220 B | 26,548 B | 29,203 |
| `useLivePreviewQuery`-only | 2,317,216 B | 14,544 B | 15,999 |
| root reach (`export *`) | — | ~1.49 MB, 0 deny hits | deny only |

Two findings explain the shape of the fix:

**Client imports already tree-shake once dist is per-module.** With one `.js` file per
source module (no shared chunk, no `splitting`), a bundler that resolves a client import
only pulls the modules on that import's reachability graph.

**Server imports don't, no matter what the dist layout is.** A **server** component
importing anything — `cn`, one hook — from a barrel makes Next register every
`"use client"` module that barrel can statically reach as a client reference, and every
one of them ships to the browser, even ones the server component's own render never
touches. This is a property of how Turbopack/webpack build the client reference manifest
from a barrel's module graph, not of tree-shaking: tree-shaking removes code a bundler can
prove is unreachable from *executed* paths, and "this module might be read by a client
component somewhere under this server component" is not something shaking can disprove
for a module already marked `"use client"`. Tested and ruled out: `optimizePackageImports`
(a Next-side heuristic the Server-Components graph doesn't run), a pure re-export barrel
with no `"use client"` of its own, and `sideEffects` — none change which modules get
registered once a server component's import statement reaches them.

The fix that actually drops TanStack Table from `/` replaces every server-side barrel
import (`layout.tsx`, `providers/server.tsx`, `unauthorized/page.tsx`) with an import
through a small local `"use client"` re-export file naming only the symbols that
component needs. That is the entry-split principle generalized: **the root export surface
IS what every server component that imports anything from it pays**, independent of what
that component actually renders.

The heavy exports (`adapter`, `fields/registry`, every collection/global/media view,
`AdminLayout*`, `data-table/**`, `dnd/**`) are the admin panel. Nothing in a public page
imports them. Everything else — core re-exports, field types, config/access/auth hooks,
the live-preview context (not the panel), `cn`, `Icon`, UI primitives — is what a public
page or a config file actually touches.

## Decision

### 1. Per-module dist, not a shared chunk
`scripts/preserveModulesPlugin.mjs` gives both packages `entry: listModuleEntries({ srcDir:
"src" })`, `bundle: true`, `splitting: false`: one source module compiles to exactly one
`.js` output, mirroring `src/`, with relative imports rewritten to point at sibling output
files (directory imports → `.../index.js`). The plugin skips relative imports inside
`node_modules`. A consumer's bundler sees the same module graph tsup saw and can shake it
per module. `@vexcms/core` ends up with 287 output files, `@vexcms/react` with about 435.

This also resolves the problem ADR-009 solved with a shared chunk — `@vexcms/react`'s `.`
and `./testing` entries both reach `components/form/AppFormContext.ts`, whose module-scope
`createContext(null)` must be evaluated exactly once. Splitting produced a shared chunk
both entries imported; preserve-modules reaches the same guarantee a different way — the
module compiles to one output file regardless of how many entry barrels reference it, so
both entries resolve it through a relative import to that one file, not through a chunk
boundary. `entry` lists every module (`listModuleEntries` walks `src/`, not an array of
barrels), so the one-instance property holds for every shared module, not just the ones an
ADR happens to call out.

### 2. Per-module `"use client"`, not a barrel banner
The root barrel stops being the client boundary. Every module that needs the directive
(`.tsx` outside `src/server/**`, `use*.ts` hooks, anything calling `createContext`) carries
its own `"use client"`, enforced by `packages/react/src/clientDirective.test.ts`. A server
component can then import `cn` or a hook from the root without tripping "you're importing
a module that depends on useState into a Server Component" — only the modules it actually
imports become client references, not everything the barrel could reach.

### 3. Root vs `/admin`, split by reach
The root (`@vexcms/react`, `@vexcms/react/form`) exports only what a public page or a
config file touches: core re-exports, field/config/access/auth types and hooks, the
live-preview context, `cn`, `Icon`, UI primitives (named re-exports only — no
data-table/dnd/sidebar/resizable at the root). `@vexcms/react/admin` exports the panel:
the adapter, the field registry, every `*FieldAdmin`/`*FieldCell`, slots, the document-edit
runtime, admin layout and views, `data-table/**`, `dnd/**`, the live-preview panel.
`useAppForm`/`AppForm` live only at `/form`, never at the root. `ReactHKT`/
`ReactAdapter` types stay importable from the root (and from `/admin`) since root field
types reference them. No deep subpaths beyond these two plus `./form`, `./client`,
`./server`, `./testing` — a consumer reaches package internals only through a named entry,
never a file path.

`@vexcms/core` ships the same way (per-module dist; it has no `"use client"` modules and no
admin/root split — its entries are already `.`/`./server`/`./internal` by server/client
concern, unchanged by this ADR).

### 4. The root `Icon` is lazy everywhere, including `/admin`
The root `Icon` resolves a name through `lucide-react/dynamic.mjs`'s on-demand import
instead of statically importing all 1703 of lucide-react's icon components. `lucide-react`
at the version this repo pins (`0.577.0`) ships **no `package.json` "exports" map** (fixed
only in 1.x) — the extensionless specifier `lucide-react/dynamic` resolves fine for TYPES
under TypeScript's "bundler" resolution but fails at runtime in Node and real consumer
bundlers (`ERR_MODULE_NOT_FOUND`); only the exact on-disk file, `lucide-react/dynamic.mjs`,
resolves everywhere. `Icon.tsx` imports the runtime value from the `.mjs` path and keeps
the real types via a separate type-only import from the extensionless path, documented
inline. `isIconName` is exported from the root for callers holding untyped data (CMS
content, a block field). The admin panel renders `Icon` too — its sidebar, collection/global
icons, field previews, and menu-item icons all load on demand into the same reserved box,
so there is no separate eager admin icon component to keep in sync with the lazy one.
`ui/button.tsx` and `ui/input.tsx` use the same `Icon` for their `icon` props. Blocks driven by
CMS-supplied icon names — Features, HowItWorks, Footer, Split, in `apps/www`, `apps/test`
and the `marketing-site` create-vexcms template — switched from a static `icons[name]`
lookup to `Icon` + `isIconName`. `SessionButton`'s sign-out icon stays a static
`import { LogOut } from "lucide-react"` since it is the same icon on every render.

### 5. The gates
Three gates hold the reach promise, because none of Next's own options can be trusted to
(see "why barrel imports ship everything" above):

- **Package import-cost gate** (`scripts/check-import-cost.mjs`, CI step "Check Import
  Cost"): bundles a handful of single-symbol fixtures against the built `dist` with
  esbuild — the same tree-shaking question a consumer's bundler asks — and fails if a
  fixture's bundle includes a deny-listed admin module or exceeds its recorded byte
  budget. The deny check only counts esbuild metafile inputs with `bytesInOutput > 0` —
  a module esbuild merely resolved but shook entirely out of the output does not count as
  a hit, so the check reflects what actually ships, not what the resolver merely touched.
  Deterministic, Next-free, catches a regression in the package itself.
- **Site bundle gate** (`scripts/check-site-bundle.mjs`, CI step "Site Bundle Budget",
  `apps/test`; `apps/www` runnable locally): runs Next's own analyzer against a real app
  and fails if a route's initial client JS includes a deny-listed module, exceeds its
  budget, or ships more than `MAX_STATIC_LUCIDE_ICONS = 200` lucide icon modules — the
  measured legitimate maximum across the sites' static imports (shadcn UI primitives,
  `@daveyplate/better-auth-ui`) is 44 on `apps/www`'s `/auth/sign-in`, far below the full
  1703-icon set an `icons[name]` lookup would reach, so 200 catches that regression class
  without false-positiving on ordinary static icon usage. Catches a regression anywhere in
  the app graph the package gate cannot see — a provider, a config component, a block —
  because it measures what Next actually decided to ship, not what esbuild could
  theoretically shake.
- **Lighthouse** (CI `quality` workflow): the user-facing proof. It hard-gates only what
  is deterministic on a shared runner: accessibility, best-practices, CLS and (off
  previews) SEO. Performance, TBT and LCP warn at the real targets (0.9 / 200 ms /
  2500 ms) and are listed per route in the job summary. They are simulated from a trace
  on whatever GitHub runner the job lands on, and they swung several-fold between runners
  for the same code: TBT on `/features` measured 295 ms on one run and 990 ms on the next.
  An attempt to calibrate CPU throttling to each runner's benchmarkIndex amplified that
  variance instead of removing it, and was dropped. JavaScript weight, the cause this
  decision targets, is hard-gated deterministically by the site bundle gate above. Today's
  site pages miss the timing targets on hydration cost (backlog.md § Hydration cost on site
  pages).

## Consequences

- **File layout stays internal.** Per-module dist is an implementation detail of how
  tree-shaking works, not a public contract — `package.json#exports` still only maps `.`,
  `./admin`, `./form`, `./client`, `./server`, `./testing` (and core's `.`, `./server`,
  `./internal`). **There are no deep imports.** A consumer writing
  `import { X } from "@vexcms/react/dist/fields/text/Input"` was never supported and still
  is not; the per-module dist tree can be rearranged freely as long as the named entries'
  export sets don't change.
- **A consumer pays for what they import, not for the package.** A client component
  importing one hook from the root reaches only that hook's module graph. A server
  component importing from the root pays for the root's whole reach — every field/config/
  access/auth/UI module, not the admin panel — which the import-cost and site-bundle gates
  keep true by construction rather than by review.
- **ADR-009's shared-chunk exception no longer applies.** `docs/standards/tooling/
  tsup-and-exports.md`'s array-of-configs default is unaffected by this ADR; the per-module
  single-config pattern replaces ADR-009's single-config-with-`splitting:true` exception for
  packages whose entries share stateful modules.
- **Adding a new admin-only export is cheap and safe by default** — it goes in
  `src/adminEntry.ts`, and the root-reach import-cost fixture catches it immediately if it
  is added to `src/index.ts` instead. Adding a new root export that happens to deep-import
  something admin-heavy (a field type reaching `dnd` through `ArrayField`, for instance) is
  caught the same way, which is why the app form's surface is `@vexcms/react/form` rather
  than root-exported `AppForm`/`useAppForm` — the root must not reach `dnd` through a field
  that uses it.
- **`lucide-react` stays pinned below 1.x's exports-map fix.** Every runtime import of
  `lucide-react/dynamic` must go through the exact `.mjs` file path, not the extensionless
  specifier; `Icon.tsx` documents this so an upgrade attempt re-checks it rather than
  reintroducing a works-in-dev, breaks-in-build import.
