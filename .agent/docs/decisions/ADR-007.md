# ADR-007: Gate changesets' peer-dependent major cascade on actual range exit

- Status: accepted
- Date: 2026-08-31

## Context

The WP-1 version rehearsal (`changeset version` in alpha pre mode) produced
`1.0.0-alpha.2` for all 8 publishable packages although no changeset declares a
`major` bump — every pending changeset is `minor` or `patch`, and the developer
had explicitly chosen the `0.1.0-alpha.x` line.

Read from `@changesets/assemble-release-plan@6.0.10` source: by default,
changesets escalates any package to a **major** release whenever one of its
`peerDependencies` receives *any* bump (`shouldBumpMajor`). `@vexcms/core` is a
peer of `react`, `next`, and the other adapters, so core's minor bump escalated
each dependent to major, and the `fixed` group then propagated major back to
all 8 — including core itself. The same mechanism explains why
`changeset status` reported "bumped at major" with no major changeset on disk.

## Decision

Set in `.changeset/config.json`:

```json
"___experimentalUnsafeOptions_WILL_CHANGE_IN_PATCH": {
  "onlyUpdatePeerDependentsWhenOutOfRange": true
}
```

Peer dependents now bump only when the released version actually leaves the
declared peer range. Since WP-A publishes `@vexcms/core` peers as
`workspace:^` (a compatible range), lockstep in-range releases no longer
trigger the cascade.

## Consequences

- Rehearsal now yields `0.1.0-alpha.2` across the fixed group; `changeset
  status` honestly reports minor.
- The fixed group already keeps all 8 versions in lockstep, so the cascade's
  original purpose (keeping peer dependents installable together) is preserved
  by construction.
- The option lives under changesets' experimental namespace
  (`WILL_CHANGE_IN_PATCH`): a changesets upgrade may rename it. The Step 1
  version rehearsal in the WP-1 spec is the canary — re-run it after any
  `@changesets/*` bump.
