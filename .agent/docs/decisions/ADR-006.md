# ADR-006: Exact inward, ranged outward — pnpm named catalogs as the dependency policy

- Status: accepted
- Date: 2026-08-30

## Context

Two opposite defects coexisted, both traceable to one cause: a single `catalog:`
entry was serving two incompatible roles.

**Inward, nothing was bound.** 69 of 88 catalog entries were ranges, and four more
version specs bypassed the catalog entirely (`react-dropzone`, `apps/www`'s `convex`,
`turbo`, `@changesets/cli`). Only `pnpm-lock.yaml` held anything in place, so any event
forcing re-resolution — a deleted lockfile, `pnpm update`, a dependency bot, adding any
package — moved versions with nobody approving a diff. Measured: one lockfile-less
resolve moved **21 of 82** catalog entries. `turbo: ^2.8.10` had already silently
drifted to 2.10.4. The acute case was `better-auth: ^1.5.0`, which resolves to **1.7.2**
and violates `@convex-dev/better-auth@0.11.5`'s `<1.7.0` peer; with
`strict-peer-dependencies=false` that installs silently and fails at runtime.

**Outward, everything was over-bound.** Because `peerDependencies` also said `catalog:`,
and catalog entries are substituted at pack time, the published manifest of
`@vexcms/core` read `"convex": "1.44.0"`, `"lucide-react": "0.577.0"`,
`"@tanstack/react-table": "8.21.3"` — **exact peers**. Convex ships roughly fortnightly
(1.45.0 landed 2026-08-21), so any consumer on a current convex got a peer conflict on
`npm i @vexcms/core@alpha`. Verified: an `npm i` probe against those peers fails with
`npm ERESOLVE`. `@vexcms/core` was additionally a `peerDependency` of three sibling
packages as `workspace:*`, which packs to the exact `0.1.0-alpha.1`.

Pinning direct dependencies also does nothing for the transitive closure — pinning
`nanoid: 5.1.16` says nothing about nanoid's own tree — which is where the 2025 npm
compromises (chalk/debug, the shai-hulud worm) actually propagated.

## Decision

**Exact inward, ranged outward**, expressed with pnpm named catalogs (pnpm 10.30.2) so
one package name can carry two specs for its two roles:

- Default `catalog:` — **exact**, consumed by `dependencies`/`devDependencies`. 85
  entries, sorted, no ranges.
- `catalogs.peers` — **ranges**, consumed only by `peerDependencies`. 12 entries.

Peer ranges are set **per dependency from what the code actually uses**, never by a
blanket floor. Generous where the consumed surface is ancient and stable
(`react >=18.0.0` — no React-19-only API exists anywhere in `packages/*/src`); tested
floors where the library churns (`convex >=1.44.0 <2`, `better-auth >=1.6.23 <1.7.0`
where the ceiling is load-bearing, `lucide-react >=0.577.0 <1` because
`LucideIconName` derives from the `icons` map and icons are only ever added, per P-009).
`next` was corrected `>=14.0.0` → `>=15.0.0`: `NextAdminPage.tsx` awaits `props.params`,
which Next 14 types as a plain object, so the old floor was a false promise.

`@vexcms/core` peers as `workspace:^`, not `workspace:*`.

**Every peer must ALSO be a `catalog:` devDependency of the package declaring it.** This
is load-bearing, not bookkeeping — see Consequences.

Blast radius is covered separately from intent: `minimumReleaseAge: 4320` (72h) with
`minimumReleaseAgeExclude: ["@vexcms/*"]`, and `onlyBuiltDependencies: []` as an
explicit, greppable statement that no dependency may run install-time scripts.

`strict-peer-dependencies=false` is replaced by `strictPeerDependencies: true` plus three
narrow, commented `allowedVersions` entries — strictly *less* suppression than the
repo-wide flag, because any new mismatch now fails loudly.

The invariants are enforced by `scripts/check-packed-manifests.mjs`, not by review:
`--sweep` asserts every dependency spec is `catalog:`/`workspace:`; `--packed` packs all
8 publishable packages with pnpm and asserts no exact peer, no ranged dependency, and no
leaked `catalog:`. Baseline was 30 violations; the gate now requires 0.

## Consequences

- `npm i @vexcms/core@alpha` works for a consumer on convex 1.45.0 — verified, 42
  packages installed, where the previous exact peers produced `npm ERESOLVE`. This is
  objective #1 of the launch plan.
- Every version change is now a reviewable diff in one file. The catalog is the single
  place a version can move, asserted by script.
- **Peer ranges duplicate type-bearing libraries unless every peer is also pinned as a
  devDependency.** pnpm auto-installs an unsatisfied peer at the range's *maximum*, so
  it lands beside the `catalog:`-pinned copy. `packages/react` declared none of its 7
  peers as devDeps (while `packages/core` already declared all 6), and a from-scratch
  resolve produced `@tanstack/react-query` at both 5.101.2 and 5.102.8 — two nominally
  distinct type identities — failing `docs#build` with `TS2322` on
  `relationship/Input.tsx`. `convex` doubled identically. Any new package MUST follow
  core's pattern.
- **The lockfile remains the only pin on the transitive closure.** Pinning the catalog
  binds direct dependencies only; ~250 transitive packages float without
  `pnpm-lock.yaml`. It stays committed, and CI must keep `--frozen-lockfile`. An earlier
  draft of this policy claimed "nothing can silently move"; that is false as stated and
  the measurement is recorded so nobody re-derives it optimistically.
- **Install settings live in `pnpm-workspace.yaml`, never `.npmrc`.** pnpm 10 reads
  `strict-peer-dependencies` from `.npmrc` as a no-op: set there, a plain `pnpm install`
  *printed* the unmet peer and still exited 0. `.npmrc` keeps only npm-generic keys
  (`shamefully-hoist`, `save-exact`, the auth token).
- A genuinely urgent upstream security patch is unreachable for 72 hours without an
  explicit `minimumReleaseAgeExclude` entry. Accepted: the window is the control.
- Adding a name to `onlyBuiltDependencies` grants arbitrary code execution at install
  time. A fresh install currently blocks 7 scripts (core-js, esbuild ×2, msw ×2, sharp,
  unrs-resolver) and the tree works regardless, because the ones that matter ship
  prebuilt platform binaries. Require evidence a package cannot work without it.
- The `@convex-dev/better-auth>better-auth` allowedVersions entry is stale upstream
  metadata, not a real incompatibility — 0.12.5 peers `>=1.6.11 <1.7.0`, which our
  1.6.23 satisfies. Delete it when that upgrade lands; the step-6 gate fails if it is
  still needed and passes if it is not.
- Supersedes nothing, but tightens ADR-005's closing note ("publishing must go through
  `pnpm`") from a caution into an enforced check.
