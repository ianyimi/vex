# ADR-013: The config splits into a client-safe half and a server half, and the RSC serialization path is deleted

- Status: accepted
- Date: 2026-09-15

## Context

`sanitizeConfigForClient` existed to move `VexConfig` across the RSC boundary. Its
`Sanitized<T>` type mapped `(...args: any[]) => any` to `null`, so **every** function in
the config arrived on the client as `null` — each field's `validate`, each
`admin.condition`, each custom `admin.components` entry — and `ClientVexConfig` was
declared as `Sanitized<Omit<VexConfig, "access">>`, so the access matrix was dropped
outright.

Three providers existed only to smuggle the stripped values back around that hole:
`VexAccessProvider` (the access matrix, imported directly in the app's
`clientProviders.tsx`), `StorageAdapterContextProvider` (the client-side `uploadFile`
map), and a family of config-shaped props threaded from server layouts into client views
(`AdminLayout`'s `config`, `CollectionListView`'s `collection`, …). Two views had already
grown "read from context, fall back to the RSC prop" blocks, which means the same
collection could reach a component by two different paths with two different fidelities.

The question was whether to keep repairing the serialization layer or remove the boundary
the config crosses.

## Decision

**Split the config into two files and delete the serialization path.**

- `vex.config.ts` resolves through `defineConfig(input): VexClientConfig` and is imported
  **directly into the browser bundle**. It carries `admin`, `access`, `collections`,
  `globals`, `mediaCollections`, `authCollections`, `basePath`, `routes`,
  `storage.clientUploads`, `schema`, and `types`.
- `vex.config.server.ts` wraps it with `defineServerConfig({ config, server })`, adding
  only `server.auth.adapter` and `server.storage.adapters`, and returns `VexConfig`.
- `sanitizeConfigForClient`, `stripNonSerializable`, and `ClientVexConfig` are deleted
  rather than deprecated.

Three sub-decisions follow, each load-bearing:

**Placement rule: a field is server-only if putting it on the client half would break the
client bundle** — not if the server reads it. `VexConfig extends VexClientConfig`, and the
CLI loads the server config, so a field on the client half is still reachable from every
server consumer. Only `auth.adapter` and `storage.adapters` fail the test (a server SDK, a
class instance, an env read). `schema` and `types` are inert path strings read solely by
the CLI, and they stay on `vex.config.ts` so that file remains the single one a developer
opens to change any project setting.

**`VexConfig` spreads `VexClientConfig` rather than nesting it.** The rejected
`{ client, server }` shape would have forced every existing `config.collections` /
`config.access` / `config.routes` reader in `packages/` and both apps to rewrite to
`config.client.*` — a repo-wide signature change for no behavioral gain. As built, the
migration for server readers was an import repoint, nothing more.

**Auth collections reach the client as data produced by a function, not by codegen.** The
auth adapter cannot run in a browser graph: `betterAuthAdapter` derives its collections
via `getAuthTables(options)`, and a real Better Auth options object reads
`process.env.BETTER_AUTH_SECRET` / `SITE_URL` and pulls `better-auth/next-js` →
`next/headers` through its plugin list. The first implementation therefore had
`vex generate` evaluate the adapter server-side and emit a committed
`src/vex.auth.ts` artifact that the client config imported, guarded by a content hash.
That was reversed on review (see "Reversal" below).

**Every config-shaped prop crossing server → client is deleted; components resolve by slug
from context** (P-001). `NextAdminPage` keeps its `config: VexConfig` prop: it is a server
component handing data to another server function, which is not a serialization boundary.

## Consequences

**Double module evaluation is accepted and bounded.** The client config module compiles
into both bundle graphs and evaluates once in each, so the server and the browser each hold
a deep-equal but reference-unequal copy. Three failure modes were checked, not assumed:
identity comparisons across the copies — none exist, every config comparison in
`packages/{core,react,next}/src` is slug/string-keyed with zero `WeakMap` usage; dual
provenance — eliminated by deleting the props, so there is exactly one path; and eval
nondeterminism — ruled out because `defineConfig` is pure (no `Date.now`, `Math.random`,
module-level registry, or env read), a property pinned by a deep-equal purity test.

**`access` now ships to the browser.** This was already true in intent — the app imported
it into `VexAccessProvider` — but it is now explicit in the config. P-004's posture is
unchanged: client-side permission checks are advisory UI gating; server API guards remain
the enforcement point.

**Access validation moved.** It runs in `defineConfig`, where the merged collections
(including auth collections) are already known, so an access rule naming a nonexistent
index fails at config load rather than in a query.

**Two client entry points were added** so declaring config no longer drags server code into
the browser: `@vexcms/file-storage-convex/client` (`defineMediaCollection`, `uploadFile`)
and `@vexcms/better-auth/client` (`betterAuthCollections`). Traced: the file-storage client
entry reaches 2 modules and imports no `convex` subpath.

**P-005 is superseded and deleted**; P-004 was rewritten. The distinction P-005 drew
between RSC-serialized props and direct-import modules stopped being a live constraint the
moment the serialization path was removed.

## Reversal: codegen'd auth collections → a function the client config calls

The first implementation shipped a generated `src/vex.auth.ts` in the user's project, plus
`hashAuthCollections`, a drift check keyed on that hash, a `VEX_CLI_BOOTSTRAP` escape
hatch, and a two-phase `loadConfig` (seed a placeholder → import → regenerate → re-import
with a fresh jiti instance, because the client config imported the file the server config
produced). The developer rejected it on setup experience: a generated JSON-shaped module
imported by a hand-authored config.

Three measurements decided the replacement:

- `getAuthTables` reads only data and accepts plain `{ id, schema }` plugin descriptors —
  **4.6 KB min / 1.1 KB gzip**. It does not need real plugin instances.
- Instantiating the real plugin factories client-side instead costs **+684 KB min /
  +154 KB gzip** on this repo's plugin set, so "just call the adapter in the browser" was
  never viable.
- A Better Auth client plugin carries `$InferServerPlugin: {} as …` — a type-only cast,
  `{}` at runtime — so `authClient` can never yield field definitions. That option is
  closed, not merely expensive.

So `@vexcms/better-auth/client` exports `betterAuthCollections(schema)`, which resolves a
declarative plugin-descriptor map against a schema snapshot committed **inside the package**
and runs it through the existing adapter conversion. The codegen still exists, but at the
dependency boundary rather than in every user's project: `gen:auth-schemas` regenerates the
snapshot, a parity test asserts it still equals what the installed Better Auth produces, and
a compile-time exhaustiveness assertion over a type-only `import type * as` of
`better-auth/plugins` fails this package's typecheck when an upstream release adds a plugin.

Verification moved server-side and lost its artifact: `defineServerConfig` compares the
client config's declared `authCollections` against the live `auth.adapter.collections` and
throws `VexAuthConfigError` naming the divergent collection or field. `server.auth` is
optional — a project with no auth omits it, and so does one that does not want the check.
`hashAuthCollections`, `generateAuthCollections`, `VEX_CLI_BOOTSTRAP`, the two-phase
`loadConfig`, `auth.outputPath`, and every `vex.auth.ts` are deleted.

The check earned its place immediately: it caught `apps/test`'s organization plugin losing
`teams: { enabled: true }` during the refactor, which had silently stopped the adapter
producing the `team` / `teamMember` collections.

## Alternatives rejected

- **Keep `sanitizeConfigForClient` and accept `null` functions.** This is the status quo
  whose cost is three providers, two prop-fallback blocks, and silently dead `validate` /
  `condition` / `components` on the client.
- **Nest the halves as `{ client, server }`.** Repo-wide reader rewrite, no gain.
- **Derive auth collections from `authClient`.** Impossible at runtime; client plugins
  carry no schema.
- **Instantiate real Better Auth plugins in the client config.** +154 KB gzip, and it
  permanently constrains every schema-bearing plugin to be client-bundle-safe.
- **Server-derives-and-injects auth collections through the provider.** Workable — auth
  collections are plain data and would serialize — but it reintroduces a config-shaped RSC
  prop and makes `useVexConfig().collections` differ from the raw `vex.config.ts` import.
