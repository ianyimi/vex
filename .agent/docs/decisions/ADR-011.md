# ADR-011: One server-side write-validation stage; `validate()` is server-only and async

- Status: accepted
- Date: 2026-09-12

## Context

The question was whether to add validation hooks alongside the document-operation
hooks of ADR-010, or whether db-operation hooks would cover most cases. Answering
it surfaced that the premise was wrong: there is nothing to hook.

**`create`'s entire write path is three steps** — `hasPermission` →
`stampUpdatedAt` → `db.insert` (`api/create/server.ts:62-104`). No validation stage
exists. Yet the field docstrings assert one does:

> `min`/`max` are runtime validation constraints, NOT schema constraints … They
> don't affect the generated Convex value type. Validation happens in the admin
> panel **and mutation handlers**.
> — `fields/text/validator.ts:12-14`; identical text at `fields/number/validator.ts:12-14`

The admin-panel half is true: `adminFieldToInputSchema`
(`fields/inputSchemas/index.ts:1-62`) builds Zod schemas and `AppForm.tsx:16` uses
them as the form's single source of truth. The mutation-handler half is false —
grep of `api/create` and `api/update` finds no `inputSchema`, `zod`, `safeParse`,
or `validate` reference.

What Convex's own schema validation enforces on `db.insert`/`patch`:

| Enforced server-side | Not enforced anywhere server-side |
|---|---|
| types — `v.string()`, `v.number()` | `text` min/max length |
| required vs optional — `v.optional(…)` | `number` min/max value |
| `select` option membership — a real literal union, `v.array(v.union(v.literal("draft"), …))` (`select/validator.ts:30-36`) | `date` min/max timestamp |
| | `array` / `blocks` / `upload` min/max count |
| | `url` well-formedness — `v.string()` only |

So a caller using the documented Local API (`docs/guides/local-api.mdx`) can write
10,000 characters into `text({ max: { value: 100 } })`. The `data` payload also
crosses the network boundary as `v.any()` (`api/create/server.ts:30`,
`api/update/server.ts:34`), with shape checking described as happening in CLI
codegen at build time.

ADR-010's after-hooks cover none of this: they are after-write by construction.

## Decision

Add **one before-write stage** to the shared write path. Transform first,
validation last, because the invariant that matters is *whatever reaches the
database satisfies the declared constraints*.

```
resolveAuth
  → hasPermission(changes = caller's raw payload)   ← unchanged
  → beforeChange(doc)        transform + derived fields        (ADR-010)
  → generated Zod            structural constraints — exists, never ran server-side
  → validate(field)          custom per-field rules; async; receives ctx
  → stampUpdatedAt                                  ← unchanged
  → db.insert / db.patch
  → triggers: afterChange / afterDelete             (ADR-010)
```

Three sub-steps, one insertion point. Running the already-generated Zod schemas
server-side is the load-bearing part and adds **no public API surface** — it simply
makes two docstrings true.

### `validate()` is server-only, async, and receives `ctx`

"Slug must be unique" is the most-requested CMS validation, requires a database
read, and is racy in most frameworks. Convex mutations are transactional, so a
`validate()` running `ctx.db.query("posts").withIndex("by_slug", …)` inside the
same mutation is genuinely sound. That is a real Convex advantage and it is worth
designing *for* rather than around — so `validate()` is async and `ctx`-bearing
rather than a pure `(value) => boolean`.

The consequence is a two-tier validation model, which must be documented
explicitly:

| Tier | Where it runs | Covers |
|---|---|---|
| Generated Zod | Client **and** server | Structural constraints — required, min/max, enum membership |
| `validate()` | Server only | Anything needing `ctx` — uniqueness, cross-document rules |

Client-side Zod cannot read the database, so a uniqueness check will not fire in
the form. Users must not be left to discover that.

## Consequences

- **Payload's `beforeValidate` / `afterValidate` are not ported.** One transform
  stage plus one validation stage covers their use cases with half the surface.
- **Partial updates need a partial validation mode.** `update` takes `Partial<…>`
  (`api/update/server.ts:37`) but `adminFieldToInputSchema` builds whole-document
  schemas, because the admin form seeds every field. Running them against a patch
  fails `required` on every absent key. Validate only keys present in the patch and
  skip required-ness for absent ones. **This is the most likely source of a
  regression in this work.**
- **The lenient mode above is what versioning/drafts will reuse.** A draft save
  must persist an incomplete document without tripping `required`, which is the
  same requirement partial `update`s impose today. That is why this ADR ships
  *before* drafts: the mode is built for a reason that already exists, so drafts
  consume it rather than this stage being generalized speculatively on their
  behalf. Design the mode as an explicit, named option rather than an inference
  from "is this a patch", so the drafts spec can request it directly.
- **Hooks receive the merged document, not the patch.** `update` already loads the
  stored row in order to authorize against it, so merge `stored ∪ patch` before
  calling hooks — cross-field rules such as `endDate > startDate` must work on a
  partial write. No additional read is incurred.
- **Ordering after `hasPermission` is mandatory**, for the field-map reason spelled
  out in ADR-010's consequences.
- **This is a behavior change for existing alpha consumers.** Writes that violated
  `min`/`max` and previously succeeded will begin to fail. Correct, and it needs a
  changeset that says so plainly rather than being filed as a fix.
- **`select` needed no work.** Its validator already emits a literal union, so
  option membership was the one declarative constraint already enforced at the
  database layer. Do not "fix" it.
