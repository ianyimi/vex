# ADR-008: The app build owns Convex deployment

- Status: accepted
- Date: 2026-09-04

## Context

`apps/www` deploys to Vercel from `master`. Its `build` script was `next build`
and no `vercel.json` existed, so the Vercel build compiled the Next.js app and
nothing else. Deploying the Convex functions was a separate manual
`npx convex deploy` documented in `apps/www/README.md`.

That separation held for exactly as long as someone remembered it. Once it was
missed, the production deployment `usable-bee-730` kept serving function code
from an earlier commit while Vercel served the current frontend, and the two
failure modes that produced both looked like application bugs:

- `convex run seed:init` executed the **deployed** `seed.ts`, so a content
  change committed to the repo and re-seeded on production had no visible
  effect. It presented as "the seed data was not updated".
- Access control enforced the **deployed** `access.ts`. The matrix before
  `9051c15` had `adminPanel: { access: false }` for the `user` role and no
  `pages` read grant, so the freshly deployed Next.js route admitted a caller
  (`canAccessAdminPanel` passing against the new matrix) whom the Convex
  queries then denied against the old one. It presented as RBAC being broken in
  production while working locally.

Both are the same fault, and neither is observable from the frontend build:
`next build` succeeds, typecheck succeeds, and the deployed app is internally
consistent. Only the backend is behind.

## Decision

The frontend build deploys the backend. `apps/www/vercel.json` sets:

```json
{
  "buildCommand": "pnpm turbo run build --filter=www^... && pnpm deploy:convex && pnpm build"
}
```

with a `deploy:convex` script (`convex deploy`) beside it. All three steps are
load-bearing, and the first two were each learned from a failed deploy.

**The workspace packages must be built first.** This was the second failure. A
fresh clone has no `packages/*/dist`, and every `@vexcms/*` package resolves
through an `exports` map pointing into it — `@vexcms/core`'s `./server` subpath
is `./dist/api/server.js`. Convex's bundler therefore reported
`Could not resolve "@vexcms/core/server"` from `convex/theme.ts`, and `next build`
would have failed identically a moment later for `@vexcms/react`. Both are the
same fault as the first failure — a gitignored build output that does not exist
yet — and neither is reproducible in a working copy, where `dist` is always
populated. `--filter=www^...` selects the app's dependencies and excludes the app
itself, so Turborepo orders the builds and nothing is built twice.

**Why `convex deploy` and not `vex deploy`.** `vex deploy` is the richer command
— it regenerates the schema and runs any auto-migration before deploying — and
it was the first choice. It cannot work here. The `vex` binary comes from
`@vexcms/cli`, a workspace dependency whose `bin` field points at
`packages/cli/dist/index.js`, and `dist` is gitignored (`.gitignore`: `/**/dist`,
zero tracked files). On a fresh CI clone that target does not exist until the CLI
is built, so pnpm has no working shim to link and the build dies immediately
with `sh: vex: command not found` — which is exactly what the first deploy
attempt did. Building the CLI inside the app's build to get its binary inverts
the dependency and slows every deploy for no gain. `convex` is a *published*
dependency of `apps/www`, so its binary exists the moment `pnpm install`
finishes.

Nothing is lost. The three generated artifacts — `convex/vex.schema.ts`,
`convex/schema.ts`, `src/vex.types.ts` — are committed, so `convex deploy` ships
the same schema `vex deploy` would have generated. `vex dev`'s watcher keeps them
current during development and `turbo typecheck` fails if they drift, which makes
the commit, not the build, the place where schema freshness is enforced.

`convex deploy` requires `CONVEX_DEPLOY_KEY` in the Vercel project environment.
When it is absent the command fails and the **whole build fails**. That is the
decision, not a side effect: a deployment that silently skipped the backend is
strictly worse than one that refuses to ship, because it produces a frontend
and a backend that disagree, and the disagreement surfaces as unrelated
application bugs days later.

## Consequences

- Frontend and backend can no longer drift on this project. A commit either
  deploys both or deploys neither.
- `CONVEX_DEPLOY_KEY` becomes a hard deployment prerequisite. It is documented
  in `apps/www/README.md`'s Deployment section alongside the Convex-side
  `SITE_URL` and the two `NEXT_PUBLIC_CONVEX_*` URLs.
- A committed `buildCommand` overrides whatever is configured in the Vercel
  dashboard. This is intentional — the build contract is reviewable in the repo
  — but it means dashboard edits are silently ineffective, so the file is the
  place to change it.
- Committed generated artifacts become load-bearing for deployment, not just for
  typecheck. `convex deploy` does no codegen, so a commit whose
  `vex.schema.ts` is stale deploys a stale schema. `turbo typecheck` is the
  guard; it must stay in the commit gate.
- Auto-migration does NOT run in CI, because `convex deploy` does not invoke it.
  A schema change needing `vex deploy`'s migration path must be run by hand
  against production before the commit that depends on it lands.
- Switching back to `vex deploy` requires `@vexcms/cli` to expose a binary that
  survives a fresh clone — either by publishing and depending on the released
  package rather than the workspace one, or by building the CLI ahead of the app
  in CI. Neither is worth doing for this app today.
- The templates still document the manual `npx convex deploy`. They are not
  Vercel-specific and ship no `vercel.json`, so scaffolded projects keep the
  older instruction until a deploy story is chosen for them. That is a known
  gap, not an oversight.
