# ADR-005: Declarations from `tsc --emitDeclarationOnly`, not tsup

- Status: accepted
- Date: 2026-08-30

## Context

All seven published packages carried `dts: false` in `tsup.config.ts`, annotated
"Temporarily disable DTS to fix CPU issue", while every `package.json` advertised
`types: "./dist/index.d.ts"`. That file was never emitted, so every published tarball
resolved to `any`. The flag had been in place since commit 9421c4b and outlived its note;
ADR-001 already records it as collateral damage ("`dts:false` leaves no `.d.ts` to resolve
against" was one reason `entryPointStrategy: "packages"` was rejected for TypeDoc).

Two independent problems were tangled together:

1. **CPU.** tsup's rollup-dts bundler pegs a core on this dependency graph — generic-heavy
   source with deep cross-package type references. This is the problem the original flag
   was reacting to, and it is real.
2. **TS6059, `File is not under rootDir`.** The workspace uses a `source` export condition
   so dev tooling resolves siblings to their `src/`. Under declaration emit that pulls
   another package's source files into the current program, outside its `rootDir`. This
   is why simply flipping `dts: true` never worked, and it is a separate issue from CPU.

An earlier declaration-emit experiment (2026-08-04) hit this and left 186 stray
`*.d.ts`/`.d.ts.map` files scattered through `packages/*/src` before being abandoned.

## Decision

Split the two outputs by tool: **tsup builds JavaScript, `tsc` builds declarations.**
Each package's build script is
`tsup && tsc -p tsconfig.build.json --emitDeclarationOnly`.

`dts: false` **stays** in every `tsup.config.ts` — it is now load-bearing configuration
rather than a temporary workaround, and each comment says so.

Resolve TS6059 at the resolution layer, not by relaxing `rootDir`: every
`tsconfig.build.json` sets `"customConditions": []`, so workspace dependencies resolve
through their published `types` entry (`dist/*.d.ts`) instead of the `source` condition.
Turbo's existing `dependsOn: ["^build"]` guarantees upstream `dist/` exists first.

Dev configs (`tsconfig.json`, `tsconfig.check.json`) are untouched and still resolve
through `source`, preserving go-to-definition and single-pass workspace typecheck.

Where a package genuinely reaches into another package's source, fix the import rather
than widen `rootDir`. `@vexcms/better-auth` imported `AuthFieldMeta` from
`../../core/src/auth/types`; `AuthFieldMeta` is now exported from `@vexcms/core` and the
adapter imports the barrel.

## Consequences

- Published packages ship types. Verified by packing `@vexcms/core`: the tarball contains
  `dist/index.d.ts` and `types` points at it.
- Two build steps per package instead of one; `tsc` is the slower half but does not pin a
  core the way rollup-dts did.
- A cross-package deep source import is now a build error, not just bad practice. Any
  type shared between packages must be part of the exporting package's public surface.
- `tsconfig.build.json` is now required in every published package (`react` and
  `richtext-plate` gained one).
- **Publishing must go through `pnpm`.** `npm pack` leaves `catalog:` literals in
  `dependencies`; `pnpm pack` resolves them.
- Unblocks reconsidering TypeDoc's `entryPointStrategy: "packages"` (ADR-001's rejection
  cited the missing `.d.ts` as one of its two reasons). Not revisited here — the
  cross-program type-identity errors were the other, and they are unaddressed.
