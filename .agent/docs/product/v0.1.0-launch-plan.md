### Sequencing principle

Each spec consumes what earlier specs built. **No spec writes inert code whose only
justification is a later spec.** Applying that rule rejected three things an
earlier draft of this plan called for; the reasoning is recorded because it is what
stops the order drifting back.

**1. F moves ahead of C.** The earlier draft told C to "route draft writes through
a shared write pipeline so F can insert one stage instead of five" — which is
exactly the anti-pattern: C building structure whose only payoff is F. With F
first, the pipeline already exists and C simply calls it. Four further reasons the
swap is strictly better:

- F closes a live correctness hole — `min`/`max` on every field are unenforced
  server-side today (see F's Finding 2). Every alpha consumer is affected now, and
  the behavior change wants maximum shake-out time before 0.1.0.
- F is core API. Freezing it before the two largest features consume it beats
  co-evolving them.
- C is the biggest, riskiest spec in the track (56 open tasks in
  `2026-08-23-versioning-drafts`). If it slips, F has already shipped value.
- **The mechanism drafts need from F is independently required today.** A draft
  save must be able to persist an incomplete document without tripping `required`
  — and F already needs exactly that lenient mode for ordinary partial `update`s
  (ADR-011, constraint 2). So F builds nothing speculative for C; C reuses a mode
  that exists for its own reasons.

  Verified there is no reverse retrofit: `_status`/`_version` are framework-owned
  and read-only, so they flow past validation the way `updatedAt` already does;
  and "does `afterChange` fire on a draft save?" is a semantic question C answers
  by *calling* F's dispatcher. Were C first, it would have to invent hook
  semantics with no hook system to hang them on.

**2. B2 ships a decision, not a reserved config flag.** See B2.

**3. A stops half-wiring what I rebuilds.** See A's scope split.

### Hard ordering constraints

Only these five are real. Everything else may be resequenced freely.

1. **B before F and D.** B2's localization decision determines whether validation
   runs per-locale and what a `richtext()` value's storage shape may be. It is a
   decision document, so it blocks on nothing and costs a day.
2. **F before C, D, G, H, I.** Everything downstream either calls the hook
   dispatcher or renders its validation errors. Server-only async validation is a
   different render path from instant client Zod errors; building the inputs first
   means reworking every error display.
3. **The config-split spec before E — ☑ done.** Splitting the config into
   per-runtime client/server entry points is tracked outside this track but was
   a prerequisite here: it is what lets `livePreview.url` be a function rather
   than a serializable template, by removing the `sanitizeConfigForClient`
   function stripping rather than working around it. **Shipped in `ed502a9`
   (ADR-013), 2026-09-15** — E can build directly against the function form; no
   fallback needed. It also unblocked collection-level `admin.components.preview`,
   so live preview and the relationship field remain its two consumers.
4. **J last.** It audits the finished surface. Running it earlier audits a surface
   that is about to change.
5. **B3 before the 0.1.0 tag** (and ideally before I, whose list-view filters
   consume `where`). After the tag, renaming `filter` → `where` needs a
   deprecation cycle; before it, it is a clean cutover.
6. **B2 (ADR-016) before G step 9 — ☑ done.** Server-side condition enforcement and the
   form renderer read values by field path; the localization storage shape had to be fixed
   first.
7. **G steps 7–8 before H and I.** The core slot model, slot outlet and single field
   registry are what H's edit-view slots and I's list-view slots build on; G's `adminHref`
   (step 17) is what H's route move edits.
8. **K pass 1 after B3, before H.** B3 (implemented 2026-10-25) renamed the access query
   layer and rewrote `api/find/server.ts`, `api/search/server.ts` and `api/queryArgs.ts` —
   files K moves; K starts from the post-B3 tree. H rebuilds the edit view on the form layer
   K replaces (`createFieldInput`, `AppFormContext`); building H first and porting it after is
   the inert-then-rewrite pattern the sequencing principle rejects.

**E moved ahead of C** for the same reason, once the transport was pinned down
(ADR-012). Reading unsaved form state over `postMessage` removes the only thing
that needed drafts — verifying autosave against the preview. C then changes only
the overlay's *base layer*, which is additive. It also means the two public-API
specs (F and E) both land before the two big feature specs consume them.

A secondary payoff, and an independent argument for the design: an
autosave-to-shared-draft preview gives every editor of a document one shared
state, which is the last-write-wins problem `backlog.md`'s concurrent-edit entry
describes. Per-editor form state sidesteps it, so live preview is not blocked on
the concurrency design.

`A` before `I` is no longer a constraint — the overlap that created it has been
removed from A's scope.

**Ships before versioning/drafts.** Reading unsaved form state removes the only

on (fetch the draft instead of the published document), which is additive.

### Design (ADR-012)

**Transport: `postMessage`, not `localStorage`.** `livePreview.url` is
user-configured and may be a different origin, and `localStorage` is
origin-partitioned — a cross-origin preview can never read the admin's store. A
`postMessage` transport has to exist regardless, and once it does `localStorage`
adds jank, a quota, persistence to clean up, and a documented throw hazard
(`ui/ThemeProvider.tsx:36-56`) without adding capability. Persistence across a
preview reload is handled by a **handshake** — the preview announces the document
it renders on mount, the admin replies with current values.

**Shape: overlay the consumer's own result; do not let a wrapper *be* the
mechanism.** Making a `useVexQuery` wrapper the only path was rejected — it would
force every consumer onto one fetching library, permanently commit us to
re-exposing TanStack's option surface, strand RSC `initialData` consumers, and
fail to compose at nested render sites. Instead the provider holds an
`id → unsaved values` map and a hook shadows whatever the consumer already
fetched:

```tsx
const { data: pages } = useQuery({ ...convexQuery(api.pages.getBySlug, { slug }), initialData })
const page = useVexPreview(pages?.[0])
```

That works against the template's current TanStack Query + `convexQuery` path
(`apps/www/src/app/(frontend)/(site)/PageContent.tsx:31-34`), a raw Convex
`useQuery`, or an RSC-passed `initialData`. The `id → values` map (rather than "the
one document under edit") solves nesting for free: a page rendering a
`relationship` to an author, while the author is the document being edited,
overlays correctly because each render site resolves its own document by id.

A `useVexQuery` convenience **may still ship as sugar over that primitive** —
`useQuery + useVexPreview` composed is a few lines and gives the transparent call
consumers reasonably want. Build the primitive first; add the helper if the
ergonomics warrant it.

**Matching: on `doc._id`.** The admin knows `(collection, id)`; the preview target
fetches by slug but the fetched document carries `_id`. No storage-key scheme, no
URL contract, no configuration. Two cases `_id` alone misses, both carried in the
handshake payload:

- **A document being created has no `_id`** — match on a client-generated
  temporary id in the preview URL plus the collection slug.
- **The merge is not a shallow spread.** `{ ...doc, ...values }` destroys nested
  `group` and `blocks` values when the form holds a partial subtree; it must walk
  the field config. `useLiveFieldMerge` already solves this in the opposite
  direction (server values into form state) — extract the shared logic rather than
  writing a second merge.

**No preview route — the target is the real route.** A single app-wide `/preview`
route that receives a path plus live data and renders the matching page was
rejected: Next's App Router has no `renderRoute(path, data)` primitive, so it
would need a `/preview/[...path]` catch-all re-implementing the app's own routing,
every previewable page refactored into a data-injectable component, and the
preview rendering through a different code path than production. Instead
`livePreview` resolves a document to its **real** URL; the real route picks up the
overlay. Pixel-identical to production because it is production, and no new route
to secure.

**Centralize the provider, not the route.** The appeal of one preview route was
having a single place to secure, with public routes carrying no listener. Keep
that property without the routing duplication: one `<VexLivePreviewProvider>`
mounted in the layout owns the gate, the origin check, and the transport, while
the rendered route stays the real one. When the gate is off it installs no
listener and `useVexPreview` returns the document untouched, so production pays
nothing. This is how Next's own `draftMode()` is shaped — a request-level flag,
not a parallel route tree.

**`livePreview.url` is a function, per the config-split spec.** As the config
stands, `sanitizeConfigForClient` strips every function before it reaches the
browser (`fields/relationship/preview.tsx:11-16` depends on this;
`config/sanitizeConfig.test.ts:93-102` demonstrates the nulling), which would
force a serializable interpolating template. **A separate spec splitting the
config into per-runtime client/server entry points lands before this one**, so
authored functions survive to the client and `url: (doc) => string` works. That
buys paths interpolation cannot express — locale prefixes, nested category
segments, conditional routes — and it also unblocks collection-level
`admin.components.preview`, which `resolveRelationshipPreview`'s own docstring
currently calls impossible in the browser. If the split slips, fall back to the
template; the overlay architecture is unaffected.

**Lifecycle hooks do not run on preview data.** `beforeChange` is server code with
a mutation `ctx` and is not contractually pure, so running it per keystroke could
fire webhooks or write rows — and it would need a server round trip, destroying
the local-overlay latency that is the point. Unlocking it properly needs a new
contractually-pure `derive` hook class, which would run client-side and is scope
creep on F. Document the limitation.

### Scope

- `postMessage` transport with a mount handshake, origin-checked both directions
  against a configured allowlist.
- `<VexLivePreviewProvider>` holding the `id → values` map, and `useVexPreview`.
- **Add `livePreview` to the collection admin config.** It exists only on globals
  today — `globals/types.ts:36, 63` declare `livePreview?: { url: string }`;
  `collections/types.ts`' `AdminCollectionConfigInput` declares nothing, despite
  `core/README.md:192-197` claiming "collection/global". Widen `url` to the
  function resolver form on both.
- Preview panel in the collection and global edit views; support both an embedded
  iframe and a popped-out window.
- Gate preview mode per request — see the security requirements below.
- Wire the marketing template and `apps/www` as the dogfooding consumer.

### Security — design this, do not discover it

The preview surface is the customer's **public** site. A route that
unconditionally listens for `postMessage` and renders the payload lets anyone
iframe it and inject content — spoofing now, XSS on the customer's domain once
richtext renders markup. All four are required:

1. Origin allowlist, explicitly configured rather than inferred.
2. Preview mode opt-in per request. In the default scaffold the admin is same-site
   and authenticated, so the route can verify the session cookie rather than share
   a secret.
3. Validate the payload against the field schema before rendering — the generated
   `adminFieldToInputSchema` Zod schemas exist for exactly this.
4. Richtext renders through the sanitizing renderer, never raw payload HTML.

### Acceptance

- Typing in a field updates the preview with no save and no autosave configured.
- A preview reload recovers current state via the handshake.
- A cross-origin `livePreview.url` works; a non-allowlisted origin is rejected.
- Two editors on one document each see their own unsaved changes.
- A `blocks` field re-renders on reorder and on per-block field edits.
- Preview respects RBAC — a field the role cannot read is never rendered.
- Documented limitation: the preview shows pre-hook state, so a `beforeChange`
  derived value does not appear until save.

### Constraints that must be in the design, not follow-ups

1. **`changes` must reach `hasPermission` on every draft write path.**
   Field-level RBAC denies a write by inspecting `changes` against a resolved field
   map — `create` does this at `api/create/server.ts:86-88`. `DRAFT_ACTIONS`
   (`access/constants.ts`) already types `readDrafts`/`saveDraft`/`publish`/
   `unpublish`, with **zero implementers**. If `saveDraft` omits `changes`, a role
   restricting a field on `update` gets no equivalent restriction on a draft save.
2. **Reuse the existing reserved-key machinery for `_status` / `_version`.**
   `RESERVED_COLLECTION_FIELDS` (`collections/constants.ts:40-57`) already gives
   compile-time rejection, runtime rejection, and a `meta.locked` escape hatch.
   Do not invent a second mechanism.
3. **Draft writes call F's write pipeline; they do not build one.** F ships first
   precisely so this is consumption rather than construction. Two things to reuse
   rather than reinvent:
   - the **lenient validation mode** F built for partial `update`s — a draft save
     persists an incomplete document without tripping `required`;
   - the **hook dispatcher**, so C only has to answer the semantic question of
     which hooks fire on `saveDraft` versus `publish`.
4. **`vex_versions` per the A-ratified `vex_` convention**, and per-locale versus
   whole-document snapshots per B2's ADR.

### Acceptance

- `versions.drafts: true` produces a real draft/publish workflow: reads return the
  published document by default, `readDrafts` returns drafts, `publish` promotes.
- Field-level RBAC applies identically to `update` and `saveDraft` — proven by a
  test, not by inspection.
- Version history is viewable and a prior version restorable from the edit view.
- Autosave writes drafts, never the published document.
- `core/README.md:119-126` and `:184-190` rewritten from "not shipped" to shipped.
- Live preview's base layer can fetch the draft instead of the published document
  — additive to E, which already handles the overlay.

### B2 — Localization: decide the model, ship no code ✅

> **Decided:** nested per-field locale maps keyed by configured locale codes; opt-in per
> collection and per field (field wins); localized containers localize their whole subtree
> and children may not override; whole-document publish; reads flattened by an independent
> `locale` key with fallback (`locale: "all"` for raw maps); localized full-text search via
> one `vex_`-prefixed search table (Convex allows 4 search indexes per table); built into
> the free core. See `.agent/docs/decisions/ADR-016.md`. The text below is the original

There is **zero** localization support in `core/src` today. That is fine for 0.1.0
test projects. What is not fine is deciding it *after* users have data, because
locale variants change how fields are stored and no optional config flag makes a
data migration non-breaking.

**Correction to an earlier draft of this plan.** It called for reserving
`localized?: boolean` on fields and `localization` on the root config — parsed,
stored, enforcing nothing — by analogy with `livePreview: { url }` and
`versions.drafts`. That analogy does not hold, and the reservation should not be
built:

- Adding an optional config option later is **already non-breaking**. The
  reservation buys nothing a future additive change would not.
- The genuinely breaking part is the stored shape of localized data, which an
  inert boolean does nothing to protect.
- An inert flag is worse than an absent one: a user sets `localized: true`, gets
  no localization, and reasonably reports it as broken.

So B2's deliverable is **an ADR and nothing else**:

- **Adapter interface vs built-in.** The adapter framing is plausible —
  `VexAuthAdapter` / `VexStorageAdapter` are the established extension pattern —
  but localization touches schema generation, which no existing adapter does.
  Decide, and record why the other was rejected.
- **Storage shape.** Sibling columns (`title_en`, `title_fr`), nested map
  (`title: { en, fr }`), or row-per-locale. This is the irreversible choice; the
  rest is additive.
- **Interaction with versioning.** Whether a version snapshot is per-locale or
  whole-document. C needs this answer, which is the second reason B precedes it.

**Why the decision must still land before D and F:** a `richtext()` value's
storage shape has to be compatible with the chosen model, and validation has to
know whether it runs per-locale. A decision is sufficient for both. No code.

**Acceptance:** an ADR recording the model, the storage shape, the versioning
interaction, and the rejected alternatives with reasons. Zero production diff.

### B3 — Backend-neutral query arguments ⏳

**Spec:** `.agent/docs/specs/2026-10-21-backend-neutral-query-args/` (10 steps, 0–9, all
`[agent]`). **Why:** `find`/`search` expose Convex's own `IndexRangeBuilder`/`FilterBuilder`
types in their public arguments (`api/find/server.ts` `FindServerArgs`), and project
`validate()` code throws `ConvexError`. A later database-adapter split
(`.agent/docs/research/db-adapter-feasibility.md`) would then break every consumer. The
fix reuses the Vex constraint builders the access layer already ships:

- `withIndex.range` is typed and compiled through the Vex index builder. The call syntax is
  unchanged, so all existing call sites compile as they are.
- `filter` → `where`, built with the access layer's filter builder (`q.eq("field", v)`,
  `and`/`or`/`not`). No app or template uses `filter` today.
- Access rules: the `constraints` callback splits into `withIndex` and `where` properties
  (decided 2026-10-23), each mapping 1:1 onto the `find` argument of the same name. `withIndex`
  takes the same static `{ name, range }` object as `find`, or a function of the caller
  returning one (decided 2026-10-25). `where` is the portable predicate; `withIndex` is the
  Convex index pushdown, which moves into the Convex adapter at the split with no call-site
  change. The rule-level `filter` property keeps its name. Any combination is allowed;
  `withIndex` alone and `withIndex` + `filter` are the expected common shapes.
- `VexError` replaces `ConvexError` in `validate()` code.
- A field's `index` takes a name or `{ name, additionalFields?, draftStatus? }` (spec step 5,
  decided 2026-10-25): compound indexes can be declared on their first field, field-level
  indexes win over collection-level ones of the same name, and two fields may not share an
  index name. One resolver feeds the schema, generated types, access validation and draft status.
- **`where` also accepts a plain, JSON-serialisable form** (`VexWhereNode`, with
  `validateWhereNode` and `whereToNode`; spec step 7, decided 2026-10-21) — I's saved views
  and URL filters store it; later an MCP server, plugin collections and adapters send it.
- **Client `find` / `search` take `where`** (spec step 8, decided 2026-10-23); a callback is
  converted to the plain form before it is sent. A `where` cannot probe a field that
  field-level RBAC hides from the caller.
- ADR-015 records the rule: no public signature exposes `convex/*` types except `ctx`; and
  `@vexcms/core/server` stays the permanent import path, with adapters plugging in beneath it.

No adapter interface or package split (Track DB). Readiness work that must precede the
plugin system rather than 0.1.0 is in `.agent/docs/specs/2026-10-21-adapter-readiness/stem.md`.

**Acceptance:** `find`/`search` accept `where` (builder or plain form) and no `filter`, on the
server and the client; a malformed plain `where` fails with `VexError` `INVALID_WHERE`; access
rules use `withIndex` / `where` and no `constraints`; a client `where` on a hidden field returns
no documents; no `api/*` public signature references
`IndexRangeBuilder`/`FilterBuilder`/`ExpressionOrValue`; `apps/test`, `apps/www`, and both

Two findings drive this spec's shape.

### Finding 1 — after-hooks cover none of validation

`convex-helpers` triggers are after-write by construction. They cannot reject a
write or transform a payload. They cover cascading deletes, denormalized counts,
webhooks, revalidation dispatch — and none of slugify, derived fields,
sanitization, uniqueness, or rejecting bad input.

### Finding 2 — constraints we already ship are not enforced server-side

`create`'s entire write path is `hasPermission` → `stampUpdatedAt` → `db.insert`
(`api/create/server.ts:62-104`). **There is no validation stage.** Yet the field
docstrings claim there is:

> `min`/`max` are runtime validation constraints, NOT schema constraints …
> Validation happens in the admin panel **and mutation handlers**
> — `fields/text/validator.ts:12-14`, identical in `fields/number/validator.ts:12-14`

The admin-panel half is true (Zod via `adminFieldToInputSchema`, `AppForm.tsx:16`).
The mutation-handler half is false — no `inputSchema`/`zod`/`validate` reference
exists in `api/create` or `api/update`.

| Enforced server-side (by Convex schema validation on write) | Not enforced anywhere server-side |
|---|---|
| types — `v.string()`, `v.number()` | `text` min/max length |
| required vs optional — `v.optional(…)` | `number` min/max value |
| `select` option membership — real literal union, `select/validator.ts:33-36` | `date` min/max timestamp |
| | `array` / `blocks` / `upload` min/max count |
| | `url` well-formedness (`v.string()` only) |

A caller using the documented Local API (`docs/guides/local-api.mdx`) can write
10,000 characters into `text({ max: { value: 100 } })`.

So the deliverable is **the stage**, not the hook. `validate()` is nearly free once
a before-write stage exists, because it is the same insertion point as
`beforeChange`.

### The pipeline

One stage in the shared write path. Transform first, validation last, because the
invariant is *whatever hits the DB satisfies the declared constraints*.

```
resolveAuth
  → hasPermission(changes = caller's raw payload)   ← unchanged
  → beforeChange(doc)        transform + derived fields
  → generated Zod            structural constraints (exists; never runs server-side)
  → validate(field)          custom per-field rules; async; receives ctx
  → stampUpdatedAt                                  ← unchanged
  → db.insert / db.patch
  → triggers: afterChange / afterDelete
```

**Two hook points, not four.** One transform stage plus one validation stage
subsumes Payload's `beforeValidate` / `afterValidate`. Do not port the full ladder.

### Implementation constraints

1. **The stage goes after `hasPermission`, mirroring `stampUpdatedAt`.**
   `api/create/server.ts:92-94` already states the rule: framework-added values go
   after the check so payload-dependent rules see exactly what the caller sent.
   Sharper reason: field-level RBAC inspects `changes`, so a `beforeChange` running
   *first* would let our own slugify hook add `slug` to `changes` and get **denied**
   for a role holding `update: () => ({ title: true })`.
2. **Partial updates need a partial validation mode.** `update` takes
   `Partial<…>` (`api/update/server.ts:37`) but `adminFieldToInputSchema` builds
   whole-document schemas — the form seeds every field. Running them against a
   patch fails `required` on every absent key. Validate only present keys; skip
   required-ness for absent ones. **This is the detail most likely to bite.**
3. **Hand hooks the merged document.** `update` already loads the stored row to
   authorize against it, so merge `stored ∪ patch` and give hooks a complete
   document — cross-field rules (`endDate > startDate`) must work on partial
   writes. No extra read.
4. **`validate()` is server-only, async, and receives `ctx`.** See ADR-011.
   Uniqueness is the most-requested CMS validation, needs a DB read, and is racy
   in most frameworks — but Convex mutations are transactional, so a `validate()`
   querying `ctx.db` inside the same mutation is genuinely sound. Generated Zod
   runs on both client and server for instant feedback; `validate()` is
   server-only because it can read the DB. Document the split so nobody expects a
   uniqueness check to fire in the form.

### Triggers integration

`convex-helpers/server/triggers` is **not a Convex component** — no
`convex.config.ts`, no `app.use()`. It is a plain library:
`new Triggers<DataModel>()` + `customMutation(rawMutation, customCtx(triggers.wrapDB))`
(source: `get-convex/convex-helpers`, `packages/convex-helpers/server/triggers.ts:57-89`).

Already a dependency of `@vexcms/core` — `convex-helpers: catalog:`, pinned
`0.1.120` in `pnpm-workspace.yaml:54`. Zero new dependencies.

- **Their loudest caveat does not apply to us.** "Forget the wrapper and triggers
  silently never run" is fatal in a hand-written app; we *generate* the mutations,
  so codegen guarantees every write uses the wrapped builder. Structural advantage
  — exploit it, and add the codegen assertion.
- **Coverage hole to document, not fix.** Triggers do not fire for Convex dashboard
  edits, `npx convex import`, or another component's direct writes. This is the
  same hole `backlog.md` records for server-side revalidation dispatch. Document
  hooks as "fire on writes through the vexcms API", never "always".
- **Veto semantics need a probe.** The maintainers state a throwing trigger
  rethrows from the `ctx.db.*` call while also describing the write as committed —
  ambiguous against Convex's normal transaction rollback. Verify empirically before
  designing any throw-to-reject behavior. Independent of the outcome, `before*`
  hooks live in the server path where rejection is unambiguous.
- **Recursion is BFS-queued**, and multiple triggers on one table can observe each
  other's intermediate denormalized state. Note it in the hook docs.

### Acceptance

- `text({ max: { value: 100 } })` rejects a 101-character write through the Local
  API, not just through the form.
- The two lying docstrings (`text/validator.ts:12-14`,
  `number/validator.ts:12-14`) become true.
- A partial `update` touching one field does not trip `required` on absent fields.
- `beforeChange` deriving `slug` from `title` is not denied by a field-map role
  that can only write `title`.
- An async `validate()` performing a `ctx.db` uniqueness query rejects a duplicate.
- `afterChange` / `afterDelete` fire through generated mutations; a codegen test
  asserts no generated mutation uses the raw builder.
- Hook coverage limits documented in a guide.

### Pass 2 — the review method

One reviewer agent per package or app: `core`, `react`, `next`, `cli`, `better-auth`,
`file-storage-convex`, `richtext-plate`, `create-vexcms` (both templates), `apps/test`,
`apps/www`, `apps/docs`. Each reads its whole tree and reports on:

- **Grouping** — domain or layer; code that lives away from its only consumer; folders that
  mix domains.
- **File roles** — every filename that recurs (`config.ts`, `types.ts`, `index.ts`,
  `server.ts`, `utils.ts`, `constants.ts`, `Input.tsx`, `Cell.tsx`, …): what the role means,
  and any file whose content does not match its role name.
- **Exports and imports** — what each `index.ts` re-exports and whether it should exist;
  package `exports` entries; import direction (domain → shared, never the reverse, no
  cycles); relative imports that cross into another domain's internals.
- **Identifiers** — functions, types, variables, constants, booleans, hooks, components:
  does the name say what the value *is in that context*? The case to look for: `field`
  means a field config in core and a TanStack `FieldApi` in react, where the config is
  `fieldDef`. Also the existing families to confirm or reject: `<type>FieldToValidator`
  converters, `Xxx` / `XxxInput` resolved/input pairs, `XxxServerArgs`, `XxxProps`.

Every finding is one of three kinds, each with paths and counts:

- **Convention** — observed and consistent; proposed as a rule with examples.
- **Violation** — breaks an observed convention; proposed fix.
- **Gap** — no consistent convention exists; the options, with how many files follow each.

Reports land in the spec folder (`review-<n>.md`). The developer decides each violation and
gap; decisions become a new step group in `spec-tasks.md` and are implemented as pass 3.
Passes 2–3 repeat until a review returns no open violation or gap. The same review re-runs as
task 16 over the code H, I, J and M add.

  extension points (slots) that plugins will build on; shell slots (nav, dashboard,
  custom routes) and server-component slots are Track PL / backlog.
